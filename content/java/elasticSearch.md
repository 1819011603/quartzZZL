**解释一下Elasticsearch中的Term Query、Match Query、Bool Query的区别及应用场景。**

在Elasticsearch中，查询（Query）是搜索操作的核心，用于从索引中检索匹配特定条件的文档。Term Query、Match Query和Bool Query是三种常用的查询类型，它们各有特点和适用场景：

1. **Term Query**

**定义**：Term Query用于精确匹配字段的完整值，不会进行任何分析（即不会使用分析器），而是直接查找与指定term完全相同的值。这适用于已知确切值且不需要文本分析的情况，如ID查找或枚举型字段的查询。

**应用场景**：

- 查询具有固定值的字段，如产品ID、状态码等。
- 需要精确匹配而不进行分词的场景。

2. **Match Query**

**定义**：Match Query是一种全文本查询，它会对查询字符串应用分析器（与字段映射中定义的分析器相同），然后尝试匹配经过分析后的文档。这意味着它支持模糊匹配，更加灵活，但同时也意味着搜索时的精确度可能不如Term Query。

**应用场景**：

- 全文搜索，比如搜索商品名称或描述。
- 当用户输入较为自由，可能包含多个词或短语，且希望获得模糊匹配结果时。

3. **Bool Query**

**定义**：Bool Query（布尔查询）是一种复合查询类型，允许通过must（必须匹配）、should（应该匹配，相当于OR）、must_not（必须不匹配）和filter（过滤，不影响评分）子句组合多个查询条件，提供非常灵活的查询逻辑构造能力。

**应用场景**：

- 复杂查询逻辑，如同时满足多个条件或排除某些条件的查询。
- 结合多种查询类型，比如同时使用Match Query进行全文搜索和Term Query进行精确过滤。
- 通过filter子句高效过滤结果，不会影响相关性评分，适合用于基于某些属性的筛选。

**总结**

- Term Query适合精确匹配需求，尤其是在不需要文本分析的场景。
- Match Query适用于全文搜索，提供了更灵活的文本匹配能力。
- Bool Query是构建复杂查询逻辑的基石，通过组合不同的查询子句，可以满足多维度、多层次的搜索需求。

**如何使用Filter和Query结合来优化搜索性能？**

在Elasticsearch中，结合使用Filter和Query是优化搜索性能的一种常见策略，特别是在那些既要根据关键词进行全文搜索，又要根据特定条件过滤结果的场景。这种策略利用了两者的不同特点：

- **Query**：用于执行全文本搜索或任何影响文档相关性得分的操作。它计算每篇文档与查询条件的匹配程度，并为每篇文档分配一个_score，表示相关性高低。
- **Filter**：用于执行精确匹配的条件筛选，不计算相关性得分，因此比Query更快。Filter的结果可以被Elasticsearch自动缓存，进一步提升后续相同过滤条件的查询速度。

**结合使用方法**

使用Bool Query来组合Query和Filter，Bool Query允许你在单个查询中同时指定必须匹配（must）、应该匹配（should）、必须不匹配（must_not）和过滤（filter）的子句。其中，filter子句就是用来放置过滤条件的地方，而must或should子句可以用于全文本查询。


假设我们要搜索包含关键词“blue shoes”的文档，但只对那些状态为“published”且价格在100至200之间的商品感兴趣，可以构建如下查询：
```
GET /my_products/_search

{
  "query": {
    "bool": {
      "must": [
        {
          "match": {
            "description": {
              "query": "blue shoes",
              "operator": "and"
            }
          }
        }
      ],
      "filter": [
        {
          "term": { "status": "published" }
        },
        {
          "range": {
            "price": {
              "gte": 100,
              "lte": 200
            }
          }
        }
      ]
    }
  }
}
```


在这个例子中，match查询作为must子句执行全文搜索，确保文档包含“blue”和“shoes”这两个词。而term和range查询则作为filter子句，精确筛选出状态为“published”且价格在指定范围内的文档，这些条件不影响相关性得分，但会提高查询效率，特别是当这些过滤条件经常重复使用时，由于缓存机制，性能提升更加明显。

**优化提示**

- 对于频繁使用的过滤条件，考虑使用过滤器缓存。
- 尽可能将不涉及相关性评分的条件放入filter子句中，以减少计算负担。
- 监控和调整缓存策略，确保高效利用资源。
- 定期审查和优化映射，确保字段类型和分析器设置正确，减少不必要的全文搜索开销。

**深分页问题**

然而，当分页深入到较后页时（深分页），比如请求几千甚至几万页之后的数据，会出现性能问题。这是因为Elasticsearch为了获取指定范围的结果，需要遍历所有匹配的文档，然后丢弃掉前面的文档，直到达到from指定的位置，最后返回size指定数量的文档。随着from值的增大，这种机制会导致以下问题：

1. **性能损耗**：Elasticsearch需要扫描更多文档才能找到所需的结果集，这会显著增加查询延迟。
2. **资源消耗**：深分页可能导致内存和CPU使用率上升，尤其是在数据量大、分片多的情况下。
3. **潜在的错误**：Elasticsearch有一个index.max_result_window设置，默认为10000，限制了from + size的最大值，以防止资源耗尽。

###  为什么去掉类型？

在 Elasticsearch 中，**索引（Index）** 是存储数据的逻辑单元，类似于关系型数据库中的数据库，而 **类型（Type）** 是 Elasticsearch 6.x 及更早版本中用于分类数据的一个概念，类似于数据库中的表。不过，从 Elasticsearch 7.x 开始，不建议使用类型，Elasticsearch 8.x 中已完全移除类型。因此，这里会分别说明不同版本的创建索引方式。


### 1. **ID 唯一性冲突问题**

在 Elasticsearch 中，每个文档的 `_id` 是唯一的，而多类型共享一个索引的情况下，不同类型中的文档实际上存储在同一个索引中。这就意味着所有类型的文档必须共享相同的 `_id` 空间。


**问题场景**：如果在同一个索引中，两个类型的文档使用相同的 `_id`，后添加的文档会覆盖前面的文档，造成数据丢失。 比如都使用1这个id


```
PUT /my_index/type1/1
{ "field": "value1" }

PUT /my_index/type2/1
{ "field": "value2" }  # 这会覆盖 type1 的文档

```


- **影响**：ID 冲突会破坏数据完整性，开发和维护难度也会加大。



### 2. **映射（Mapping）冲突问题**

多类型共享一个索引，这意味着不同类型中的字段名称必须兼容，因为它们的底层存储（Lucene 索引）是共享的。

- **问题场景**：如果不同类型中字段名相同，但数据类型不同，映射冲突会导致索引无法使用。

```
{
  "type1": {
    "properties": {
      "field1": { "type": "text" }
    }
  },
  "type2": {
    "properties": {
      "field1": { "type": "keyword" }
    }
  }
}

```

在这个例子中：

- `type1` 将 `field1` 定义为 `text` 类型（适合全文搜索）。
- `type2` 将 `field1` 定义为 `keyword` 类型（适合精确匹配）。

**问题**：

1. Elasticsearch 允许字段名相同，但它们的类型必须一致。
2. 在底层 Lucene 中，`field1` 无法同时存储为 `text` 和 `keyword` 类型的数据。
3. **结果**：会导致映射冲突，Elasticsearch 会报错，阻止索引写入或查询。


### 3. **设计上的冗余**

- 多类型设计本质上与关系型数据库的表类似，但 Elasticsearch 的核心思想是非结构化数据和文档式存储。多类型的概念与这种思想有冲突。
- 多类型会引导用户将 Elasticsearch 视为关系型数据库，从而滥用其功能，降低性能。




### **4 如何解决这个问题？**

Elasticsearch 从 7.x 开始去掉了类型（Type），鼓励用户使用以下替代方案来避免映射冲突：

#### **方法 1：每种数据类型使用单独的索引**

- 不同类型的数据存储在独立的索引中。
- 每个索引有自己独立的映射，字段不会冲突。

#### **方法 2：在同一个索引中使用标识字段（如 `type` 字段）**

- 如果必须将多种类型的数据存储在同一个索引中，可以通过一个额外的字段（如 `type`）标识不同的数据类别。


#### **方法 3：使用索引模式**

- 使用索引模式（Index Pattern）管理多个索引，如 `products-*` 和 `orders-*`。
- 在查询时可以一次性查询匹配的所有索引。



### 倒排索引是什么 快的原因是什么 是不是大概就是一个`Map<String,List<Integer>>`

- 存储包含该关键词的文档 ID 列表，以及其他相关信息（如词频、位置等）。

```yml
今天: [ Doc1: (词频=1, 位置=[1]), Doc2: (词频=1, 位置=[1]) ]
```


Elasticsearch中的倒排索引（Inverted Index）是一种特殊的数据结构，它颠覆了常规的文档到单词的索引方式，转而建立了从单词到文档的映射关系。这意味着，倒排索引并不关注文档中单词出现的顺序，而是记录了每个单词出现在哪些文档中以及它们在文档中的位置。这种结构极大提升了全文搜索的效率，具体体现在以下几个方面：

1. **快速定位文档**：在倒排索引中，每个单词都有一个条目，该条目指向包含该单词的所有文档的ID列表。这意味着，当你搜索一个关键词时，Elasticsearch可以直接查找到该词对应的文档ID列表，而不是逐个文档去检查是否包含该词，大大减少了搜索所需的时间。
2. **支持复杂查询**：倒排索引不仅记录了单词到文档的映射，还包括了单词在文档中的位置信息，这使得它能够支持布尔查询、短语查询、同义词替换、模糊匹配等多种复杂的查询类型，增强了搜索的灵活性和准确性。
3. **减少I/O操作**：由于索引已经预先计算好，搜索时直接访问内存中的索引条目即可，避免了频繁的磁盘I/O操作，这对于大规模数据集来说至关重要，因为磁盘I/O往往是性能瓶颈所在。
4. **优化资源利用**：通过分词和标准化处理（如小写转换、去除标点符号等），倒排索引确保了即使用户输入的查询词形式与文档中的不完全一致，也能正确匹配到相关文档，提高了搜索的召回率。
5. **支持高效过滤和排序**：倒排索引可以附加额外信息，如文档频率（DF）、词频（TF）等，这些信息在计算文档的相关性评分（如TF-IDF）时至关重要，从而支持高效的排序和相关性筛选。



1. **明确字段类型**：为每个字段明确指定合适的数据类型，如text、keyword、integer、float、date等。这不仅影响数据的存储方式，还决定了查询时的处理逻辑，比如text字段会经过分析器处理，而keyword字段则不会。
2. **使用分析器**：对于text类型字段，选择合适的分析器至关重要。分析器负责将文本分解成词汇单元（tokens），不同的分析器适用于不同的语言和需求。错误的分析器可能导致搜索效率低下或结果不准确。
3. **禁用不必要的字段索引**：对于不需要被搜索的字段，可以将其索引属性设为false，这样可以减少索引的大小和提高写入速度。例如，只用于聚合或显示的字段可以选择不建立索引。
4. **控制动态映射**：动态映射虽然方便，但可能会导致意外的字段类型推断错误，影响查询效率。适当限制或完全关闭动态映射，并为所有预期字段手动定义映射，可以提高系统的稳定性和性能。
5. **使用Keyword和Text字段搭配**：对于需要精确匹配和全文搜索的场景，可以为同一字段定义两个子字段，一个作为text用于全文搜索，另一个作为keyword用于精确匹配和排序。
6. **合理使用忽略_above**：对于高基数的字段（如用户ID），可以设置ignore_above参数来忽略超过指定长度的值，避免因大量独特值导致的内存消耗。
7. **映射模板**：利用映射模板来自动化地为符合特定条件的新字段应用预定义的映射，这有助于保持映射的一致性并减少手动配置的工作量。


**如何处理分析器（Analyzer）和Tokenizer？举例说明自定义分析器的场景。**

在Elasticsearch中，分析器（Analyzer）负责将文本字段的内容转换成可供搜索的词项（tokens）。一个完整的分析器由三部分组成：字符过滤器（Character Filters）、分词器（Tokenizer）和标记过滤器（Token Filters）。它们共同协作，完成文本的预处理、分词和后处理。

**分词器（Tokenizer）**

分词器是分析器的核心部分，它负责将输入的文本切分成一个个的token（词元）。例如，标准分词器（Standard Tokenizer）会按照Unicode文本段落边界规范来切分文本，适用于大多数欧洲语言。

**标记过滤器（Token Filters）**

标记过滤器在分词之后对生成的token进行操作，如转换为小写、去除停用词、同义词替换等。例如，Lowercase Token Filter会将所有的token转换为小写，这对于实现不区分大小写的搜索非常有用。

**字符过滤器（Character Filters）**

字符过滤器在分词前对文本进行处理，如移除HTML标签或特殊字符。

## 1. **布尔查询（Boolean Query）**

**实现原理：** 布尔查询基于布尔逻辑操作（AND、OR、NOT）组合多个关键词，快速筛选文档。

- **倒排索引：** 每个关键词对应一个文档列表。例如：
    
    
    `"今天": [1, 2, 3] "天气": [2, 3, 4]`
    
- **操作逻辑：**
    
    - **AND（交集）**：返回同时包含多个关键词的文档。
        
        
        `查询 "今天 AND 天气" => 交集: [2, 3]`
        
    - **OR（并集）**：返回包含任意一个关键词的文档。
        
        
        `查询 "今天 OR 天气" => 并集: [1, 2, 3, 4]`
        
    - **NOT（差集）**：排除包含某个关键词的文档。
        

        
        `查询 "今天 NOT 天气" => 差集: [1]`
        

**优化技术：**

1. **跳跃表（Skip List）：**
    - 跳过不相关的文档 ID，加速集合操作。
2. **文档频率排序：**
    - 优先处理文档较少的关键词，减少计算量。

---

## 2. **短语查询（Phrase Query）**

**实现原理：** 短语查询要求关键词按照特定顺序连续出现。例如，查询 `"今天 天气"` 只匹配包含这两个词并且顺序正确的文档。

- **倒排索引扩展：** 倒排列表除了存储文档 ID，还存储每个关键词在文档中的位置。例如：

    
    `"今天": [Doc1: [1], Doc2: [1]] "天气": [Doc1: [2], Doc3: [1]]`
    
- **匹配过程：**
    
    - 在倒排索引中找到两个关键词的文档列表及位置。
    - 检查关键词的位置是否满足顺序和间隔要求：
        

        `查询 "今天 天气" Doc1: "今天" 在位置 1，"天气" 在位置 2 => 匹配 Doc2: "今天" 在位置 1，没有 "天气" => 不匹配`
        

**优化技术：**

- **邻近查询（Proximity Query）：** 支持关键词之间允许一定距离（如 "今天 天气" 可以匹配 "今天真的是好天气"）。

---

## 3. **同义词替换（Synonym Replacement）**

**实现原理：** 同义词替换允许将查询关键词替换为其同义词，从而扩大搜索范围。例如，查询 `"汽车"` 同时返回包含 `"车"` 的文档。

- **同义词词典：** 定义同义词关系，例如：
    

    
    `"汽车" -> ["车", "轿车"]`
    
- **处理流程：**
    
    - 在查询阶段，扩展用户输入的关键词：
        

        
        `查询 "汽车" => 查询 "汽车 OR 车 OR 轿车"`
        
    - 在索引阶段，存储文档时扩展同义词，使搜索时无需扩展。

**优化技术：**

1. **查询时扩展：** 查询扩展到多个同义词的倒排列表。
2. **索引时扩展：** 将同义词直接存入索引，减少查询时计算量。

---

## 4. **模糊匹配（Fuzzy Matching）**

**实现原理：** 模糊匹配支持匹配拼写错误或相似的关键词。例如，查询 `"苹果"` 也可以匹配 `"苹果"` 或 `"appl"`。

- **编辑距离（Edit Distance）：** 衡量两个词的相似度，常用 Levenshtein 距离（允许插入、删除、替换操作）。
    
- **处理流程：**
    
    - 在查询阶段，计算查询词与索引中词的编辑距离。
    - 返回编辑距离小于某阈值的匹配结果。
- **倒排索引优化：**
    
    - 构建一个 **k-gram 索引**（n-gram 分片）：
        
        
        `"苹果" -> ["苹", "果"] "appl" -> ["ap", "pp", "pl"]`
        
    - 查询时，找到共享 k-gram 的词，并计算编辑距离。

**优化技术：**

1. **阈值限制：** 限制编辑距离，减少计算开销。
2. **k-gram 索引：** 仅比较可能相关的词，避免全表扫描。

---

## **查询速度快的原因**

1. **倒排索引：**
    
    - 将关键词直接映射到文档列表，避免扫描全文。
2. **高效数据结构：**
    
    - 跳跃表、B+ 树、布隆过滤器等结构加速查询。
3. **并行计算：**
    
    - 多线程处理不同关键词的倒排列表。
4. **压缩技术：**
    
    - 差值编码、跳跃表减少存储和计算负担。
5. **缓存和优化：**
    
    - 常用查询的结果缓存。
    - 查询规划器优化查询顺序（如优先处理小集合）。


在 Elasticsearch 中，字段类型定义了数据的存储方式和查询处理逻辑。常见字段类型主要分为几类，包括文本类型、数值类型、日期类型、布尔类型、地理类型、对象类型和特殊类型等。以下是详细说明：

---

### **1. 文本类型**

- **`text`**
    
    - **特点**: 用于存储全文本内容，通常需要分词和索引。
    - **存储方式**: 数据会经过分析器（Analyzer）处理，分词后存储到倒排索引中。
    - **查询逻辑**: 支持全文搜索（如 `match` 查询），可以按词匹配。
    - **用途**: 搜索引擎中处理文章、描述等需要分词的文本。
- **`keyword`**
    
    - **特点**: 用于存储短文本或精确匹配的字段。
    - **存储方式**: 原样存储，不分词，直接建立倒排索引。
    - **查询逻辑**: 支持精确匹配（如 `term` 查询）和聚合操作（如 `terms aggregation`）。
    - **用途**: 存储唯一标识符、标签、分类、状态等。

---

### **2. 数值类型**

- **整型字段**
    
    - `integer`（32 位）: 存储范围约为 -2³¹ 到 2³¹-1。
    - `long`（64 位）: 存储范围约为 -2⁶³ 到 2⁶³-1。
- **浮点型字段**
    
    - `float`（单精度）: 存储范围和精度适合较小的浮点数。
    - `double`（双精度）: 存储更大的浮点数范围，更高精度。
- **特点**:
    
    - 以压缩形式存储，支持范围查询（如 `range` 查询）。
    - 索引时会直接存储数值在倒排索引中，无需分析器处理。
- **用途**:
    
    - 用于统计、排序、范围查询，如价格、评分、计数等。

---

### **3. 日期类型**

- **`date`**
    - **特点**: 用于存储日期和时间数据，支持多种格式。
    - **存储方式**: 转换为毫秒级时间戳存储。
    - **查询逻辑**:
        - 支持范围查询（如 `range` 查询）。
        - 支持日期数学运算（如 `now-1d/d` 表示昨天）。
    - **用途**:
        - 存储时间戳、事件时间、日志时间等。

---

### **4. 布尔类型**

- **`boolean`**
    - **特点**: 表示 `true` 或 `false` 的布尔值。
    - **存储方式**: 通常用 1 位存储。
    - **查询逻辑**:
        - 支持精确匹配。
    - **用途**:
        - 存储标志字段，如是否启用、是否删除等。

---

### **5. 地理类型**

- **`geo_point`**
    
    - **特点**: 用于存储地理坐标（经纬度）。
    - **存储方式**: 存储为点坐标，支持特定的地理空间算法。
    - **查询逻辑**:
        - 距离查询（如查找附近的点）。
        - 地理边界查询（如矩形、多边形范围内查找）。
    - **用途**:
        - 存储位置数据，如商家地址、用户位置等。
- **`geo_shape`**
    
    - **特点**: 用于存储复杂的地理形状（如多边形、线）。
    - **查询逻辑**:
        - 支持地理空间交集、包含等复杂查询。
    - **用途**:
        - 地理信息系统（GIS）相关应用。

---

### **6. 对象和嵌套类型**

- **`object`**
    
    - **特点**: 用于存储键值对形式的数据。
    - **存储方式**: 每个字段会独立索引，类似于扁平化处理。
    - **查询逻辑**:
        - 支持对字段的精确匹配查询。
- **`nested`**
    
    - **特点**: 用于存储嵌套对象。
    - **存储方式**: 将每个嵌套对象视为独立文档，但逻辑上与父文档绑定。
    - **查询逻辑**:
        - 支持对嵌套字段的组合条件查询，确保上下文一致。

---

### **7. 特殊类型**

- **`ip`**
    
    - **特点**: 用于存储 IPv4 或 IPv6 地址。
    - **查询逻辑**:
        - 支持范围查询（如 CIDR 查询）。
- **`binary`**
    
    - **特点**: 用于存储二进制数据（如文件或图像的哈希值）。
    - **查询逻辑**:
        - 通常不支持直接查询，仅用于存储。

---

### **处理逻辑的对比**

| 类型          | 是否分词 | 支持全文搜索 | 支持精确匹配 | 支持聚合 | 支持排序 | 适用场景    |
| ----------- | ---- | ------ | ------ | ---- | ---- | ------- |
| `text`      | 是    | 是      | 否      | 否    | 否    | 搜索文章描述等 |
| `keyword`   | 否    | 否      | 是      | 是    | 是    | 标签、状态等  |
| `integer`   | 否    | 否      | 是      | 是    | 是    | 年龄、数量等  |
| `float`     | 否    | 否      | 是      | 是    | 是    | 价格、评分等  |
| `date`      | 否    | 否      | 是      | 是    | 是    | 时间戳、日期等 |
| `boolean`   | 否    | 否      | 是      | 否    | 否    | 是否启用标志  |
| `geo_point` | 否    | 否      | 是      | 是    | 否    | 经纬度坐标   |



### **常用分词器和分析器总结**

- **英文**: 使用 `standard` 或 `simple` 分词器。
- **中文**: 推荐使用 **IK 分词器**。
- **精确匹配**: 使用 `keyword` 分词器。
- **模糊搜索/补全**: 使用 `ngram` 或 `edge_ngram` 分词器。
- **多语言支持**: 使用 `icu` 分析器。



- **模糊搜索**: 使用 IK 分词器后，通过 `fuzzy` 或 `match` 查询实现。
- **自动补全**:
    - IK 分词器适合用作基础分词工具。
    - 实现补全功能时，推荐结合 **Edge N-gram** 或 **Completion Suggester** 方案。

IK 分词器擅长分词，但模糊搜索和补全依赖 Elasticsearch 的查询策略与索引配置来实现。
