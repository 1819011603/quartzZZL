
# 继承的问题

优点:
	1. 复用, 缺点: 子类必须有该特点, 子类必须实现该方法, 有些特殊的子类有可能没有该方法, 绝大部分有该方法
		1. 为了这个特殊的子类, 会多上鸡肋的"特征".
		2. 空方法在某些场景可以解决这个问题, 但是如果此方法之前不是空方法, 这样会导致子类含有大部分重复代码. 如果该方法多了其他几种情况, 子类的该方法的代码会冗余. 比如实现赚钱方法的接口一开始只有赚钱的实现, 但有部分子类现在有了不赚钱的实现, 只能将父类的赚钱方法该为空闲,在子类实现各自的实现, 但这样会导致子类有多个实现的副本, 有重复代码. (当然可以在父类抽出公共方法实现不同的策略, 但这样代码就有些乱)

### 使用接口解决

	1. 复用: 将经常变化的行为抽出接口方法来实现行为
	2. 缺点:
		1. 每个子类都需继承和实现该接口 造成代码冗余
		2. 修改  改一下动全身


### 分开变化和不会变化的部分

使用变化行为的接口和对应的实现类, 组合进来, 这样就可以使得代码解耦

如果增加变化行为,  增加对应的实现类即可, 不会影响之前的代码.
如果不需要这个行为,  使用空实现的实现类即可, 不会因为特殊子类影响这个类的公共属性.

# 观察者模式

观察者模式定义了对象之间的一对多依赖,这样一来,当一个对象改变状态时,它的所有依赖者都
会收到通知并自动更新。


主题, 观察者, 事件,

### 核心概念

1. **事件 (Event)**：事件是要发布的数据载体，通常是某个类的实例，继承自 `ApplicationEvent`。
	1. 事件就代表类型和数据
2. **事件发布者 (Event Publisher)**：负责发布事件，通常是实现了 `ApplicationEventPublisher` 接口的 Spring 容器中的任何 bean。
3. **事件监听器 (Event Listener)**：负责处理特定类型的事件，通常是带有 `@EventListener` 注解的方法或实现了 `ApplicationListener` 接口的类。

### 装饰者模式

### 主要组成部分

1. **组件接口（Component）**：定义一个对象接口，可以给这些对象动态地添加职责。
2. **具体组件（ConcreteComponent）**：实现组件接口，代表具体的被装饰对象。
3. **装饰器抽象类（Decorator）**：实现组件接口，持有一个组件对象的引用，通常定义一个与组件接口一致的方法，并将请求转发给组件对象。
4. **具体装饰器（ConcreteDecorator）**：继承装饰器抽象类，并实现具体的装饰功能。

### 优点

1. **灵活性高**：可以动态地增加或删除对象的职责。
2. **遵循开闭原则**：通过使用装饰者模式，可以在不修改现有代码的情况下扩展对象的功能。
3. **细粒度控制**：可以通过多个具体装饰者类的组合，实现不同的功能扩展。

### 缺点

1. **复杂性增加**：由于使用了较多的类和对象，系统会变得更复杂。
2. **调试困难**：由于是通过组合多个装饰者对象来实现功能扩展，调试时可能比较困难。

### 应用场景

1. **需要扩展一个类的功能，或给一个类添加附加职责**。
2. **动态、透明地为对象增加职责**。
3. **需要通过子类扩展功能，但子类的数量太多，导致系统变得复杂**。
