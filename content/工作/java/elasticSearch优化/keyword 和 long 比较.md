

> 低基数选keyword，高基数选long，范围/排序/优先long，精确/聚合低基数keyword无敌！



并且long在低基情况下占用cpu高


聚合（terms aggregation）到底用keyword还是long？

## 🎯 结论速答

- 绝大多数场景下，聚合用keyword性能更好！

- 只有在超高基数（百万级唯一值）时，long才有优势。

## 📊 详细对比

|场景|唯一值数量|keyword聚合|long聚合|推荐类型|
|---|---|---|---|---|
|超低/低基数|<1万|极快|快|keyword✅|
|中基数|1万-10万|很快|快|keyword✅|

|超高基数|>100万|变慢/内存暴涨|稳定|long✅|


## 实际建议

- 绝大多数业务字段（状态、类型、标签、枚举等）聚合用keyword，性能最佳。

- 用户ID、订单号等超高基数字段聚合，建议用long，防止内存爆炸。

- 如果聚合字段基数不确定，建议mapping时keyword+long双写，聚合时根据实际基数选择。


###   Mapping写法

假设你有一个字段叫userId，既要支持精确聚合（keyword），又要支持高基数/范围/排序（long）：
```json
PUT /your_index

{

"mappings": {

"properties": {

"userId": {

"type": "long", // 主字段：long，支持范围/排序/高基数聚合

"fields": {

"keyword": {

"type": "keyword" // 子字段：keyword，支持精确聚合/过滤

}

}

}

}

}

}
```


不能用 user.long，只能用主字段名（如 userId），不能用 userId.long。


### 1. Elasticsearch多字段（multi-fields）机制

- 主字段：直接用字段名（如 userId），类型是你在mapping里声明的主类型（如 long）。

- 子字段：用 userId.keyword 这种形式，类型是你在fields里声明的（如 keyword）。
### 2. 为什么没有 userId.long？

- ES的multi-fields机制，只有主字段和你自定义的子字段。

- 主字段就是 userId，类型是long。

- 子字段你可以叫 keyword、raw、text，但没有long类型的子字段，也不会自动生成long子字段。


主字段直接用字段名，子字段用“字段名.子字段名”，没有long子字段！

## 3. 技术原理

### keyword类型

- 底层结构：倒排索引+FST（有限状态机）

- 优势：精确查找O(1)，低基数时内存极省，查询极快

- 劣势：唯一值多时Term字典膨胀，FST遍历和字符串比较变慢，内存消耗线性增长

### long类型

- 底层结构：BKD Tree（数值KD树）

- 优势：高基数下查找复杂度O(logN)，数值比较极快，内存消耗稳定，范围/排序/聚合都高效

- 劣势：低基数时比keyword慢（但差距不大），terms查询不是最优

## 选择建议

- 基数<1万：无脑用keyword

- 1万-10万：优先keyword，关注内存

- 10万-100万：混合mapping（keyword+long），看查询类型

- >100万：用long，keyword只做展示/聚合

- 有范围/排序/数值运算需求：必须用long

// Keyword类型查询过程 (超低基数)

2. 在倒排索引中直接定位

3. 返回预构建的文档ID列表

4. 无需额外计算

执行时间: O(1)

## ES中Keyword哈希冲突的真实原因

### 并不是传统的哈希表冲突

```
// ❌ 我之前的解释有误导性
// ES的Term字典不是简单的哈希表，而是更复杂的结构

ES Term字典实际结构：
┌─────────────────────────────────────┐
│ FST (Finite State Transducer)      │ ← 主要数据结构
├─────────────────────────────────────┤
│ Term Dictionary (sorted)            │ ← 排序的字符串字典
├─────────────────────────────────────┤
│ Term Index (sparse index)           │ ← 稀疏索引
└─────────────────────────────────────┘

// 性能瓶颈不是哈希冲突，而是：
1. 字符串前缀匹配的复杂度
2. FST遍历的开销
3. 内存局部性问题
```

### 真实的查找过程

```
// Keyword类型查找"12345678"的实际步骤：

步骤1: FST前缀匹配
- 从根节点开始
- 逐字符匹配 '1' → '2' → '3' → '4' → '5' → '6' → '7' → '8'  
- 每次字符匹配需要内存访问
- 复杂度: O(k) 其中k是字符串长度

步骤2: Term Dictionary定位
- 基于FST结果定位到Term Dictionary的位置
- 可能需要多次内存跳转
- 复杂度: O(1) 但常数较大

步骤3: 倒排索引访问
- 获取Term对应的倒排索引指针
- 读取posting list
- 复杂度: O(1)

总复杂度: O(k) + 常数开销
```
