
Servlet的本质是Web容器提供的HTTP处理抽象层。开发者通过继承`HttpServlet`类并实现特定方法（如`doGet()`），将业务逻辑嵌入HTTP请求处理流程中。而容器负责底层Socket操作、协议解析、请求分发及响应发送，确保高效与安全性.

绝大部分web项目本质就是基于tcp/ip协议在客户端与服务端互传数据包，而servlet使用最多的场景是HttpServlet也就是我们常说的http请求，所以我们只要按照http协议解析socket中的请求数据就行了。并且java.net包和java.nio包下分别提供了阻塞io、非阻塞io、异步io三种io模型api来读取网络socket中的数据，然后像tomcat这样的框架就通过这些api帮我们高效的从socket中读取http请求数据，然后按照HttpServlet中定义好的规范封装成HttpServletRequest对象传给我们，我们拿到数据后进行业务逻辑处理然后将业务数据写入HttpServletResponse，最后tomcat再通过socket将响应数据发送给客户端。所以servlet本质上就是在socket解析层和我们业务层中间的一个对象而已，web容器将解析后的数据传给servlet，最后servlet再将业务数据传给web容器。

### servlet


从你的原文来看，Servlet 主要由 **请求对象（Request）和响应对象（Response）** 组成：

- `ServletRequest` / `HttpServletRequest`：封装请求数据（URL、参数、Headers 等）。
- `ServletResponse` / `HttpServletResponse`：封装响应数据（返回 HTML、JSON、文件流等）。
- `service()` 方法：Servlet 核心逻辑，处理请求和响应。




### ServerSocket 的accept方法是什么时候调用的

ServerSocket与Socket不同。服务器套接字的作用是等待来自客户端的连接请求。一旦服务器套接字收到连接请求，它就会创建一个socket实例来处理与客户端的通信。


### **调用时机**

1. **服务器端调用 `accept()`，进入阻塞状态**：
    
    - `ServerSocket` 会一直监听指定端口，等待客户端连接。
    - `accept()` 方法会 **阻塞**，直到有新的客户端请求。
2. **客户端发起连接（`Socket.connect()`）**：
    
    - 客户端通过 `new Socket("host", port)` 连接到服务器。
3. **服务器端 `accept()` 返回，返回 `Socket` 对象**：
    
    - `accept()` 方法从 **等待状态** 变为 **就绪状态**，并返回一个 `Socket` 对象，用于与客户端通信。

`accept()` 方法的阻塞与返回**

- **返回**：当**操作系统检测到有可用连接**时，`accept()` 方法会立即返回，并提供一个新的 `Socket` 以供服务器端和客户端进行通信。

### **Servlet 的生命周期总结**

1. **初始化（`init()` 方法）**
    
    - 当 Servlet 第一次被调用时，服务器会**加载 Servlet 类**，并**调用 `init()` 方法**（只调用一次）。
2. **处理请求（`service()` 方法）**
    
    - **每次有请求**，服务器会：
        - **创建** `ServletRequest` 和 `ServletResponse` 实例（封装请求和响应数据）。
        - **调用 Servlet 的 `service()` 方法**，将请求和响应对象传递进去，处理 HTTP 请求（如 `doGet()` 或 `doPost()`）。
3. **销毁（`destroy()` 方法）**
    
    - 当服务器关闭或 Servlet 被卸载时，**调用 `destroy()` 方法**，用于释放资源。

### **简要流程**

**初始化（`init()`） → 处理请求（`service()`） → 销毁（`destroy()`）**

这个流程保证了 Servlet 只在启动时初始化一次，但**每个请求**都会创建 `ServletRequest` 和 `ServletResponse`，并调用 `service()` 方法处理。





###  暴露风险  应给用户ServletRequestFacade类 防止强制转换导致的接口暴露


**问题核心**：  
将自定义的 `Request/Response` 对象直接暴露给 Servlet 时，用户可通过强制类型转换获取内部敏感方法（如 `parse()` 和 `sendStaticResource()`），存在安全隐患。

**风险**：

- 恶意开发者可直接操作底层资源（如解析请求、发送静态文件），破坏容器安全边界。
    

**简洁解决方案**：  
**使用门面模式（Facade）**

1. 创建 `ServletRequestFacade` 和 `ServletResponseFacade` 类，仅暴露 Servlet API 的标准方法。
    
2. 在传递参数时，将自定义的 `Request/Response` 对象包装到门面类中，再传给 Servlet。


### 为什么还要用门面模式？

这其实是一场 **安全博弈**：

|防御层级|攻击成本|实际意义|
|---|---|---|
|**直接暴露**|直接转型：`(Request)request`|零成本，小学生都能破解|
|**门面模式**|反射操作：需知道字段名/类型|需要专业黑客技能|
|**门面+混淆**|反射+反编译：字段名被混淆|攻击成本指数级上升|
|**门面+安全管理器**|反射权限被JVM安全策略禁止|核弹级防御（但现实中很少启用）|
### 关键结论

1. **纵深防御原则**：  
    门面模式是 **安全防线中的一层**，而非终极解决方案。就像现实中的保险箱——防不住专业大盗，但能挡住99%的顺手牵羊。
    
2. **提高攻击成本**：  
    通过门面模式：
    
    - 迫使攻击者从 **「直接转型」** 升级到 **「反射+逆向工程」**
        
    - 结合代码混淆后，字段名会变成 `a`、`b` 等无意义字符，反射时需要遍历所有字段猜类型：

### 门面模式（Facade）核心作用一句话总结：

**用统一接口封装复杂子系统，降低使用成本，隐藏实现细节。**


### session

关于会话标识符（`jsessionid`），它是Java Servlet和JSP技术中用来跟踪用户会话的一种机制。通常情况下，会话ID通过cookie存储在客户端，这样每次客户端发送请求时，浏览器都会自动将这个cookie包含在请求头中发回给服务器，从而维持用户的会话状态。

然而，如果客户端禁用了cookie支持，或者开发者希望以其他方式传递会话ID，可以通过将`jsessionid`嵌入到查询字符串中来实现。例如，URL可能看起来像这样：`http://example.com/page;jsessionid=123456789`. 这种方法允许在不使用cookie的情况下保持会话跟踪，但它也有缺点，比如安全性问题（因为会话ID直接暴露在URL中）和用户体验上的不便（需要手动管理URL）。

总的来说，虽然使用cookie是最常见和推荐的方法，但在某些特定情况下，如需应对不支持或禁用了cookie的情况，将`jsessionid`放在查询字符串中是一个可行的替代方案。不过，应该注意采取适当的措施保护会话ID的安全性。



### 连接器


在这一章中，您学习了连接器是如何工作的。构建的连接器是Tomcat 4默认连接器的一个简化版本。如您所知，默认连接器由于效率不高已经被弃用。例如，它会解析所有的HTTP请求头，即使这些请求头在servlet中可能不会被使用。因此，默认连接器运行缓慢，并已被一个更快的连接器Coyote所取代，其源代码可以从Apache软件基金会的网站上下载。然而，默认连接器作为一个学习工具仍然非常有用，并将在第4章中详细讨论。






Http chunk 长度

在HTTP 1.1中，当发送方无法预先知道整个响应或请求的长度时，可以使用`Transfer-Encoding: chunked`来解决这个问题。这种方式允许数据被分块传输，每一块都以该块的大小（十六进制表示）开头，接着是回车换行符（CR/LF），然后是块数据本身。最后一个块的长度为0，表示数据传输结束。

根据您提供的示例，如果您想将38个字节的数据分成两块发送，第一块长度为29字节，第二块长度为9字节，那么实际的HTTP响应体可能会像下面这样构造：

深色版本

```
Transfer-Encoding: chunked

1D\r\n
(这里是29字节的数据)\r\n
09\r\n
(这里是9字节的数据)\r\n
0\r\n
\r\n
```

解释如下：

- `1D` 是29的十六进制表示，表示第一个块有29字节的数据。
- `\r\n` 是回车换行符，用来分隔块大小和实际数据。
- `(这里是29字节的数据)` 表示实际要发送的数据部分。
- `09` 是9的十六进制表示，表示第二个块有9字节的数据。
- `(这里是9字节的数据)` 表示实际要发送的第二部分数据。
- `0` 表示这是最后一个块，其大小为0，意味着数据传输完成。
- 最后一个`\r\n`确保消息正确结束。

通过这种方式，即使服务器不知道最终需要发送多少数据，它也能开始向客户端发送数据，而不需要等待所有数据都准备好。这对于动态生成内容或者长时间运行的过程特别有用，因为它允许更高效的资源利用和更快的响应时间。此外，这也使得持久连接更加实用，因为不必为每个请求/响应对关闭和重新打开连接。



###  100 -continue

![[../../../壁纸/附件/Pasted image 20250208152737.png]]

**`IMMEDIATELY` (立即):**

- **行为：** Tomcat 在接收到包含 `Expect: 100-continue` 请求头后，**立即**发送 100 Continue 响应，而**不会进行任何预先的检查或授权**。
- **优点：** 响应速度最快，客户端能尽早收到 100 响应并开始发送请求体。
- **缺点：** 可能会在未进行充分验证的情况下就发送 100 响应，如果后续请求被 Servlet 或应用程序逻辑拒绝，可能略有资源浪费（虽然只是接收了请求头，但仍发送了 100 响应）。在安全性要求较高的场景下，可能不是最佳选择。


### Coyote

**简单来说，你可以把 Coyote 看作是 Tomcat 服务器与外部客户端进行 HTTP 通信的 “桥梁”。 它负责接收客户端的请求，并将请求传递给 Tomcat 内部处理；同时，它也负责将 Tomcat 内部生成的响应，格式化并发送给客户端。**


Coyote 组件负责创建这个响应对象，并负责将这个对象按照 HTTP 协议规范， 序列化成字节流，并通过网络连接发送回客户端。
