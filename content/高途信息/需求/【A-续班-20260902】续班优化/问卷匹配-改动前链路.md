# 问卷匹配：改动前链路（master）

> 来源：2026-10-08 读 `origin/master` 代码整理，未跑验证。student-data / teacher-tool 两段本分支未改，仍是现状；本分支只改 product-server 认人部分（见文末「本分支语义变化」）。

## 0. 整体链路

```
CDS 表单提交 MQ  test_future_landingpage_form_submit
  └─ product-task  QuestionnaireRecordConsumer → QuestionnaireRecordService#dealCDSMsg
       ① 认人：computed_user_id
       ② 认班：clazz_number（大班号）+ share_course_numbers
       ③ 写 gaotu.questionnaire_record → 发问卷记录 MQ
  └─ student-data-dws  DwsRenewalQuestionnaireConsumer
       ④ 按「人 × 共享课」扇出到多个班：意向表 / 学员动态 / 触达 / ES 花名册状态
       ⑤ 每班发一条明细 MQ
  └─ teacher-tool  QuestionnaireConsumer
       ⑥ 写 user_questionnaire_record（问卷明细）
```

全程「班级」= 大班 clazzNumber，不是辅导班。辅导班只在跨班兜底里用来比对辅导老师。

## 1. product-server 认人认班（`dealCDSMsg`）

- 只处理 `businessType == 8`；异常返回 `Suspend`（顺序消息重试）。
- 匹配参数：表单姓名（fieldContentType=1）、手机号（=2）、CDS 带的 userId（登录态才有）。
- 从 `clickUrl` 解析 `bindNumber` → 查 `questionnaire_bind_data` 拿链接班 / 问卷 / 老师 accountId。

### 路径 A：链接带有效 bindNumber（主路径）

1. 在**链接班内**跑 4 条规则，命中即停（`compute.rule.name.list`，线上未配，走代码默认）：

| 档 | 规则 | 怎么认 |
|---|---|---|
| 1 | `originUserRuleService` | 提交带的 userId 在链接班有记录 → 认该 userId |
| 2 | `mobileRuleService` | 填写手机号查注册用户，该用户在链接班 → 认他 |
| 3 | `nameRuleService` | 遍历链接班花名册，姓名完全相等（不 trim），同名取 ID 最小 |
| 4 | `relationIdService` | 填写手机号当亲属号查挂靠学员，在链接班的取 ID 最小 |

   「在班」= status 1/2/3，**已退出也算**。

2. 命中：`computed_user_id`=命中人，`clazz_number`=链接班，`questionnaire_number`=链接问卷。
3. 未命中且 `across.clazz.questionnaire.submit.switch=true`（默认）→ 跨班兜底 `dealNotExistedComputeUserId`：
   1. 候选人（全局查，不分先后）：userId + 手机号注册用户（只取第一个）+ 亲属号挂靠学员（全部）+ 同名学员（姓名长度>1，前 20 个，不排序）。
   2. 计划范围：链接问卷 → 流程 → 续班计划 → 计划下绑同一问卷的前置课。
   3. 查所有候选人在这些前置课下的辅导班（不过滤状态）。
   4. 选班：所有候选的辅导班混在一起，取第一个辅导老师 = 链接 accountId 的；**找不到就 `subclazzDTOS.get(0)`**。
   5. 用选中班的**大班**重跑上面 4 条规则认人；记录的 `clazz_number` / `questionnaire_number` / `share_course_numbers` 都换成选中班的，tag `no_existed_compute_user_submit`。
4. 兜底也失败：照常按链接班写一条 `computed_user_id=0`（未归属）。

**兜底的问题**：
- `get(0)` 是随机归属，顺序取决于候选收集和下游返回顺序。
- 选中的班不一定是 userId 本人的班；重跑规则可能认成别人（如姓名候选 S2 所在班老师恰好是链接老师），也可能认不出（computed=0 但返回 true）。
- computed=0 的兜底记录挂在随机班上，且重试 Job 不会捞它（见第 4 节）。

### 路径 B：没有 bindNumber / 绑定数据不存在

1. userId：优先 CDS 带的，否则手机号查注册用户取第一个。
2. 前置课：所有**已发布**计划里绑了该问卷的前置课。
3. 取该人在这些课下的第一条班级记录 `get(0)`，在该班重跑 4 条规则后落库（`accountId=0`、绑定号 `0`，tag `no_bind_data_user_commit`）。
4. 认不出人 / 找不到班：写 `renewal_questionnaire_record`（tag `cds_no_user_submit`），这张表没人读。

### 共享课 `share_course_numbers`

`all.share.questionnaire.renewal=true`（默认，线上未配）或计划在 `share.questionnaire.renewal.numbers` 名单里 → 取计划下绑同一问卷的全部前置课；否则为空。下游靠它扇出到同计划其他班。

## 2. student-data 扇出（`DwsRenewalQuestionnaireConsumer`）

- **已认出人（computed > 0）**：`listStudentByUidByCourseNos(人, 共享课, 全部状态)` 取该人在共享课下所有班（含已退出）→ 逐班写意向表、学员动态、触达、ES 花名册 `renewalQuestionnaireStatus=3` + 提交时间 → 每班一条明细 MQ（非链接班重新生成 uniqueBizId，`questionnaireGroupId` 指向原记录）。「先调后填 AB 都展示」「多班在读都展示」靠这里，与认人规则无关。
- **未认出人（computed = 0）= 广播**：`noBindClazzNumbers` = 绑了该问卷的所有前置课下的所有大班（按问卷查、**不按计划过滤**；现网禁止一问卷绑多计划，实际遇不到）。不写意向表和花名册，只发一条带班号列表的明细 MQ。
- **手动绑定（manual_user_id > 0）**：computed 取 manual 值，查该人在上述班里实际所在班（`bindUserClazzNumbers`）更新花名册；不发明细，明细由 teacher-tool rpc `handleExistRecord` 处理（未细读）。

## 3. teacher-tool 明细落库与查询

- **已认出人**：按「user + 班 + 填写手机号」查旧记录，新提交更晚则覆盖，否则不动；无旧记录则新增。→ 同手机号只留最新，不同手机号各一条。先查后插非原子，偶发重复行。
- **未认出人**：主记录 + `noBindClazzNumbers` 每班一行 `user_id=0`，同 `questionnaireGroupId`（广播）。
- **查询**：`project_number = 问卷 AND clazz_number = 该班 AND (user_id IN 该班花名册 OR user_id = 0)`。老师看到的 = 挂在本班且人在本班花名册的明细 + 广播行。

## 4. 未归属重试 Job（`QuestionnaireRecordComputeHandler` → `dealNotExistedComputeUser`）

本意回溯 N 天内 `computed=0` 的记录重新匹配；但 master 条件是 `manual_user_id != 0`，只捞已手动绑定的，**普通未归属从不重试**。

## 5. 要点

1. 认人只在链接班内做；学员在同计划别的班只能靠兜底猜，核心是 `get(0)`。
2. 认班是大班维度；辅导老师只在兜底里比对，老师可见性靠「明细挂的班 + 自己的花名册」。
3. 一份提交多班展示 = student-data 按共享课扇出，依赖 `all.share=true`。
4. 认不出人 → 按问卷广播到所有绑该问卷的班，等人工绑定收口。
5. 同手机号只保留最新的去重在 teacher-tool，维度「人 + 班 + 手机号」。
