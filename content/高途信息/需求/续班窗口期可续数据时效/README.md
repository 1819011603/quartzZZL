# 续班窗口期「可续数据」时效问题 — 现状与优化方案

> 一句话：**去年用"不计算"换"稳定"（漏数据）；彻底方案是"照算 + 业务看定稿值"（不漏、不慢、不慌）。**

## 一、业务要什么

- 「可续人数」不是普通展示字段，是**续班率 / 续班进度的分母**（老师排名、投屏看板的基数）。所以业务要它：
  - **稳**：锁分母后固定基数，所有老师同一口径比，考核/激励不算错；
  - **准**：T+1 早上 9:00 前能看（大续尤其）。
- 场景量级：大续，精品班一轮约 **23W 可续**；全国多地投屏实时关注，影响面大。
- 2026 节点：一轮续班窗口 **11.6–11.15**、二轮可续锁定 **11.6–11.8**。
- 本质是**考核口径**诉求，不是技术洁癖。

## 二、现在是什么情况

链路：判单/可续任务（performance-attribution）每天批量重算 → 写 `performance_regular_can_renewal_sign_x` → MQ → ES `ads_large_subclazz_user_index` → EES 续班看板；数分（大航海）另走 T+1。

四个毛病：

1. **跑得慢 + 中间态可见**：任务凌晨 4:00 起跑、约 7 小时；上午业务看到的是**半成品**——只跑完「标记」环节，后面的「调课修正 / 退费修正 / 灰名单」还没跑（四个环节都往同一张表写）。→ 数据"不准"。
2. **可续本身会变**：判单、订单（退款/调课/重报）、可续时间到期、续班关系配置都在动 → 分母变 → 排名不可比。
3. **意外脆弱**：pod 被重启（2025-10-31 04:15 qingzhousystem 重启）、任务超时 → 任务没跑/晚跑（曾晚到 21:00+），甚至影响次日调度。
4. **口径不齐**：EES 实时 / 数分 T+1，两边天然不等。

## 三、去年（2025 一轮）的做法与坑

做的事情（三个都是"绕"）：

| # | 做法 | 实质 |
|---|---|---|
| 1 | 提速（优化后上午能跑完） | 治标，意外/超时仍会晚 |
| 2 | T+1 可续数据降级兜底 | 少一天数据 |
| 3 | **给"不计算可续的班级列表"，窗口期这些班不计算可续** | **冻结 = 漏算**（纪要说：不执行任务，除灰名单外可续结果不再变） |
| 4 | 全局暂停任务 | 不行，其他学部还要算 |

坑：

- **白名单人工维护易漏**——漏一个班就一直变（"还是会变"）；
- **一轮二轮交织**——一轮过可续截止、二轮还没过时，**一轮标记也会变**（已确认），白名单边界难划；
- **意外挡不住**——重启/超时照样打乱；
- **代价是漏真实变化**——窗口期内退款/调单/新报名都不反映。

## 四、后续怎么优化（彻底方案 = 工程提速 + 口径定稿）

**A. 工程层——治"不准 / 慢 / 意外"**

- **增量重算（核心）**：现成的 `CanRenewalService.renewalOrderCanRenewalBack(List<orderNumbers>)` 已经是一条龙「标记 + 调课修正 + 退费修正 + 灰名单修正」，现在只用在回溯和灰名单置白。把它接到**事件**上即可：订单事件 `gaotu_order_event`（OrderCreated/PaySuccess/ApplyRefund/RefundSuccess…）已被 `AttributionOrderEventConsumer` 消费做判单，**在判单之后**触发可续重算（天然满足"可续依赖判单、必须后跑"）。
  - 只算变化的单 → 任务从 7h 降到分钟级，任一时点都准；
  - 过滤「是否落在活跃可续范围」+ **攒批去重/延迟窗合并** + **同单串行/幂等**（照抄 fairy `comment.todo.merge` 的窗口合并思路）。
- **全量重算降级**：保留但变为**低频对账兜底**（凌晨一次，覆盖时间到期、配置变更、灰名单批量等无事件变化）。
- **告警**：链路任务失败/未完成要报警（别让"没跑完"被当成"逻辑问题"来找）。

**B. 口径层——治"要稳"，且不漏**

- 锁分母后，业务看板读**定稿值 / 锁定值**（把"冻结"做成**读侧定稿**，而不是"不计算"）。
  - 业务看到稳定、权威的分母；真实变化照算不丢；其他学部不用停；白名单退休。

**C. 边界（说清楚，别承诺做不到的）**

- 「实时」和「不变」只能二选一，**"实时且不变"是伪命题**，不要承诺；
- 无事件的变化（可续时间到期、配置变更、灰名单批量）必须靠**定时对账**兜底，不能只靠事件。

## 五、后续动作

1. **增量落地方案**（变更集采集 / 触发点 / 幂等编排 / 对账 / 告警）——性能归因侧。
2. **定稿值口径**（锁定后业务看哪个值、怎么展示）——产品 / 数分。
3. **监控告警 + 意外重启自愈**（任务失败可感知、可快速重跑）。
