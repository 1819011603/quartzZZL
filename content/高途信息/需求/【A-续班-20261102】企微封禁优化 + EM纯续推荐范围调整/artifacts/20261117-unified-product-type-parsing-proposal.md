# 大小班商品类型解析统一方案（共用层 + 差异层）

> 2026-11-17 · 响应 owner 指示：『共用的放共用 差异化的放自己的处理的地方』『用一个合适的最佳实践设计模式』
> 状态：**方案，未实施**——老代码大班链在获 owner 认可前零改动。

---

## 一、现状（任务 1 答案，代码事实）

**是两条独立分支**。同一个商品类型（联报 23 / 组合 51 / 班级 2·6004）的解析逻辑，大小班各写一套：

| 解析职责 | 大班老链（RenewalService） | 小班新链（SmallRenewalCoreService + handler 包） |
|---|---|---|
| 候选构建 | coreHandle 逐前置班循环内联 if-else（CLAZZ 1540 / 23 1552 / 51 续后） | **方案一已收编**：`buildCandidates` → ProductTypeHandlerRegistry 策略路由，一处接入 |
| 白名单校验 | 23 新模板正查（3380-3481）+ recommendMapType 分支内联（1552-1648） | **方案一已收编**：WhiteListMatchPlugin → handler 路由 |
| 展示组装 | RenewalService:1721（23 填充）+ convertResultToClazzDetailDTO:741（扩科加购 23/51/else 三分支） | buildRecommendResult:842-852（CLAZZ/51 两支）+ RenewalSinglePlanDetailService:1531（23 降级组装） |

**加膨胀券（现状）要改约 5 处、两套代码**：小班 2 处（新增 Handler + 展示组装加分支）、大班 3 处（候选构建加分支 + 白名单语义 + 展示组装加分支）。方案一的收编范围**只在小班链内部**，大班链未动——所以"是不是还得改两处"的答案是：**是**，类型通用逻辑大小班各一套，这是现状（不动老代码口径的既定代价）。

## 二、目标结构（owner 定）

- **共用层**：类型通用解析（"这个类型是什么、候选怎么建、白名单怎么校验、通用条目字段怎么填"）——一处维护；
- **差异层**：班型特有处理（大班的新模板正查/已勾选优先/扩科加购、小班的插件链上下文/回退态展示取舍）——留在各自链路。

## 三、模式选型：策略族 + 共用组件（推荐），否掉纯模板方法

**为什么不是模板方法（Template Method）**：
- 模板方法靠继承定骨架：需给大小班两条链抽共同父类——动两条链的类结构，直接违反"不动老代码"；
- 大小班流程本来就不同（大班 coreHandle 逐前置班、小班 12 步 SubBuilder+插件链），强行统一流程骨架=过度设计；
- Java 单继承，后续没有腾挪空间。

**为什么策略族+共用组件合适（组合优于继承）**：
- 方案一已在小班落地并验证（ProductTypeHandler 接口 + Registry + 三实现，逐字等价、三方端到端一致）——方案是它的自然升格，不是推倒重来；
- 每个**类型**一个策略实现 = 新类型通用解析只写一处（开闭原则：加类型不改既有代码）；
- 共用/差异的边界天然清晰：**接口里只放跨班一致的通用段**，班型差异不进接口、留在各自链路（这正是"共用的放共用、差异化的放自己"）。

**角色映射**：

| 结构层 | 模式角色 | 承载 |
|---|---|---|
| 共用层 | Strategy 接口 + 实现族 | `ProductTypeHandler`（6004/51/23 实现，未来膨胀券实现）——类型通用解析 |
| 共用层 | Registry（上下文/查找） | `ProductTypeHandlerRegistry`（已存在，List 注入建 Map） |
| 差异层 | 链路私有逻辑（不进接口） | 大班：新模板正查、已勾选优先、扩科加购转换；小班：插件链、回退态展示取舍 |

## 四、以膨胀券为例（假设 productType=6005）

| 场景 | 现状（两条分支） | 方案后（共用+差异） |
|---|---|---|
| 纯通用（两班型行为一致） | ≈5 处、两套 | **1 处**：新增 `ExpandVoucherHandler`（候选+白名单+通用条目一起进共用层） |
| 有班型差异（如大班券需绑定班级展示） | ≈5 处 | **1 + N 处**（N=真实存在差异的班型数，≤2）：通用进 Handler，大班展示组装点补一个差异分支，小班零改动 |

接入步骤（方案后）：写一个 Handler 实现类 + Apollo 配类型开关（如有）→ 两班型自动获得该类型候选/白名单能力 → 仅有真实差异的链路各补差异点。

## 五、与大班老代码的关系（三种取舍）

| 选项 | 内容 | 代价/风险 | 与"不动老代码"口径 |
|---|---|---|---|
| A 不动 | 大班保持内联 if-else | 新类型仍两套写、长期语义漂移（23 已出现：大班正查 vs 小班白名单直配） | 完全符合，零风险 |
| B 全动 | 大班类型分支一次性全委托共用层 | 一步到位但动生产主链路，回归面大 | 违反口径 |
| **C 桥接（推荐）** | 分两步：①共用层落位（handler 移包 `renewal/product/handler`+接口分段命名，**只动小班新代码，老链零改动**）；②大班逐类型桥接（每类型把分支体换成 `registry.get(type)` 委托，其余大班流程一字不动），每步一轮 compare+31 样本+大班端到端抽样 | ②才真正动老链，但 diff 可枚举（每类型一处分支体替换），可停在任意中间态，风险按类型分片 | ①不违反；②启动前需 owner/领导点头 |

**边界把握**：桥接只改"类型分支的实现来源"，不改大班流程结构（逐前置班循环、已勾选优先、扩科加购合并、展示顺序全部不动）。

## 六、迁移路径（若认可 C）

1. `small/handler` → `renewal/product/handler` 移包 + 接口通用段/钩子段命名明确化（小班引用改 import，行为零变化，全量 563 回归）；
2. 大班按类型逐个桥接：23 先行（共性价值最大，大班 3380-3481 正查可下沉为 Handler 可选钩子或留在大班差异层，二选一在桥接时定）、51/2 跟进；
3. 每步验证口径同方案一：全量单测 563 基线 + compare 31 样本 + 大/小班端到端抽样对照；
4. 膨胀券等新类型出现时即理想接入点：只写 Handler 一处。
