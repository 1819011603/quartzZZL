## 2. 总体架构与职责边界

```
Controller / Feign / Job                 ← 唯一开关层（Apollo）
        │ enabled=true
        ▼
RenewalV2Service（新增 · 编排核心类）     ← 关联解析、逐计划推荐、纯续合并、预热写入、开关
        │ 调用
        ▼
RenewalCommonService（新增 · 公共复用层） ← 纯续提取、合并/去重、VO 装配代理、缓存 key、状态核验
        │ 复用（只读/无副作用）
        ▼
RenewalService（老链路）                  ← 只新增 2 个包内方法；原方法体不动
        │
        ├── RenewalDataService / SmallRenewalCoreService / SmallRenewalPreheatService
        └── Redis
```

### 2.1 为什么拆 `RenewalCommonService`

- 决策 1 要求「复用老代码，拆出公共类」；决策 6 要求「尽量不动老代码」。
- 做法：**不搬迁** `RenewalService` 的 `coreHandle`/`processClazz` 等老逻辑，只在 `RenewalService` 新增 2 个包内方法作为稳定出口；把 V2 需要的「纯续提取、合并、去重、VO 装配、缓存 key、从计划状态核验」集中到 `RenewalCommonService`。
- 结果：老链路方法体零改动；V2 不复制老逻辑；公共逻辑只有一个归属。
- 不做全量抽取（把 500+ 行老逻辑搬进公共类）：那是参考分支的大改法，违背决策 6，且回归面大。

### 2.2 开关（Apollo）与默认值

| key | 默认 | 作用 |
|---|---|---|
| `renewal.recommend.v2.enabled` | `false` | 读路径：C/B 详情走 V2 |
| `renewal.preheat.v2.enabled` | `false` | 写路径：预热走 V2 |
| `renewal.preheat.v2.prefix.enabled` | `false` | V2 写 v2 key（`renewal:preheat:v2:`），**只写不读** |

- 默认全 false：代码先上线，行为不变。
- 业务总闸沿用 `renewal.pure.relation.enabled`（默认 true；关闭时 V2 直接回老逻辑）。
- 沿用 `preheat.cache.enabled` 作为读缓存总闸；`false` 时全走现算。

### 2.3 入口与开关矩阵

| 入口 | 老方法 | V2 方法 |
|---|---|---|
| `GET /web/renewal/cart`（C） | `getRenewalDetail(7参)` | `RenewalV2Service#getRenewalDetailForC` |
| `GET /web/renewal/operation/cart`（B） | `getRenewalDetail(5参)` | `RenewalV2Service#getRenewalDetailForB` |
| Feign `/renewalCart` | 7 参 | `getRenewalDetailForC(fromBCart=true)` |
| `GET /web/renewal/preheat` | `preheat(userId,plan)` | `RenewalV2Service#preheat` |
| Feign `/preheat` | `preheat(plan,userId)`（现有参数顺序反） | `RenewalV2Service#preheat`（**不修老方法**，见 §8） |
| XJob `RenewalJobHandler` | `preheatByRenewalNumber` | `RenewalV2Service#preheatByRenewalNumber` |

> 开关放调用方；V2 调 `RenewalService` 包内方法时不会再次触发开关，无递归。
> 选品/换课/换年级入口**不接 V2**（决策 4）。

## 3. 处理流程

### 3.1 C 端详情

1. 加载主计划；`relatedRenewMasterNumbers` 为空或总闸关 → **直接走老方法**（逐字段不变）。
2. 批量核验从计划状态（一次 RPC），只保留状态 1/2、未删、非自身 → `activeSubs`。
3. 无 `activeSubs` → 走老方法。
4. 有 `activeSubs`：
   - **命中老 key 预热**（`preheat.cache.enabled=true` 且 `!fromBCart`）→ 按「已是主+从合并 map」直接装配纯续 VO；主计划扩科/加购/年级/价格在线补。
   - **未命中** → 主计划 + 各从计划分别按自身逻辑算纯续，合并、去重，主计划扩科/加购照旧。
5. 单个从计划异常只丢该从计划，不拖垮主计划。

> 无版本键/无标记：V2 无法区分缓存是「老单计划值」还是「V2 合并值」。上线切换窗口内读到老值时按合并值消费，结果只含主计划（不劣于基线）；下一次预热写入后自然变为合并值。见 §7.3。

### 3.2 B 端详情

- 不读预热（`fromBCart=true`），按「主 + 从」分别现算后合并纯续；不补扩科/加购（与老 B 链路一致）。
- 纯续商品集合需与 C 端「命中 vs 未命中」口径一致。

### 3.3 单用户预热

1. 加载主计划 + `activeSubs`。
2. 逐计划算纯续 map：
   - 大班：`RenewalService.v2ComputeSinglePlanPureMap(config,userId)` → `coreHandle(config,userId,false,false,false).getItem1()`（不读写缓存）。
   - 小班：`smallRenewalCoreService.recommendAll(userId,plan,config)` → 纯续结果转 `ClazzDetailDTO`（key=`beforeCourseNumber`；`productType` 空补 6004）。
3. 合并：主计划优先，从计划 `putIfAbsent`；同年级同商品去重。
4. 写入：
   - `prefix.enabled=true` → 只写 `renewal:preheat:v2:{plan}:{user}`（供人工 diff，不读）。
   - `prefix.enabled=false` → 写 `renewal:preheat:{plan}:{user}`（生产）。
   - value 仍是 `JSON.toJSONString(Map<Long, ClazzDetailDTO>)`；TTL 26h；扩科/加购不写入。

### 3.4 计划级批量预热

1. 只从 **A 自己的 `courseNumbers`** 取已付用户：
   - 大班：`orderInfoAdapterFeignService.listByCourseNumberPage`，`orderStatus ∈ {2,7}`。
   - 小班：`orderInfoFacade.listByCourseNumber`。
   - 多前置课去重，一批 1000，使用现有预热线程池或 V2 有界线程池。
2. 小班先保留 `smallRenewalPreheatService.preheatInternal(user, plan)`（下游/扩科内存预热），再写合并 map。
3. **不遍历从计划的学员集合**；从计划作为入口时由 XJob 自己的计划号处理。
4. 单用户失败只计数，不中断整批。

### 3.5 选品/换课/换年级

**不做**（决策 4）。保持老行为：不接 V2、不新增所属计划路由、不新增预热带失效。
影响：主链接里更换从计划课程后，旧预热在 TTL 内仍可能返回旧商品（老代码本来也没有该失效逻辑）。见 §8。

## 5. 缓存契约

| 项 | 约定 |
|---|---|
| 生产 key | `renewal:preheat:{plan}:{user}`（不变） |
| diff key | `renewal:preheat:v2:{plan}:{user}`（`prefix.enabled=true` 时**只写不读**） |
| value | `JSON.toJSONString(Map<Long, ClazzDetailDTO>)`（**完全不变**，无前缀、无包装、无新增字段） |
| TTL | `preheat.cache.time`，默认 26h（不变） |
| 版本键 | **不引入** |
| 清缓存 | **不做** |
| 读 | 只读生产 key；v2 key 永不读 |
| 写 | prefix=true 只写 v2 key；prefix=false 写生产 key |

### 5.1 读取与切换窗口

- 无版本键，V2 读到生产 key 即按「合并 map」消费。
- 切换前已存在的单计划老值：V2 会当合并值消费，结果只含主计划（不劣于基线）；V2 预热跑过一次后变为合并值。
- 关联关系/状态变化：TTL 内仍可能返回旧从计划商品；按决策 3/4 **不兜底**。

### 5.2 回滚

- 关闭 `renewal.recommend.v2.enabled` 和 `renewal.preheat.v2.enabled`。
- 老代码会读到生产 key 里的合并值；按决策 3 **不加守卫、不清缓存**，这是已知残留风险（见 §8/§9）。
- 可选运营动作：跑一次老预热 job 用单计划值逐步覆盖（不是清缓存）。

## 7. 验证方案

### 7.1 三类场景用例

| 编号 | 场景 | 入口 | 前置 | 期望 |
|---|---|---|---|---|
| V1 | 大→小 | C | 未预热 | 主大班 + 从小班纯续都在；无 6004 丢失 |
| V2 | 大→小 | C | V2 预热后 | 商品集合/年级/signUp/allSignUp/默认年级/排序与 V1 一致 |
| V3 | 大→小 | B `fromC=0/1` | — | 不读缓存；与 C 现算口径一致 |
| V4 | 小→大 | C/B | 造数新建关系 | 主小班 6004 + 从大班 2；扩科/加购只来自主 |
| V5 | 无关联 | C/B | — | 与改前逐字段一致；不写 v2 key（无关联不走 V2 预热） |
| V6 | 开关关 | C/B | 关系存在 | 只返回主计划，与基线一致 |
| V7 | 双开关同开 | C | 关系存在 | 无 5xx；从计划失败不影响主计划 |

### 7.2 新老预热 diff（人工 Redis）

1. 老预热：分别对主计划和每个从计划调用老 `preheat`，得到 `old(main)`、`old(sub1)`…。
2. 期望集合 = `old(main) ∪ old(sub1) ∪ …`，按「同年级同商品去重、主计划优先」得到 `expected`。
3. V2 预热（`preheat.v2=true` + `prefix=true`）→ 只写 `renewal:preheat:v2:{plan}:{user}`。
4. 人工 Redis 对比 v2 key 与 `expected`：
   - key 集合完全相等（无多、无少）。
   - 公共 key 字段相等：`productSkuNumber/productType/beforeCourseNumber/afterCourseNumber/price/signUp/forceBuy/recommendType/teacherList/...`。
   - 从计划条目的 `forceBuy/signUp/allSignUp` 等于该从计划自身老结果（不被主计划覆盖）。
   - 无关联：v2 key 不应出现（无关联走老预热）。
5. 判定：全部通过才切生产。

### 7.3 上线与回滚

**上线顺序**

1. 代码上线，三开关 false → 行为不变。
2. test：`preheat.v2=true` + `prefix=true` → 跑 §7.2 人工 diff。
3. test：`prefix=false` + `preheat.v2=true` + `recommend.v2=true` → 一次切读写老 key；跑 V1~V7。
4. 生产：`prefix=false` + 两个 V2 开关同开；随后对受影响计划跑一次 V2 预热 job（把老单计划值替换为合并值；不是清缓存）。
5. 观察：V2 命中率、P99、5xx、Redis key 大小/TTL、XJob 时长、从计划失败数。

**回滚**

1. 两个 V2 开关同时关；老代码回到老路径。
2. 生产 key 里可能仍有合并值，老代码会读到（决策 3 不兜底）。
3. 必要时跑老预热 job 用单计划值覆盖；不做批量清 key。

## 8. 风险与取舍（按 owner 决策）

| 风险 | 说明 | 处理 |
|---|---|---|
| **关联变化后 TTL 内旧从计划** | 决策 3/4：无版本、不清缓存、不做换课失效；关系/状态变化后最长 26h 仍可能返回旧从计划商品 | **不兜底，需 owner 确认接受** |

| 选品/换课不做 | 从计划课程在主链接里更换仍是老行为 | 决策 4 接受 |
| Feign `/preheat` 参数反 | 老 bug | 决策 6 不修，仅记录 |
| `@mergedRenewal@` 历史脏值 | 上一版可能写过 | 上线前人工确认/覆盖，不写清理代码 |

## 9. 仍需 owner 确认的事项

已定事项不再追问。**仅剩 1 个需要确认**：

1. **接受「关联变化后 TTL 内可能返回旧从计划商品」的风险**：
   - 决策 3（无版本键、不清缓存）+ 决策 4（不做换课/选品失效）后，删除/新增从计划、从计划状态变化、换课/换年级，最长 26h 内预热仍可能是旧结果。
   - 不引入版本键、不加老代码守卫、不做批量清缓存；可选运营动作是跑一次预热 job 覆盖（非清缓存）。
   - 请确认接受；确认后即按本方案进入开发。

> 其余（开关名/默认值、公共类拆分、编译提交、小→大造数）按现有授权和技术规范自行推进，不再询问。

## 10. 为什么这样改

- **满足决策**：公共类复用、v2 只写不读、回老 key、无版本/不清缓存、不动选品换课、尽量不动老代码、依赖升级。
- **兼容**：value 完全不变、老 key/TTL 不变、无关联走老逻辑、开关关闭可回退。
- **可验证**：v2 key 只写，owner 直接 Redis 人工 diff；通过后再切生产。
- **改动集中**：编排在 `RenewalV2Service`，复用细节在 `RenewalCommonService`；`RenewalService` 只加 2 个方法。
- **明确取舍**：不兜底 TTL 旧数据，换取「不加版本键、不清缓存、不动老代码」的简单性。

## 11. 开发前置确认结论（2026-11-12 落实）

### 11.1 Redis value 结构不改、只新增字段，是否足够？——**足够，且无需新增字段**

- value 仍是 `JSON(Map<前置课号, ClazzDetailDTO>)`，key 为 `renewal:preheat:{plan}:{user}` 或测试用 `renewal:preheat:v2:{plan}:{user}`。
- 主从合并、纯续合并、去重所需的字段均已在基线 `ClazzDetailDTO` 中：
  - 前置课：map key + `beforeCourseNumber`
  - 后置课/班级：`afterCourseNumber`、`productSkuNumber`、`clazzNumber`
  - 联报：`activityNumber`、`productType=23`
  - 同年级同商品去重：用 `afterCourseNumber`（缺省 `beforeCourseNumber`）反查课程年级，再按 `grade + productSkuNumber` 去重，**不需要把 grade 写进 value**。
- 结论：**不改 value 结构、也不需要新增字段**；如后续仅为排查方便，可选加 `sourceRenewalNumber` 之类的只读辅助字段，老代码反序列化会忽略，但本期不加。

### 11.2 商品 type 专项——**需要，但现有 value 已包含，且必须保留**

- 商品类型由基线 `ClazzDetailDTO.productType` 承载（普通班级 2/6004、联报 23、组合商品 51），老代码在读取/组装时依赖它区分商品种类。
- 主从合并时**不能丢 `productType`**：每条纯续条目必须保留其自身商品类型，不能统一改写成主计划的类型；小班纯续条目为空时补 `6004`。
- 现有限制（既有，不是本次引入）：老读取链路按**计划级** `RenewalPreCourseDTO.productType` 决定订单/联报处理分支。若主计划与从计划商品类型不同，默认写回原 key 后被老代码读取时可能按主计划类型错误处理。本期由于 v2 只写不读、且默认回原 key 是对既定风险的接受，暂不改；**最终切换读取前必须改为按条目 `productType` 分派**。
- 老代码忽略新增字段是否安全：安全（FastJSON 反序列化忽略未知字段）；本期未新增字段。

### 11.3 多计划共用同一前置课——**直接报错**

- 校验位置：`RenewalV2Service#validateNoSharedPreCourse`，在关联解析完成后、推荐/预热合并前执行。C 端详情、B 端详情、单用户预热、计划级预热都会经过。
- 规则：主计划 + 所有有效从计划的前置课集合，若同一前置课出现在**两个不同计划**中，抛 `CommonsException(..., ErrorType.BUSINESS_ERROR)`，消息包含冲突前置课号与两个计划号；同一计划内部重复前置课不算冲突。
- 影响范围：单次详情请求/单用户预热直接失败；新 job 按计划粒度 `try/catch`，单个计划失败只影响该计划，同批次其他计划继续。
- 已补单测：主+从共用、两个从计划共用两种用例均覆盖。
