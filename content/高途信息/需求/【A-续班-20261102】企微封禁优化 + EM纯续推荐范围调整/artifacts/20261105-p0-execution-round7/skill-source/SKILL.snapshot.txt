# Banshan 用例

## 先探索、守范围、自主推进

- 先明确本次要做的是生成用例、执行验证还是回写状态，按用户指定功能和优先级推进。写 case 时可以按需准备必要测试数据，不自动扩成整套回归、部署或平台回写任务。
- **先看懂已有功能，再选 case**：自主查需求/已确认规则、现有入口与实现、已有用例和必要数据；说明实际覆盖与预期依据。代码用于确认现状和观察点，不能把现状直接当正确预期。没有本次 PRD 或代码 diff，也可以针对已确认的存量功能编写用例。
- 用户要已有功能的 **P0 case**，就聚焦该范围内已有的核心业务路径与关键结果，优先复用有效用例、样本和入口；不臆造新功能、新规则，不把相邻模块、全部边界组合、P1/P2 或历史全链路塞进 P0。只有前置依赖或影响证据确有必要时才覆盖相关行为，说明依据，保持最小范围。
- **范围核对不是审批**：简要说明覆盖哪些、不覆盖哪些及原因，然后自主继续。普通用例选择、查证、步骤整理和已有授权内的操作由 Agent 决定，不问“这条要不要写 / 要不要继续”。先自行解决；仅关键业务预期经查仍不明确、确实无法推进，或必要的高风险/范围外操作未获授权时，携证据和建议问具体问题，同时完成不受阻的部分。
- **必要测试数据自主准备，不重复询问**：用户允许在合理范围内直接造数、增删改测试环境表内数据，生成用例和执行用例时都适用；但本次用户或所有者明确的只读、不造数、不写平台等边界优先，不能用本条通用授权扩大动作范围。优先复用有效样本，缺少前置时自行选择造数入口或测试库 DML，限定本次账号、班级、订单等测试对象，核对环境与写入条件，保留必要原值/恢复方式并独立回读。数据准备后的自验不等于整条 case 已通过；不能直接把待验证结果改成期望值来伪造通过。这项授权不包含生产数据写入、修改表结构、扩大功能范围或修业务代码。
- **发现问题只报告**：给出预期依据、实际现象、复现与已有证据；尚未确认的标为疑点，不夸大为缺陷。不能为了通过 case 修改业务代码、改变业务规则、绕过被测逻辑或降低预期。构造测试前置所需的数据修改按上条直接执行，与修功能分开；修复须有相应授权，生成/执行 case 本身不包含修复授权。

面向拿文档过 case 的人，采用测试侧的简洁用例风格。**正文只写必要前置、简短操作、关键预期和已有实际结果；完整证据集中附录或链接，不逐条粘贴排查过程、重复背景、原始响应和日志。** 生成、修改用例或执行记录使用 [doc-templates](references/doc-templates.md) 的简洁执行卡；涉及班级/学员/消息目标时保留已核实的班级 bizId、班名、学员 ID，不能用数据库主键替代业务编号。

### P0 用例信息最低门槛

写或改 P0 前读取并逐条回读 [doc-templates](references/doc-templates.md) 的 **P0 信息完整性清单**；它是对象、计算、证据引用、覆盖映射和版本复用的唯一完整规则来源。业务语言优先；计算保留真实输入、规则/公式、简短代入和结果，单位/时间边界/去重/取整按影响说明；规则筛选范围用一句纳入/排除依据，不硬凑公式。未知值和未执行如实标缺，精简不降低证据门槛。

页面 `https://qa.baijia.com/banshan/#/caseManager/{productLineId}/{caseId}/{recordId}/{iscore}`
是 SPA，正文不在 HTML 里，**socket.io 推**。走 `banshan-case` MCP，别手拼 curl。

## 工具

| 工具 | 用途 |
|------|------|
| `banshan_get_case` | 粘页面 URL → 脑图落成 md/outline/json，返回模块+用例索引(带节点 id、执行状态) |
| `banshan_list_records` | 列某 case 下的执行任务，挑 recordId |
| `banshan_set_status` | 改用例执行状态并保存，**默认 dry_run=true** |
| `banshan_save_json` | 本地脑图 JSON 全量覆盖保存，**默认 dry_run=true** |

典型流：`banshan_get_case(url=...)` 看索引 → 拿节点 id → `banshan_set_status(node_ids=[...], status='通过')`
先 dry_run 回显并自行核对节点与变化；已有回写授权覆盖时直接 `dry_run=false`，不逐条再问。仅生成用例或未授权回写时不落库。

**写是全量覆盖**，写前务必备份（MCP 已自动存 `/tmp/banshan_backup_{caseId}_{recordId}_{ts}.json`）。

# 跑回归 SOP（通用）

上半部分是平台机制，这一节是**拿到一份用例集后怎么跑、怎么判、怎么写**。不含任何具体业务资产。

## 输入与产物

输入：用户指定的功能、优先级和任务类型，以及需求/已确认规则；caseManager URL（或caseId+recordId）、分支和环境按生成或执行的实际需要查找。不能因缺 PRD/diff 就扩大成全量探索，也不能按实现反向修改预期。生成文档时按需自主补齐必要测试数据，确实无法补齐的前置如实标明；数据准备完成也不冒称用例已实际执行。

以下是执行回归时按需维护的产物；仅生成用例时交付用例即可，已无阻塞不新建空造数需求，未授权平台回写则报告未回写：

| 产物 | 位置 | 内容 |
|-|-|-|
| 执行记录 | `<feature>-case-record.md` | 逐条用例的结论 + 证据，按模块组织 |
| 造数需求 | `<feature>-data-requirements.md` | 只写「跑不了」的用例，按用例一节 |
| 用例状态 | 平台上 | 已授权回写时逐节点更新，`dry_run` 核对后落库 |

若判断这套用例会**反复回归**，把该功能的固定资产（测试班级/账号/学员清单、可反射调用的入口签名、DB/ES 校验口径、业务特有的坑）另存一份功能笔记，本节负责流程、它负责资产。

## 六条工作约定（每轮都照做，不可省）

1. **时间前提按被测行为处理**。时间不是本case被测点时，优先选已满足条件的有效样本；只有能证明不改变被测行为和必要前置时，才用等价入口代跑并注明证据边界。不能为跑通而改系统时间、绕过被测规则或调整业务实现；时间边界本身是被测点时才准备两侧数据。
2. **缺测试数据先自己补，不把可做的活交给用户**。按上方数据授权自行造数或修改测试样本并回读；只有确实无法完成时才记造数需求，说明已尝试什么、卡在哪里、缺少哪些表/字段/值及自验方式。影响关键预期或操作超出授权时再提具体问题。
3. **在本次范围内查证，不全环境穷举**。优先查已有有效样本和必要候选，记录查过的范围、结果及缺失前提。证据不足时写“本次查找尚未找到”，不能声称环境绝无数据，也不能因此扩成全库、全模块搜索或增加无关 case。
4. **区分四种结论**，前三种都不是 bug：

   | 结论 | 含义 | 处理 |
   |-|-|-|
   | 通过 / 部分通过 | 主判定成立；部分通过要写明哪一半没验到、为什么 | 记录证据 |
   | 跑不了 | 数据或环境缺，实现未被检验 | → data-requirements；已授权回写时平台标**阻塞** |
   | 有异议 | 旧用例与最新需求冲突，或需求口径尚不明确 | → 给出需求依据与替代步骤；口径未定记**阻塞**，平台回写按授权，不按实现倒改需求 |
   | 失败 | 证据已证明实际行为偏离确认预期 | 给最小复现与已有定位证据，只报告，不自动修功能 |

5. **有异议时必须按需求给替代写法**。说明旧case与最新需求哪条冲突，列修正步骤/预期；只有代码不同于case，不能据此判case错，应核对需求或明确待确认。
6. **回写前先 `dry_run=true`** 自行核对节点匹配；已有授权覆盖时直接 `dry_run=false`，未覆盖不回写。

## 0 环境判定（第一步，别跳）

先从用户指定环境、需求泳道和实际部署记录查清本次验证目标与版本。分支是否合入、record 名叫“线上回归”都不能代替实际环境版本，也不自动授权生产执行；当前必要测试数据的造数与修改沿用前面的测试环境授权。

验证新改动前核对环境实际镜像 commit 包含目标改动，再确认新机器 `eurekaStatus=UP` 与泳道路由；已有正确版本就复用，不为每条 case 重新部署。具体跟踪方式与按批验证见 [deploy-image](../../skills/deploy-image/SKILL.md)。

## 1 拉用例，建执行清单

`banshan_get_case(url=…)` → 拿模块+用例索引（含**节点 id** 与现有执行状态）→ 按本次功能、优先级与影响依据筛出选定节点，再组织执行清单。拉到整份脑图不等于执行整份；未选节点不执行、不改状态，选定 node id 是回写凭据。

## 2 逐条执行

顺序固定：**读需求定预期 → 核实现与数据 → 按场景实际执行 → 取证 → 回写人可复跑的执行卡**。

1. **读确认规则定预期，读实现找验证点**。有本次需求变更时核 PRD、diff 及有证据的影响；针对已有功能时核用户指定范围、有效规则与已有用例。只执行本次选定的 case，不把无关历史功能扩大成验收门槛。
2. **按被测行为选入口**：页面操作、权限、联动、展示须实际页面验证；接口契约走真实HTTP；内部规则可用单测/服务调用。不能用反射代替页面保存、账号权限或完整链路。全类名、形参、SQL等留在执行卡后面的技术证据区。
3. **取证**，只认落库效果与返回值，不认"接口 200"：
   - DB：结果表 / 留痕表（调用次数、幂等、任务状态都在这里比对）
   - ES：文档 `_id` 与字段值（列表/筛选类用例）
   - 日志：按 traceId 查（[traceid-debug](~/.claude/skills/traceid-debug/SKILL.md)）。注意**服务层 INFO 常查不到**，排链路靠异常堆栈 + DB 效果。
4. **每条写简洁执行卡并引用集中证据**：只保留影响操作和判断的账号/入口、班级 bizId/班名/学员 ID、必要关系、关键计算、操作/预期/实际及恢复结论。缺项须查询或明确标缺，不能杜撰或用“某班/符合条件”占位。原始调用、完整 DB/ES 与日志放证据区，不在各卡重复展开。

## 3 回写状态

状态四选一：`通过` / `失败` / `阻塞` / `不执行`（`progress` 值映射见 [platform-mechanics](references/platform-mechanics.md) 的「执行状态」）。约定：

- **部分通过不自动标通过**：优先拆分可独立判定子case；未拆分且仍有必验项未完成时，按真实原因标阻塞或失败，说明已验与未验部分。只有该节点全部必验项满足才标通过。
- **跑不了 / 有异议 → 标「阻塞」**，理由落在 data-requirements。
- 状态挂在**用例级节点**（带 `priority` 那层），不是步骤节点。
- 改之前让浏览器关掉同一 tab，同账号同用例会互踢。

## 4 文档模板

两份模板见 [doc-templates](references/doc-templates.md)：`case-record.md` 按模块逐条记结论+证据，开头汇总总数/通过/跑不了/有异议/失败 + 环境结论，末尾留「遗留待办」；`data-requirements.md` 开头阻塞清单，逐条四段（为什么跑不了 / 要造的数据 / 验收步骤 / 注意事项）。

## 5 通用坑

与业务无关、每个项目都可能撞的坑见 [common-pitfalls](references/common-pitfalls.md)。

## 验证

- 落库后**重拉一遍** `banshan_get_case(url=…)`，读用例级节点的 `data.progress`（通过=9 / 失败=1 / 阻塞=5 / 不执行=4）；或 `GET /api/banshan/api/record/getRecordInfo?id={recordId}` 看 passCount/blockCount 是否随之变动。只有回读到新值才算生效。
- 不算通过：MCP/命令的「保存成功」、ws 回的 `save_event: 保存成功`、服务端「当前用例内容无变化，无需存入备份表」（`save` 只写备份表，`edit` 才落库）、`dry_run=true` 的回显、HTTP 200。
- 测试数据写入后按造数/数据库 skill 回读确认对象、状态与关联满足前置；记录准备动作与必要恢复方式，不以修改结果数据代替验证。
- 生成/编辑后逐条核对功能与优先级、预期依据和纳入原因，删去没有范围依据的扩展；未执行不标通过，发现业务问题仅报告，不夹带功能修复或平台写入。
- 生成/编辑文档后回读正文及必要证据：按对象、动作、预期和实际能执行判断；精简前后场景、真实验证状态及证据引用不丢失。班级 bizId 不与主键混用，计算可按真实输入复算；缺数据或样本已消耗时说明，不能宣称可直接复跑。

## 常见合理化（别这样）

| 借口 | 正确做法 |
|---|---|
| “多补些模块和边界，把它们都标P0更全面” | 只覆盖指定功能的核心行为；额外验证须有依赖或影响依据，不能靠升优先级扩大范围。 |
| “缺陷都定位了，顺手修掉省时间” | 本任务只报告复现与证据；写/跑case不包含修功能授权。 |
| “改测试表也得逐次征求同意” | 当前 case 必要且合理范围内的测试数据准备已获授权；核对目标、修改、回读并记录即可。 |
| “数据补齐了，直接标case通过” | 数据前置自验与被测行为验证分开，未执行case不能标通过。 |
| “范围内每个小选择都问用户更稳妥” | 先自主查证并决定，只有关键卡点或必要未授权操作才提具体问题。 |
| “精简就是删掉对象、计算和证据” | 保留班级 bizId/班名/学员 ID、关键条件和计算；原件集中引用，未知和未测不能省略。 |
| “证据完整就要每条粘完整响应和日志” | 正文采用必要前置、操作、关键预期和实际；完整证据集中引用，避免重复。 |
| “有个班级数字就可以当 bizId” | 查清页面/接口业务编号与数据库主键的映射，不靠字段名猜，不可取得就标缺。 |
| “代码就是这么写的，改case适配它” | 需求决定预期；代码偏离需求需定位或确认，不倒置依据。 |
| “服务调用通过就等于页面通过” | 按真实入口记录覆盖范围，未逐页面执行不能写已全部点击通过。 |
| “旧订单以前通过，可以继续当正例” | 先核当前有效性与执行顺序；已全退/已消费样本写明不可重复使用，补新样本或重建步骤。 |
| “提到发送目标就等于可以发消息” | 目标说明用于定位；实际发送仍需当前任务明确授权，不能由用例文字推导授权。 |

## 验证范围与缺陷登记

需求验收按 PRD/diff 及有证据的影响选范围，已有功能回归按用户指定功能与优先级选范围。范围外问题简要报告现象与关联依据，不自动增加 case 或设为本次完成门槛；确实阻塞选定 case 时说明具体依赖与未验项。失败先提供复现与证据，不自动修改业务或登记 TAPD；发布告警的状态副作用和授权边界见 [告警归属与登记边界](../../skills/qingzhou-release-plan/references/alarm-triage.md)。
