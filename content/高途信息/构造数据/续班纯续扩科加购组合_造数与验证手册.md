> 适用：要让某学员在某续班计划下**推出**纯续、扩科、加购或组合商品，并在 B 端推荐、C 端续班购物车、下单支付三段上验证。
> 环境：TEST。泳道以实际部署为准（历史样本在 `test-gtbg-dev-3`、`test-eco-8`）。
> 依据：cart `feature-renewal-preheat-v2-20261112` @ `500dfa8d` 源码（2026-11-25）、data-agent @ `e3693d4`、本目录三篇案例文档、需求归档 `【A-续班-20261102】`。
> 配套：接口全表 [造数项目能力与接口总览.md](造数项目能力与接口总览.md)；业务口径 [续班推荐业务逻辑（纯续-扩科-推荐排除）](../知识库/续班科目/续班推荐业务逻辑（纯续-扩科-推荐排除）.md)；新增商品类型改动面 [续班商品链路接口清单](../知识库/续班商品/续班商品链路接口清单.md)；线上排障 [工单/续班与业绩/续班推荐加购](../工单/续班与业绩/续班推荐加购/README.md)。

## 0. 一张图看懂：推荐里的四种东西从哪来

| 推荐位 | `recommendType` | cart 枚举 `RecommendType` | 数据从哪来（源码） | 怎么造 |
|---|---|---|---|---|
| **纯续** | `1`（或 null） | `RENEWAL` 在读推荐 | 学员**在读前置课** → 计划 `renew_master_course_relation` 前置 → course-center 续报关系（`course_relation_map`，`relation_type=1`、`calculate_renewal_type=1`）→ 后置课/班；主计划还会**并上**主从关联的从计划前置课（`mergeRelatedPreCourseNumbers`，单向） | §2 |
| **推荐位白名单 / 组合纯续** | `1` | 同上 | 续班报名流程 type=2 的节点 type=3：`recommendProductType` + `recommendFile`（前置班→指定推荐商品）/ `combineRangeFile`（组合 SPU） | §5 |
| **扩科** | `2` | `EXPAND_SUBJECT` 扩展推荐 | 计划扩科节点（`node_config` type=6，`ext_config` 带 beginTime/endTime）+ `gaotu.renewal_expand_subject_recommend`（renewal_number, grade, subject, product_type, product_number），按后置年级匹配；再被 `excludeMode` 推荐排除过滤 | §3 |
| **加购** | `3` | `ADDITIONAL_PURCHASE` 二讲推荐 | **B 端购物车**：`BCartFacadeImpl#listAdditionalPurchase(userId, sellerId)` → sellerId（员工 employeeId）转 accountId → order `BCartQueryApiFeignClient.listByUserIdAndAccountId`。只在 `includeBCart=true` 且有 `sellerId` 时查 | §4 |

商品类型：`2` 大班班级 / `23` 联报（productId=activityNumber）/ `51` 组合（productId=组合 **SKU**）/ `6003` 旧 1v1·1vN / `6004` GPS 小班（SKU 号=clazzNumber）/ `8014` 膨胀券 / `8027` OMO。

合并规则（V2 `RenewalV2ResultMerger` + `dedupClazzByGradeByProduct`）：同年级同 SKU 只留一个，优先级**纯续 > 扩科 > 加购**；跨年级保留。展示排序：未购在前、已报名沉底，强制购买在前，纯续 > 扩科 > 加购。

## 2. 纯续：造数 → 测试 → 验证

### 2.1 造数（从零）

链路（data-agent）：

1. **建计划骨架**：`renew_clone_plan{source}`（复制已知可用计划的维度）或 `create_renew_master`。
2. **前后置课+班**：
   - 有现成源计划：`renew_build{source,target,price,publish:true}`（含绑定+保护期+发布+自校验）；
   - 只差后置：`renew_add_posts{plan,posts_per_pre,price}` 或 `create_post_course_with_clazz_for_renewal`（后置年级=前置+1，学年/学期∈计划 target）；
   - 前置班要干净可用：`create_renewal_regression_clazz{courseNumber,...}`。
3. **补推荐流程**（最常漏）：`arrange_renewal_recommend` 或直接 `product_b_b_renewal_process_edit`，给计划配 **type=2 续班报名流程 + type=3 节点**（`recommendProductType`=2 大班 / 6004 小班 / 51 组合），时间窗覆盖当前。没有它：cart 恒空、B 端发链接报「暂无续班报名流程」。body 样例见 [续班C端下单 §8.8](续班C端下单_构造与复现步骤.md)。
4. **学员在读前置**：`order_by_product_number{productNumber:<前置班/SKU>, userId}`（自动识别 productType + mock 支付）。
5. **可售门槛回读**（铁律）：后置 `saleStatus=40`、课节>0、老师非空；不满足用 `resume_clazz_sale` 或 6004 走 `publish_uniform_product → sale_uniform_sku → shelf_uniform_sku`。
6. （需要「可续」口径时）配保护期 + 判单，见 [总览 §4.5](造数项目能力与接口总览.md) 与仓库 `execution.md`「可续学员构造」。

前置绑不上（报「存在不符合当前续班计划的前置课程编号」）先查：课程 `courseType∈{30,40}`、`operationMode=1`（线上）、`publishStatus=40`、`canFollowCourse=1`、末级部门=计划部门末级、学年学期年级学科一致。CES 小班课要产品线 `online_big_class=1` 才会同步成可续课。

### 2.2 主从关联（EM 纯续并集）

```bash
# skills/data-agent 下；默认只预览，确认后加 --apply
python -m continueclass.plan_relation --main <主计划> --children <从计划> --mode append --cookie "$OES_COOKIE" --traffic <泳道>
```

- 单向：主→从，从计划单独发起不会合并主计划。
- 读回：`GET /product-b/b/renewMaster/relation/list?renewMasterNumber=<主>`。
- product 侧有版本化缓存（`renewal:relation:version:{main}`），**只有 B 端 save 会刷新**；DB 软删 `renew_master_relation` 不会让 product 侧实时变，cart 预热缓存（`renewal:preheat:<计划>:<学员>`，TTL 26h）也会残留，需关 cart Apollo `preheat.cache.enabled` 再验，测后恢复。
- 开关：cart Apollo `renewal.pure.relation.enabled` 关闭时关系保留但不推关联。

## 3. 扩科：造数 → 验证

1. 确认计划有**进行中时间窗内**的扩科节点（`node_config` type=6）。没有就用 `product_b_b_renewal_process_edit` 建；**新造节点会被 product 配置组装链多层缓存挡住，不一定实时生效**（2026-11 实测）。
2. 加扩科商品（任选其一）：
   - 正式入口：`product_b_b_renewal_process_expandsubject_add`（`POST /product-b/b/renewal/process/expandSubject/add`，年级+学科→商品），`_list` 回读；
   - 测试库直插：`gaotu.renewal_expand_subject_recommend` 一行（renewal_number, grade, subject, product_type, product_number）。**已有节点时实时生效**（缓存全开也生效）。cart 按计划号读，忽略 node_number。
3. 扩科对应的是**后置年级**；同 (grade, subject) 的扩科与加购去重后按扩科呈现；与纯续同 SKU 时只留纯续。
4. 推荐排除：`excludeMode` 会按「学员在其它授课模式在读的学科」过滤扩科，读侧是 student-data `/feign/renewal/otherModeInReadSubjects`。该接口 404 会降级为不排除，表现为条数忽多忽少（「一次 2 一次 4」）。

## 4. 加购：造数 → 验证

**本质是 B 端购物车**，不是计划配置：

1. 老师（员工）在 B 端给学员加购：order-b `POST /bgwApi/orderComponent/b/cart/addCart`，body 商品数组 `[{productNumber:"<SKU 字符串>", productType:<2/6004/51/8014…>}]`（productNumber 用字符串防精度丢失；网关要登录态，或容器直连）。
2. C 端带 `includeBCart=true&sellerId=<该员工 employeeId>` 才会查；cart 内部把 employeeId 转 accountId，再按 `userId+accountId` 取购物车。**sellerId 不传/传错 = 加购位一定空**（不是 bug）。
3. 加购项 `canChangeCourse=false`；`signUp` 按加购 SKU 本身查有效订单；组合按 SKU 展开。
4. 坑：同商品重复加 → `ONCE_BY_LIMIT`；同模式真重复 → `SAME_CLAZZ`/`SAME_COURSE`；跨请求混加大小班撞既有 `PAYMENT_SIZE`（资金账户不一致，非续班代码）。
5. 只读核对加购原始数据：桥调 cart `BCartFacadeImpl#listAdditionalPurchase(userId, employeeId)`，与 C 端返回逐条比。

> 加购验证只能证明「加购路径」；组合在加购位缺失**不能**推出组合纯续不支持（两条独立链路）。

## 8. 常见坑速查

| 现象 | 原因 → 处理 |
|---|---|
| C 端「未查询到满足条件的课程」 | 计划号不是学员所在主计划；或计划没配 type=2 流程/type=3 节点 |
