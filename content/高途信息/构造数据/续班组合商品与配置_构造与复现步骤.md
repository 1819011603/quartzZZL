## 3. BossBatch 下单：造组合/班课订单

**用途**：给学员造组合（pt51）或大/小班课的有效订单，驱动 C 端 signUp 0→1。

**入口**：容器直连 `POST /web/order/batch/boss/prepare|createOrder`（服务 `ORDER.GAOTU100.COM`）。网关 `/web/order/**` 有登录拦截（返 700/CAS），必须容器直连绕过（invoke_feign 按 Eureka 找 ip:port）。

**body（productList 格式）**：

```json
{"productList":[{"productNumber":"<SKU>","productType":51,"quantity":1}]}
```

- `productType`：`51`=组合、`2`=大班课、`6004`=小班课；可多元素混下单。
- create 需**有效 source orderTag**：test Apollo `can.create.order.when.invalid.source=false` 强制校验。**source 合法规则（实测）=纯数字 10-20 位、或 `z` 结尾即合法**（`MonitorSourceTagProcessor`，无库表校验）；orderTags 实测用 `tj173304329532355584z` 通过。
- 完整入参样例：需求归档 `20261105-p0-execution-round7/preview-main-small.json`。

**支付**：

- **0 元单免支付**：组合 totalPrice=0 时 `needPay=false` 自动完成（`pay_channel=40`）——sjg 组合下单即生效，**不需要 mock_pay**。
- 非 0 元单走 data-agent `mock_pay`：传 createOrder 返回的**订单号（批次单号）**，不是支付单号；`traffic_env` 与下单环境一致（历史 run `r-20261106100523-08edf28b`）。

**验证方式**：

- DB 回读：批次单号查 `gaotu.pay_info`（`pay_status=1`）；组合订单**大班子班落 `order_info`、小班 SKU 落 `order_item`**（均 `order_status=2`）。
- 运行时：C 端 `/cart/web/renewal/cart` 看组合拆条 `signUp` 0→1（sjg 5 拆条全变 1，1v1 组合等未购保持 0 作负向对照）。
- 实证（2026-11-19）：批次单 `434960574395711494`（order_info `434960574395712006` 大班子班 / order_item `434960574395712518` 小班 SKU 483180833165871104）；signUp 0→1 TID `cart_gaotu100_com.286.17950882549710151`（支付前）→ `cart_gaotu100_com.286.17950886932860162`（支付后）。

**坑**：

- 造数班可能**库存不足**：GPS 班 `579971527131324416` prepare code=0 但 createOrder code=408（造数班库存限制，非代码问题；未改他域库存，正向用历史有效订单覆盖）。
- 下单走 order-b 不分 cart 泳道，但**验证要回对应 cart 泳道**（pod 直连 + traffic-env），否则看到的是别的泳道的缓存/数据。

## 4. 扩科组合配置：`renewal_expand_subject_recommend` 直插

**用途**：让计划在**扩科位（rt2）** 出现组合条目。

**入口/参数**：测试库 `renewal_expand_subject_recommend` 直插一行（pymysql；测试库可直连写）。字段口径参考既有行：

- `id118`：小班主从计划（586116340522184704）grade11 subject6 → sjg 组合 483217233600958464（pt51）
- `id119`：大班主从 grade31 subject3 → sjg 组合（计划归属以表内实际行为准，来自归档第二十八轮记录）

**步骤**：

1. 确认目标计划**已有「进行中时间窗内」的扩科节点**（这是硬前提，见生效规则）。
2. INSERT 配置行（计划 + grade/subject + 组合 SKU）。
3. 只读回读确认行在。

**生效规则（关键）**：

- **已有扩科节点**（时间窗内）→ INSERT **实时生效**，cart 缓存全开也生效。实证：小班 rt2 组合条目出现 TID `cart_gaotu100_com.292.17950897429110285`、大班 rt2 TID `…285.17950897986280271`。
- **新造扩科节点** → 会被 product 配置组装链的**多层结构缓存**挡住不生效（第二十九轮 S4 临时扩科节点即失败后删除）。

**行为口径**：配置年级单条不拆条；同 (grade,subject) 的 rt2 与 rt3 去重后合并为 rt2 呈现。

**注意**：id118/119 在测试库**保留不清**（测试文档场景 21/22 断言依赖）。

## 5. 推荐位组合配置：DB 直插不生效，正式入口 B 端 editProcess

**用途**：让计划**推荐位（rt1）** 出现组合条目。

**结论（勿走弯路）**：`renewal_link`（product_type=51）+ `renewal_recommend_file` DB 直插**不实时生效**——3 计划 6 行尝试、cart 两个缓存开关全关仍不生效（product 配置组装链多层缓存）；验后全部 is_del=1 清理。

**正式入口**：B 端 `editProcess`（product-b `POST /b/renewal/process/edit`，`ProcessService#editProcess`；acl 桥直调方式参考续班C端笔记 §8.8）。

**验证方式**：C 端 `/cart/web/renewal/cart` 看 rt1 组合条目。定性口径：组合推荐位**解析**由主从运行时+代码同路径覆盖，「直插不生效」是**配置链路限制**而非解析缺陷。

## 6. 单主计划临时构造：软删 `renew_master_relation`

**用途**：现成 case 计划全是主从集群、无单主×组合样本；临时把某计划变「单主」验证单主形态行为。

**步骤**：

1. 软删 `gaotu.renew_master_relation` 该计划 **main 侧**关联行（`is_del=1`，逐行精确 update 并记录原值）。
2. **关 cart 预热缓存**（Apollo `preheat.cache.enabled=false`）再验证——软删后**预热缓存仍残留主从合并值**（key `renewal:preheat:计划:学员`，TTL 26h），关缓存才实时。
3. 验证：C 端 `/cart/web/renewal/cart`——从计划纯续/推荐条目应正确消失、主计划条目保持，与主从态逐条对照。
4. **验后精确复原 `is_del`**。

**坑/注意**：

- **product 侧主从真源不是这张表**：product `productRelationList` 下发 `relatedRenewMasterNumbers`（`RenewalMasterRelationService.listSubNumbers`），有版本化 Redis 缓存 `renewal:relation:version:{main}` / `v2:{main}:{version}`，**仅 B 端 save 刷新**——软删 DB 行不会让 product 侧实时变化（验证 cart 侧行为够用）。
- 批量改可能造成同表其它行 **`update_time` 时间戳漂移**（F 计划历史关联 13 行漂移过，is_del 精确复位、内容无损）——用精确 WHERE 逐行改。
- 实证 TID：单主×小班 `cart_gaotu100_com.293.17950922090910280`（缓存开）/ `…285.17950925541890335`（缓存关干净态）；单主×大班 `…289.17950923791810306`。

## 7. DB 查询口径（订单/支付/主从）

| 表 | 口径 |
|---|---|
| `gaotu.order_info` | **大班班课（type 2）** 落这里，按**班级号**查；组合订单的大班子班也在 order_info |
| `gaotu.order_item` | **6004 小班课、组合拆条子班** 落这里，按 **SKU 号**查（`order_status=2` 有效）。Bug 1486168 根因即 6004 只查 order_info 班级号必空（DB 实证：order_info by clazz=SKU 0 行、order_item 有单 `433534690352694278`） |
| `gaotu.pay_info` | `pay_status=1`=已支付；`pay_channel=40`=0 元自动完成、`6`=mock_pay |
| `gaotu.renew_master_relation` | 主从计划关联（`is_del` 软删；分清 main 侧/从侧行） |

## 8. 常见坑

| 现象 | 原因 / 处理 |
|---|---|
| createOrder 报 source/orderTag 无效 | source 规则=纯数字 10-20 位或 `z` 结尾（MonitorSourceTagProcessor，无库表校验）；用 `tj173304329532355584z` 这类 |
| 0 元组合单不确定要不要 mock_pay | 不用：totalPrice=0 → needPay=false 自动完成（pay_channel=40） |
| mock_pay 传支付单号无效 | 认的是 createOrder 返回的**订单号（批次单号）** |
| 组合下单后 C 端 signUp 还是 0 | ①看落库口径（小班 SKU/组合子班在 order_item）；②确认查询走了正确泳道/缓存开关 |
| 扩科位组合不出现 | 新造扩科节点被 product 结构缓存挡——改用**已有时间窗内节点** INSERT 配置行（实时生效） |
| 推荐位组合配了不出现 | renewal_link/renewal_recommend_file 直插不实时；走 B 端 editProcess |
| 软删主从关联后行为没变 | 预热缓存残留合并值（TTL 26h）——关 `preheat.cache.enabled` 再验 |
| 7746793735/7746793736 混用 | 两个不同学员，case 里都出现过 |
| 下单成功但验证看不到 | 下单不分泳道（order-b），验证须回对应 cart 泳道；mock_pay 的 traffic_env 与下单一致 |
