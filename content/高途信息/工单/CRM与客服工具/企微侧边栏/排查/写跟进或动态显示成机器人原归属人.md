# 企微侧边栏 · 写跟进或动态显示成机器人原归属人

> **只解决**：企微侧边栏（AI途途）里写跟进、看学员动态时，操作人显示的不是当前机器人使用人，
> 而是转号前的原归属人（或另一个同事名字）。
> 字段保存了不回显走 [`字段保存了不显示.md`](字段保存了不显示.md)；整个侧边栏打不开走 [`某客服看不到侧边栏.md`](某客服看不到侧边栏.md)。

## 链路（为什么会显示成别人）

**登录识别**：侧边栏壳（企微客户端 webview）→ crm-service `GET /crmApp/scrm/wk/auth/account?code&corpId&appId`
（[WkAuthController#account](/Users/gaotu/IdeaProjects/JavaProject/crm-service/server/src/main/java/com/gaotu/crm/server/app/controller/scrm/WkAuthController.java)）：

1. **cookie 账号优先**：webview 里有登录态且 redis `CRM_WK_ACCOUNT_<accountId>` ≠ `"1"` → 直接用 cookie 账号，
   **企微 OAuth code（能解析出机器人当前归属人）被忽略**。
2. 仅当 CAS `batchGetAccountRole` 返回 `status==1`（离职/停用）时才写 redis 标记 24h
   （`crm.wk.account.account.expireTime`，默认 1440 分钟），**下一次**调 /account 才走 code 重新识别。
   2026-01 修复（commit `5aa4b6c79`）只覆盖了「原归属人已离职」的场景。
3. Apollo `wk.account.avatar.map`（线上为 `{}`）可强制改写 accountId；`robot.info.switch` 开关只补
   hookId/logicId，不改归属人。

**落库归属**：写跟进走 student-center `POST /ols/w/studentArchives/addFollow`
→ `OlsStudentArchivesBiz#addFollow` 创建人取 `LoginInfoUtils.getLoginUser().getAccountId()`（登录态），
**前端 body 里的 accountId 入参不参与归属**。动态流的操作人名字就是这条落库的创建人。

**code 解析 accountId（linkup，重登时才走）**：crm `wkAuthGateway.account(code, corpId, appId)`
→ linkup `WkAuthQueryProcessor#getWkAccountId`：code →(瓦力云 queryAuthUserInfo)→ 企微成员 userId →
prod 开关 `wk.queryAccount.emailFirst=true`：userId 纯英文（或在 `wk.queryAccount.emailFirst.userId.set` 白名单）
**先邮箱**（企微成员 email 前缀 → CAS `getAccountByName`），失败再 userId 当账号名查；userId 含数字
**先 userId**，失败再邮箱。两路都失败抛「企业微信xxx无法匹配高途账号」。另有 `wk.wxAccountIdToUsername.switch`
（prod=false）+ `wk.wxAccountIdUsername.list` 强制映射表。
**核邮箱配置必须用企微实时接口**：`GET https://link.gaotu100.com/linkup/wk/auth/getCorpUserInfo?userIds=<成员userId>&corpId=<corpId>`
（userIds 可重复传多个；linkup `WkAuthClientImpl#getCorpUserInfoByUserIds`）。解析链路走的就是实时通讯录；
linkup DB 镜像 `wk_member_corp_info`（`getWkMember` 读的）可能数月不同步，email 是陈旧占位值，别拿它下结论。

**残留来源**：机器人跑在虚拟 windows 的微信助手上，webview 会话按机器存。瓦力云（link/walle）改归属
只影响企微侧身份，**不会清理 webview 里的旧登录态** → 原归属人在该 VM 上留下的 cookie 被下一个使用人继承。

## 排查

1. **定 accountId**：`gaotu.employee`（cluster `gaotu-center-prod`，db `gaotu`）按 `email_prefix` 查
   `account_id`；再用 crm acl 桥（`POST https://fuwu.baijia.com/bgwApi/crmApp/test/acl/compare/services`，
   经 baijia-proxy）调 `com.gaotu.crm.server.domain.upstreamservice.cas.service.CasApiService#batchGetAccountRole`
   params `[[<accountId>...]]` 核对 name/displayName/**status**（0=在职，1=触发 redis 标记）。
2. **看登录实际解析到谁**：qingzhou 日志（prod, logType=app）
   `__tag__:app: "crm-app-service-gaotu100-com" and messages: "getWkAccount" and messages: "<accountId>"`。
   转号后仍高频持续解析到旧 accountId、从不出现新 accountId → cookie 残留实锤（code 分支没被走过）。
   再拿 crm 侧 traceId 查 `__tag__:app: "linkup-gaotu100-com" and messages: "<traceId>"`，
   linkup 无 span = code 分支确实没走。
3. **排除 avatarMap**：Apollo `crm-app-service.gaotu100.com` PROD `wk.account.avatar.map` 应为 `{}`；
   非空时 accountId 会被改写成映射值，先看这条。
4. **核邮箱配置**（影响重登后能否解析出新归属人）：直调企微实时接口
   `GET https://link.gaotu100.com/linkup/wk/auth/getCorpUserInfo?userIds=<成员userId>&corpId=<corpId>`，
   看 email 前缀能否匹配 CAS（对照 `gaotu.employee.email_prefix`）。机器人成员 userId 从 linkup 日志搜号
   （手机号形态）可得。要模拟 CAS 匹配/调其它 bean 时走 linkup acl 桥（免进 pod）：
   `POST https://link.gaotu100.com/linkup/test/acl/compare/services`，头
   `teacherNumber/accountId/employeeId: 0`，body `{"requests":[{"serviceNameAndMethodName":
   "com.gaotu.linkup.wechat.pc.adapter.wxwork.WxWorkServerApiBoost#getCorpUserInfo","params":[["<userId>"],"<corpId>"]}]}`；
   同法可调 `CasApiBoost#getAccountByName`、`WkAuthQueryProcessor#getWkMember`。
5. **看写跟进归属**：student-center `addFollow` 落库创建人取登录态（`OlsStudentArchivesBiz#addFollow`），
   所以「动态显示错人」等价于「登录态是旧归属人」，不必再查写入链路。

## 处置（业务变更需先确认）

**先记住**：要清的是侧边栏 H5 的登录态，不是企微客户端登录——**不需要退出企微、不需要验证码**。
prod 无 `tokenExpire`/`casTokenExpire` 配置，用默认值：前端登录态 JWT **10 天**（`TokenHandler` 864000s）、
casToken 7 天、redis 标记 TTL 24h（`crm.wk.account.account.expireTime` 默认 1440 分钟）。
⚠️ 每次打开侧边栏 `/account` 都给当前 cookie 账号**换发新 10 天 token** → 只要在 10 天内打开过侧边栏，
旧身份永不过期，「放着等自然过期」不可靠。

- **方案 A（推荐，服务端一个 key，客户无感）**：prod redis `SET CRM_WK_ACCOUNT_<旧accountId> 1 EX <秒>`。
  这是 2026-01 修离职账号侧边栏的既有机制（`WkAuthController#account:128`，commit `5aa4b6c79`）手动触发：
  key 存在 → 跳过 cookie → 走企微 OAuth code → 解析出新归属人（前提：实时通讯录邮箱前缀能匹配 CAS，
  见排查第 4 步）→ 换发新登录态。TTL 按需给（覆盖假期用 7 天 604800；key 过期时 cookie 已是新人的，无所谓）。
  下次打开侧边栏自动生效，客户什么都不用做。
- **方案 B（客户侧轻量操作）**：微信助手/企微里清 H5 缓存 cookie，或虚拟机里重装微信助手客户端——
  都不动企微号登录、不用验证码。
- **代码层（未实施，需评审）**：/account 在拿到 code 且解析结果与 cookie 账号不一致时以 code 为准，
  或机器人归属转移时联动设置上述 redis 标记 / 清理会话。影响面：同人多角色切换、多人共用机器人场景。

## 验证

处置后：getWkAccount 日志应解析到新归属人 accountId；再写一条跟进，动态操作人应显示新使用人。
仅「重登成功」不算生效，必须看日志解析结果 + 新跟进的归属。
