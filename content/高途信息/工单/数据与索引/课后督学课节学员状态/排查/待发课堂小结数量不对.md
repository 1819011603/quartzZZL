# 课后督学课节学员状态 · 待发课堂小结数量不对

> **只解决**：EES 课后督学（课节学员页）卡片/筛选「待发课堂小结」的人数与老师/运营预期不符——怀疑少算、多算、或口径不一致。
> 大班课节学员其它字段（练习、听课、课节报告）同理可套。小班课花名册走 [`../../小班课花名册ES/README.md`](../../小班课花名册ES/README.md)。

## 判定入口

- 页面：`https://fuwu.baijia.com/crm/cronus/lessonStudentList?...&bs=lessonAfterUser`，卡片「待发课堂小结 N 人」= 接口 `/lesson/after/statistic` 返回的 `waitClazzSummaryCount`（student-center）。
- 先问清三件：班级号（页面顶部的 `clazzNumber`）、课节（`clazzLessonNumber`）、辅导班（`subclazzNumber`）；只报名字时可反查（见下）。
- **先分清三种「没发」口径**，它们不是一回事，直接决定是不是 bug：
  1. **页面口径** = 课节学员 ES 里 `clazzSummaryStatus` 不是「已发送(1)」的人（0 或字段缺失）。
  2. **触达口径** = 「课后课堂小结」场景里的**发送失败**记录数。注意字段口径是**任一次发送成功即算已发送**，"发送失败"≠"未发送"（可能是成功后的重发失败）。
  3. **真实送达口径** = 家长实际有没有收到。这属于触达(reach-service)送达真伪，不是本页能回答的。

## 数值来源（已验证）

- 卡片值 `waitClazzSummaryCount`：student-center `ClazzSummaryCountQueryService#buildData` 对 `ads_lesson_user_index_{年}` 做聚合，条件 = `clazzStudentStatus=1` 且 `internalStaffFlag=0` 且 `clazzSummaryStatus ∈ {0, 字段缺失}`，按 `clazzLessonNumber + subclazzNumber` 分组。
  - 索引按**班级 createTime 所在年份**动态选：`AdsLessonUserIndexServiceImpl#batchGetIndexes` → `ads_lesson_user_index_2026`。
  - 同页「待发课节报告」走 `LessonReportCountQueryService`，逻辑同构，字段是 `afterrReportStatus`。
- 复现页面数字（只读，走 SRE `runDslAction`，见 `es-apply` skill；集群 = `student.serve.es.cluster.host`，student-center PROD = `es-cn-4xl3gu6ls0007l185`）：
  ```bash
  python3 es_workorder.py search --instance-id es-cn-4xl3gu6ls0007l185 \
    --index ads_lesson_user_index_2026 \
    --query '{"size":0,"query":{"bool":{"filter":[{"term":{"clazzStudentStatus":1}},{"term":{"internalStaffFlag":0}},{"term":{"clazzLessonNumber":<lesson>}},{"term":{"subclazzNumber":<subclazz>}}]}},"aggs":{"by_status":{"terms":{"field":"clazzSummaryStatus"}}}}'
  ```
  或直接调接口（打通了鉴权/路由）：
  ```
  POST https://fuwu.baijia.com/bgwApi/component/student-center/lesson/after/statistic
  {"clazzNumber":"<c>","subclazzNumber":"<s>","clazzLessonNumber":"<l>"}
  ```
  大数字 id 一律传字符串，别传 JSON number（超 2^53 会截断）。

## `clazzSummaryStatus` 谁写（student-data，0=未发送 / 1=已发送）

唯一来源是**触达「课后课堂小结」场景**的发送记录（场景 code=`clazz_summary`，reach scene id=**50**）：

| 写入者 | 触发 | 口径 |
|---|---|---|
| `DwsLessonUserRemindSyncConsumer` | 触达通道子任务完成事件（`ChannelSubtaskFinishedOuterEvent`，scene=`clazz_summary`） | `taskStatus=SUCCEEDED`→1，否则→0 |
| `ClazzSummaryStatusDataQueryService` | 构建课节学员 ES 文档时（DataQueryServiceV2） | 查触达记录算 |
| `BackClazzSummaryStatusService` | 回溯/自愈 job（`BackClazzSummaryStatusHandler`） | 任一 SUCCEEDED→1 |
| `AdsLessonUserOrderConsumer` / `AdsLessonUpdateSyncConsumer` / `HistoryRecallClazzLessonUserHandler` | 主文档构建 | 初始置 0 |

查某学员的触达记录（student-data acl 桥代调 feign，只读）：
```
project=student-data
service_method=com.gaotu.student.data.client.acl.adapter.ChannelSubTaskAdapter#recordByScene
params=[{"userLessons":[{"userId":"<uid>","clazzLessonNumber":"<lesson>"}],
         "reachSceneCodes":["clazz_summary"]}]
```
返回该 (学员,课节) 的**全部 final 记录**（CANCELED/FAILED/SUCCEEDED），带 `reachType`（19=微信助手私聊群发）、`taskStatus`、`sendType`（1=手动）。

## 判据

- **有任一 `taskStatus=3(SUCCEEDED)`** → 该学员应为「已发送」，页面「待发」里就不该出现他。据此逐人对照页面数字。
- 全无成功记录（只有 FAILED / 无任何记录）的才是真「未发送」。
- **已知会写偏**：`ClazzSummaryStatusDataQueryService#buildData` 用 `Collectors.toMap(..., (a,b)->a)` 取**任意一条**触达记录定状态，若命中的第一条是 FAILED（哪怕是同一次群发里的失败子任务）、另一条才是 SUCCEEDED，就会把已发送写成 **0（未发送）** → 页面「待发」**偏高**。逐人核对发现"有成功记录却显示未发送"即命中此点。

## 近义场景坑

触达里有两个名字极像的场景，别搞混：
- id **48** `class_summary` → 名称「课堂小结」，path「研发使用-测试数据-课堂小结」（测试用）。
- id **50** `clazz_summary` → 名称「课后课堂小结」，path「学员服务通知-课后督学-课后课堂小结」（课后督学实际用）。

student-data 默认 `${ods.clazzSummary.reachSceneCode:clazz_summary}`（=50），PROD 未覆盖该 key → 用的是 50，正确。

## 验证

- 结论「页面数字对」：该班 ES 里 `clazzSummaryStatus=0/缺失` 的人，逐个查触达**都没有 SUCCEEDED 记录**；`=1` 的人**都有** SUCCEEDED 记录。
- 结论「页面数字错（偏高）」：能举出"ES=0 但触达有 SUCCEEDED"的具体学员。
- 结论「页面数字错（偏低）」：需举出"ES=1 但触达无任何 SUCCEEDED"的学员；只有到这一步才说明是本页/字段的问题，否则查触达送达真伪。
- 只看接口返回 200、卡片刷新、或单条触达记录，都不足以定性，必须逐人对照。
