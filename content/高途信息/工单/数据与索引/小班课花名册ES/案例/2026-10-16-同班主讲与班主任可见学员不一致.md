## 结论

**现象确认（同一班级，主讲与班主任可见学员集合不同），但当前不判为数据缺陷，属权限维度口径差异**（王永诗最初「口径问题」的判断更接近事实）：

- 权限过滤 `SmallClazzUserPermissionFilterService#build` = **OR**：ES 文档字段 ∈ {登录 accountId + 兼职}；PROD `es_query_config`（type=permission/account）配的字段含 `assistantAccountId` + `mainTeacherAccountIds`。
- `mainTeacherAccountIds` **班级级** → 主讲看到**整个班级下所有辅导班**的学员；`assistantAccountId` **辅导班级** → 班主任只看到**自己辅导班**的学员。这正是 PRD 子需求2「小班续班适配主讲」已定口径（主讲按班级维度、仅班主任按辅导班维度）。
- 青藤9阶各班被拆成多个辅导班（「善思班-N / 智源班」各配一位班主任），故差异显眼；78年级同类现象暂未印证（8阶班同样含 12 位班主任，故「78年级没问题」的成因未证实，见「未确认」）。

**对反馈给出的 3 个 userId：以班主任 许祎笑 登录实测，在续班服务与花名册两个 tab 均能看到**（她自己的辅导班里）；「班主任看不到这 3 人」在当前数据下**无法复现**。真正差异是「主讲看到全班、班主任只看到自己辅导班」。

**「学员状态不一致」（业务后续澄清的点）**：`clazzStudentStatus` 是**按「班级 + 辅导班」存储**的（ES 文档 `_id = clazzNumber-userId`），不是按人。实测**同一条班级记录下，主讲和班主任返回的学员状态逐条完全一致**（见证据）→「同一条记录两边状态不同」不成立。看起来不一致的真实来源是：**同一学员在同一学期有多条班级/辅导班记录、状态相反**——如朱浩宇/肖锐在【2026/秋】青藤9阶思维（苏科版）善思班下有两条：辅导班「许祎笑TK231008」(clazz `...580`)=在班(调课)、辅导班「许祎笑TK231004」(clazz `...582`)=退班(调课)（582 joinClazzTime 更早，580 是后来的调课目标）。谁显示哪条取决于他筛选/落到的班级号；当同一课程下存在多个**同名班级**（`580` 与 `582` 的 `clazzName`、`courseNumber` 都相同）时，主讲与班主任很容易各自落到不同班级号，于是同一个人显示成不同状态。

**最终定位（马胜，2026-10-16）**：**不是某个数据字段错，而是「筛选条件」差异 —— 「班级」选的条件不同/选得太多**。一个续班计划下约 **300 个班级**，页面「班级」选择器支持全选/多选（`showSelectAll`、`maxTagCount=1` → UI 只显示「青… +99」）；把整个计划的班级全选后，会同时命中同一学员在**多个班级/辅导班的新旧记录**（在班 + 退班各一条），看起来就是「同一人学员状态不一致」。**把班级范围缩到具体班级就没问题**（马胜：「这样是没问题的」）。

## 根因确认与临时处置（2026-10-16 · 马胜）

**根因**：**班级下拉列表条数上限** —— `SmallFilterComponentServiceImpl#doListFilterComponentByClazz`（student-center）用 terms 聚合 `field("clazzNumber").size(size)`，`size` 取 `small.clazz.filter.max.size.with.renewal`（有续班期筛选）/ `small.clazz.filter.max.size.default`（其它）。班级数超过上限的续班计划，下拉只加载前 N 个班级，**其余班级的学员在续班服务/花名册"看不到"**（chip 显示「青… +N」）。

## 后续优化点（按优先级，2026-10-16）

> 背景：一个续班计划约 300+ 班，且页面要求「把该计划的班全选上」；把上限从 250 提到 500/1000 只是抬阈值。ES 侧一次查 1000 无压力（terms 查询/聚合都远低于 `max_terms_count`/`max_buckets` 默认值），瓶颈在**下游逐班调用**和**硬截断本身**。

- **P0 · 指标接口逐班 Feign（最主要，易超时）**：`SmallRenewalService#queryQuestionnaireUserIds`（`SmallRenewalService.java:695-703`）对每个班级**串行**调一次 `questionnaireAclService.typeUsersQuestionnaires`，调用次数 = 班级数，且**无缓存**；`/roster/small/renewal/statistic`（顶部可续学员数/问卷提交率等）每次搜索都重算。500→1000 即 500→1000 次下游调用。**优化**：批量化/并发化，或找按班级集合批量查问卷的接口；必要时给指标加短缓存。
- **P1 · 班级下拉的硬截断（根因本身）**：`SmallFilterComponentServiceImpl#doListFilterComponentByClazz` 的 terms 聚合 `size` 取 `small.clazz.filter.max.size.*`，**超上限静默丢班级**。**优化**：改分页/搜索式加载（不要全量下拉），或至少在上限触顶时**返回截断标记 + 前端提示/告警**，不要静默。
- **P2 · 前端渲染**：班级选择器一次渲染上千选项、请求体偏大，可能卡顿；配合 P1 的分页/搜索式加载一起解。
- **P3 · 监测**：班级数接近上限时打点/告警（避免下次又靠人工发现"数据少了"）。

**不作为优化项（已讨论）**：续班轮次的 Redis 缓存 key 是**整个班级号集合拼串**（`SmallRenewalService#generateCacheKey`，`SmallRenewalService.java:201`），1000 班时 key 很长——但**不拆更好**：单 key 一次 `getOrSet` 就能命中，拆成多个 key 反而多几次往返、更容易不命中；长 key 只是观感问题，Redis 单 key 没有压力。保留现状。
