# 退费预测分层配置 · 某班学生集中标为高危

> **只解决**：某班/某批学生"AI预测退费意向"高危占比异常。
> 三次事故根因都是 `predict_intent_config` 缺精细配置后退化到 `defaultGrade` 兜底，
> **先查配置再怀疑代码或算法**。

适用：收到「某班/某批学生高危退费占比异常」类反馈。**先查配置缺口，再怀疑代码或算法模型**
——两次真实事故都不是代码 bug，而是 `ees_data.predict_intent_config` 缺精细配置后静默退化到
`defaultGrade` 兜底阈值。

## 0. 先分清两个 job（最容易搞混）

| | `refundPredictionCheckHandler` | `SyncRefundResultHandler` |
|---|---|---|
| 作用 | **每天自动产出**「AI预测退费意向」 | **仅手动补数/回溯历史** |
| prod job | job_id=10073，jobGroup=314（`高途-运营工作台-student-data`） | job_id=12513「退费分层回溯」、10251「退费结果回溯」，jobGroup=530（`student-data-dws`） |
| 状态 | triggerStatus=1 运行中，cron `0 0 6,9 * * ?` | triggerStatus=0 **已停止，不会自动跑** |
| 入口方法 | `RenewalComponent#refreshRefundSnapshotIntentRecord` | `RenewalComponent#refreshRefundResultIntentRecord` |

**推论：阈值配置改完不需要人工干预**，次日例行调度会自动用新配置处理当天新产出的记录。
只有要修**历史存量**记录时才需要下面第 2 步的回溯。查 job 现状走 `xjob-admin` skill：
`xjob_list_jobs -k handler=<refundPredictionCheckHandler 或 SyncRefundResultHandler>`。

## 1. 定位是不是配置缺口

配置表 `ees_data.predict_intent_config`，结果表 `ees_data.ai_refund_prediction_results`，均 PROD
`cluster_id=336`（走 `mysql-query` skill）。维度是「业务线 × 学部 × 学期 × stage × 年级 × 新老生」，
任一组合缺精确配置即退化到 `grade='defaultGrade'` 兜底行；阈值区间存在 `intent_config` 一个 JSON
字段里（`[{code,start,end}]` 四档），不是拆开的独立列。具体 SQL 见 [`Scripts/排查.sql`](../Scripts/排查.sql)。

判据：**某个 `prediction_level`（尤其 4=高）占比畸高**，且精确配置查不到、对应组合
`grade_specific_rows=0` → 基本可判定为配置缺口。

⚠️ **补完配置要顺手验一件事**：2026-09-14 发现新补的配置里有阈值区间宽度为 0（`intent_config`
四档里中间两档 `start==end` 重合，比如精品班学部/初三/老生那条）的情况，疑似算法侧样本量不足
导致分位点重合。补完配置后核对一遍（`排查.sql` 第5步），命中重合就先别回溯，反馈算法侧确认。

## 2. 决定要不要回溯

- 只影响**当天及以后** → 不用回溯，等次日例行调度。
- 要修**历史存量** → 走 [`Scripts/回溯.sh`](../Scripts/回溯.sh)。
- **配置只补了一部分时不要做全量回溯**：回溯只能修好已补齐的那部分，剩下的仍吃兜底，跑完反而
  让人误以为已经全好了。等配完整、且阈值区间无异常再统一回溯。

## 3. 回溯历史数据

命令见 [`Scripts/回溯.sh`](../Scripts/回溯.sh)。走 `student-data-dws` 的 prod pod，用 `pod-terminal`
skill 的 arthas HTTP API（优先于 `baijia-invoke` 的 HTTP 桥——那条路容易碰到"未找到服务实现类"或
登录失效）。**必须显式传完整时间区间**：默认空参数只回溯"今天"，会静默漏掉全部历史存量记录且跑完
不报错，"跑完没报错"不能作为历史数据已更新的验证信号（2026-09-11 案例用的是 `20260815`~`20260908`）。

## 4. 验证

1. DB：重跑「排查.sql」第1步的分层分布，确认高危占比回落。
2. ES：查 `ads_large_subclazz_user_index`，确认与 DB 一致（走 `es-apply` skill，**PROD ES 不能用
   es-aliyun MCP**）。
3. 两边不一致说明同步链路有问题（`DwsRefundIntentConsumer`），不是阈值问题。

2026-09-11 参考值：补配置+回溯后，高一数学班从 110 人 92 高危 → 97 人 8 高危，DB 与 ES 一致。

配置读取有 **300 秒本地缓存**，改完配置后立即验证会读到旧值，等 5 分钟。

依赖的全局 skill：`xjob-admin`（查/触发 job）、`mysql-query`（查配置与结果）、`pod-terminal`
（arthas 回溯）、`es-apply`（查 PROD ES）。

## 5. 「低危」占比反常地高，是不是又出问题了

跟第 1 步「高危畸高」相反的症状：某个组合补完配置后，几乎所有学生都被判「低」，只有极少数是
中/中高/高。**先看 `intent_config` 里「低」那一档的区间宽度**，不要直接怀疑算法模型：

```sql
SELECT grade, student_type, prediction_level, COUNT(*) cnt,
  MIN(prediction_score) min_score, MAX(prediction_score) max_score
FROM ees_data.ai_refund_prediction_results
WHERE clazz_number = <x> AND stage = '<stage>'
GROUP BY grade, student_type, prediction_level;
```

若某一档（通常是「低」）的 `min_score`~`max_score` 横跨一个远超其他档位的区间（例如 0~0.70，
而「中」「中高」「高」加起来只占 0.70~1 这一小段、且命中人数个位数），说明 `predict_intent_config`
里这一档的阈值区间本身设得过宽，跟第 1 步「补完配置要顺手验一件事」提到的「区间宽度为 0」是
**同一类问题的另一种表现**——都是算法侧分位点计算可能有问题，不是「配置补上了就一定没事」。
命中就反馈算法侧确认这批阈值是否符合预期，不要当成新 bug 去查代码。

2026-09-15 案例：高考地理决胜班（H业务线/精品班学部/stage=4/高三）新生的「低」档横跨
`0.0002~0.7034`（931/938 人落在这一档），远宽于 stage=2/3 时「低」档只到 0.22 左右的量级，
判定为同类阈值质量问题，已反馈算法侧。

## 6. 花名册跟退费看板（或其他报表页面）数字对不上

**根因是两边统计的人群范围本身不同，不是 bug、不是没刷新**。排查时会先怀疑"看板数据滞后"，
这个方向**不完全对**——job 很健康、重新单独触发也不会让数字变化，因为两边查的就不是同一批人：

| | 花名册 | 退费看板 |
|---|---|---|
| 数据来源 | 实时查 ES `ads_large_subclazz_user_index`（`aiRefundIntentScoreResult`） | 定时快照表
`subclazz_refund_process_snapshot`（Doris/SelectDB，cluster_id=460，`student_data_renewal` 库），
由 `RefundDashBoardHandler`（job_id=10099，prod jobGroup=314，cron 每 2 小时一次）查同一个 ES
聚合后写入 |
| **人群口径**（差异根源） | 严格 `clazzStudentStatus=1 且 subclazzStudentStatus=1`（即
`StudentSubStatusEnum.IN_IN`＝"在读且本人辅导班"） | `RefundDashBoardHandler.java` 里是
`must_not`（`clazzStudentStatus=1 且 subclazzStudentStatus=2`，即 `IN_OUT`＝"在读非本人辅导班"），
**只排除这一种组合，其余全算**，包含 `OUT_OUT`（退款）等花名册严格口径不算的人；另外还叠加了
排除 `internalStaffFlag`（内部员工测试账号）、`checkChangeClazz`（变更班级中）等花名册没有的
过滤条件 |
| 看历史 | 不支持，只有当前 | 有「查看日期」筛选，选中某天 = 看那天**冻结**的快照 |

排查顺序（按耗时从低到高排）：

1. 先查 job 10099 是不是健康在跑（`xjob_list_jobs -k job_id=10099` 看 `triggerStatus`，
   `xjob_job_logs -k job_id=10099` 看最近几次 `handleCode`）——健康就不是 job 挂了。
2. 确认看板界面「查看日期」选的是不是今天，不是就切到今天再比一次。
3. **日期也对、job 也健康，数字还是差很多** → 别再怀疑"没刷新"，直接去查两边的 ES 查询条件
   差在哪（花名册走 `RefundIntentInfoQueryServiceV2`/roster 接口的过滤逻辑，看板走
   `RefundDashBoardHandler#buildEsQueryRequest`），大概率是人群口径不同，不是同一个问题。
   验证方法：拿花名册严格口径（`clazzStudentStatus:1 AND subclazzStudentStatus:1`）跟看板口径
   （`must_not clazzStudentStatus:1 AND subclazzStudentStatus:2`）分别查 ES 聚合对比，数字会大幅
   跳变（本案例从个位数跳到几百），就是口径问题实锤，不用再往"回溯/同步链路"方向查。

2026-09-15 案例：高考地理决胜班（clazzNumber=545524684567900160）花名册显示
0 高/3 中高/6 中/1768 低（对应 ES 严格口径实测 0/2/3/1770，总 1778，跟花名册基本一致，
**花名册本身没问题**）；退费看板今天(9/15)的快照显示 高/中高/中 合计 129+132+74=335（在班 1753）。

排查过程：
1. 先怀疑"看的是历史日期"——查到 9/11~9/15 每天的快照确实在逐日下降（1714→1324→1231→440→129），
   证明回溯在生效，但**今天的快照(335)跟今天的花名册(9)还是对不上**，排除"选错日期"这个解释。
2. 怀疑"快照没刷新"——手动单独触发 `xjob_trigger_job job_id=10099 executor_param=[545524684567900160]`
   针对这一个班重新跑一次（`handleCode=200`，几十秒内跑完），重新查 Doris 快照表，**数字完全没变**
   （还是 129/132/74/1891，只有 `update_time` 变了）。证明不是没刷新。
3. 去读 `RefundDashBoardHandler.buildEsQueryRequest`（`student-data-facade/.../job/dashboard/RefundDashBoardHandler.java:1532-1546`）源码，发现人群过滤是 `must_not IN_OUT` 而不是花名册的
   `must IN_IN`，范围完全不同。
4. 用看板同款口径重新查 ES：`clazzNumber` + `must_not(clazzStudentStatus:1 AND subclazzStudentStatus:2)`，
   总人数 2522、高危相关(中+中高+高)合计 426——**跟看板的 335/1753 已经是同一量级**，
   跟花名册严格口径的 5/1778 相差近百倍。差的这点尾差（426 vs 335）大概率是
   `internalStaffFlag`/`checkChangeClazz` 等看板还叠加的次要过滤条件，不再深挖。

结论：**花名册和退费看板都没有 bug，两者反映的是同一份 ES 数据在两种不同人群口径下的结果**。
业务侧如果想让两个页面看起来"对得上"，需要产品侧决定统一口径，这不是 EES/代码能单方面"修好"的。

不属于本案例范围：`feature-predict-level-reason` 重构分支是另一套逻辑；两次事故都发生在
**重构前的旧逻辑**上。
