# 续班看板指标 · 小组长列出现虚拟架构里没有的组

> **只解决**：过程数据排名"小组长"列出现了业务认为不该有的"独立小组"——某人（如组内战队长）被当成小组长，而业务在 OES 虚拟架构里找不到以 TA 命名的组。
> 同类现象若出现在**"小组长+1"列**（某人只是小组长却上了 +1 榜），走 [`小组长+1榜里出现小组长.md`](小组长+1榜里出现小组长.md)，与本文件互不覆盖。

## 判定入口

"小组长"列不是手工指定，而是**取该二讲所在虚拟组织节点的负责人**：

- 代码：`student-data-facade` 的 `RenewalDashBoardHandler`，`getStaffListLeadersByTypeDTOMap()`（约 961-985 行）→ `staffFeignClient.listLeadersByTypeBatch()`，`leaderTypes` 取 Apollo `renewal.plan.dashboard.leaderTypes:[2,1]`（实线 2 在前、虚线 1 在后）。
- 去重规则：同一位二讲返回多条候选人时**只留一条**——有实线(2)则保留实线；两个都是虚线(1)时**保留接口里靠后返回的那条**（`Collectors.toMap` 的 merge 函数 `existing.getLeaderType()==2 ? existing : replacement`）。
  - 后果：一个节点若挂了**多个虚线负责人**（如「组长 + 组内战队长」），取到哪个**取决于接口返回顺序**，不是稳定的"组长"。

看板把它显示成"独立小组"，是因为排名按 `group_leader_name` 聚合；而该人的 `group_leader_plus_name` 走的是另一套数据（CAS/PS 上级，见 `小组长+1榜里出现小组长.md`），若恰好是组长，就会呈现"某人一行、+1 是组长"的样子。

## 排查

1. 先看板把谁当成了小组长、挂在哪个节点（SelectDB，表 `student_data_renewal.sub_clazz_renewal_process_snapshot`）：

```sql
-- 某人作为小组长挂在哪个节点、+1 是谁
SELECT DISTINCT group_leader_name, group_leader_number, group_leader_plus_name, group_leader_org
FROM sub_clazz_renewal_process_snapshot
WHERE group_leader_name = '<姓名>';

-- 该节点下所有二讲实际被算到谁名下（对齐某天榜）
SELECT snapshot_time, group_leader_name, group_leader_plus_name, COUNT(*) cnt, SUM(can_renewal_count) can_renewal_sum
FROM sub_clazz_renewal_process_snapshot
WHERE group_leader_org = '<org_number>' AND snapshot_time = '<yyyy-MM-dd> 00:00:00'
GROUP BY snapshot_time, group_leader_name, group_leader_plus_name;
```

2. 看该虚拟架构节点有几个负责人（student-data 同步表 `ees_data.virtual_employee_info`；`is_owner` 1=虚线 2=实线，`job_type` 1=主岗 2=兼岗；**`org_number` 无索引，按 `email_prefix` 查**）。命中同一 `org_number` 的**多条 `is_owner=1`** 即"多虚线负责人"：

```sql
SELECT account_id, email_prefix, full_name, job_type, is_owner, org_number
FROM virtual_employee_info WHERE email_prefix IN ('<前缀1>','<前缀2>') AND isdel = 0;
```

3. 复核看板实际取到的负责人（staff 实时接口，无缓存）：走 `baijia-invoke` 调 `com.gaotu.staff.feign.StaffFeignClient#listLeadersByTypeBatch`，body `{"accountIds":[<该节点某二讲 accountId>],"leaderTypes":[2,1]}`（线上用 `traffic_env=prod`）。返回**多条** `leaderType` 即印证节点有多个负责人。

OES 侧背景：`虚线汇报` 是 staff 域的关系（知识库「组织架构」页：`/staff/add|delete/leader.do`、`staff_organization_relation`，type 区分成员/实线/虚线），**一个节点可以挂多个虚线负责人**——所以"OES 里没有某人的组"和"某人是某节点的虚线负责人"可以同时成立。

## 验证

- **不是"看板算错"**：`listLeadersByTypeBatch` 对该节点二讲确实返回多个 `leaderType=1`，"小组长"只取其一属实现口径；排名忠实取 staff 的负责人。
- **想让它显示组长**：要在 **OES 侧**改该节点配置（只保留/指定一个负责人，或给战队长单独建子节点），或在 student-data 明确"多虚线负责人"时的取值规则——属业务口径决策，重算数据解决不了。
- 改 OES 后**下一轮** `RenewalDashBoardHandler` 即生效（staff/CAS 均拉取式无缓存，非 T+1）；但历史快照行的组织列会被 `RenewalDashBoardUpdateHandler` 刷成最新、量化指标不动，见 [`小组长+1榜里出现小组长.md`](小组长+1榜里出现小组长.md) 的「历史数据会不会被改」。
