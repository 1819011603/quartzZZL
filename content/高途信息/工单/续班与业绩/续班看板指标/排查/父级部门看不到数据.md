# 续班看板指标 · 父级部门行看不到数据（组织列只取最深节点）

> **只解决**：业务在虚拟架构里配好了某个**上级/父部门**、也设了（虚线）负责人，但续班过程数据/续班看板里这个部门**行是空的**——而它在组织树上明明是个"有人的节点"。
> 看板指标数值算错（意向率、可续量）走其它 runbook；"小组长"列出现虚拟架构里没有的组走 [`小组长列出现虚拟架构里没有的组.md`](小组长列出现虚拟架构里没有的组.md)，与本文无关。

## 判定入口

续班过程数据/看板的组织维度，取的是**每个带班二讲 / 小组长的「主岗虚拟组织路径的最深节点」**，**不向父级汇总**。

- 代码：`student-data-facade` `RenewalDashBoardHandler`，`setSnapshotValues` 里 `snapshot.setAssistantTeacherOrg(getLastOrg(renewalInfoVo.getAssistantMainPostTag()))`（约 933 行）；小组长同理由 `getLastOrg(organizationListByOrgNumbersDTO.getPathFromRoot())`（约 746 行）。
- `getLastOrg`（约 257 行）把 `pathFromRoot` 按 `_` 拆开、**只取最后一段**。

所以一个"父节点"（如「沪浙本地化」）只有在**它正下方直接挂了带班二讲/小组长**（该人的主岗路径最深节点就是它本人）时才有数；人挂在它的下级节点时，数据落在下级节点行，**父节点行恒为空**。数据没丢，也不是算错。

## 排查

1. 确认这棵子树里到底有没有带班二讲（Doris 快照 `student_data_renewal.sub_clazz_renewal_process_snapshot`；二讲组织列存的是**组织 ID**，不是名字）：

```sql
SELECT assistant_teacher_org, COUNT(*) c, SUM(can_renewal_count) s
FROM student_data_renewal.sub_clazz_renewal_process_snapshot
WHERE snapshot_time = '<yyyy-MM-dd> 00:00:00' AND assistant_teacher_org LIKE '<父节点ID前缀>%'
GROUP BY assistant_teacher_org ORDER BY s DESC;
```

命中行 = 该子树里真正带班、且已记到快照上的节点。若命中行**都不是父节点本身**，父节点行为空就是口径所致，不是数据缺。

2. 把命中的组织 ID 解析成名字/路径（staff，acl 桥；线上 `traffic_env=prod`）：

`com.gaotu.student.data.client.acl.OrganizationSyncAclService#listByOrgNumbers`，入参 `[["<orgId>"]]`（**ID 传字符串**，否则精度截断），返回 `orgName` / `parentOrgNumber` / `pathFromRoot` / `orgNamePath`。

## 让父节点行显示数据的两条路

- **改组织（不改代码，下一轮 job 生效）**：把该子树里的带班二讲/小组长**主岗虚拟组织**直接上提到目标节点（其主岗路径最深节点 = 目标节点，不在其下再挂一层）。注意：只能调到目标部门本身、不能调到别的部门；只动**主岗**——只加虚线负责人不会改变组织归行。
- **改代码 / 数据集**：把报表或数据集的「N 级部门」维度从"取最深节点"改成"按虚拟组织路径第 N 级**向上汇总**"（父级汇总子级），改完即生效。具体改哪一层（student-data 快照出维度、还是数分侧数据集）需先确认该报表归属。

> **改了虚拟组织后要"回溯"/刷历史组织列，跑 prod xjob `9745`「续班看板_更新」（`RenewalDashBoardUpdateHandler`，cron `0 0 0/1 1/1 * ?`）**：它把最新组织列回写到该辅导班的**全部历史快照行**（`UPDATE ... WHERE sub_clazz_number=?`，不带 `snapshot_time`）。触发 `xjob_trigger_job job_id=9745`（入参留空 = 全部在窗续班计划；带 `[续班计划id,...]` JSON 数组则只跑这些计划）。
> 当天行由主任务 `9744`「续班看板」（`RenewalDashBoardHandler`，`0 0/5 * * * ?`）重算，组织变更后一般**下一轮自动生效**，无需手动跑 9744；`9745` 管的是**历史行**（当天 vs 昨天的组织列差异回写）。

## 验证

- 父子关系：快照命中 org 的 `parentOrgNumber`（staff 解析）等于父节点 ID ⇒ 印证"人挂在子节点、父级行为空"。
- 改组织后查快照：**当天行**等主任务 `9744`（`RenewalDashBoardHandler`，prod `0 0/5 * * * ?`）跑完即出现；**历史行**的组织列由 `9745`（`RenewalDashBoardUpdateHandler`）刷成最新（见 [`小组长+1榜里出现小组长.md`](小组长+1榜里出现小组长.md) 的「历史数据会不会被改」）——量化指标历史行不变，只有组织/人员列变。
- **历史行刷新的前提**：`9745` 只按「当天快照 vs 昨天快照」的组织列差异回写，所以得先让 `9744` 产出最新当天快照，再跑 `9745` 才有得刷。
