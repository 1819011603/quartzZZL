# 续班看板指标 · 续班过程看板的日数据从哪取（能否带主讲维度导出）

> **只解决**：想拿「续班过程看板」的数据（可续学员量、预报名意向收集/报名/考虑/不报名等）做导出/对表，尤其要带 **学年学季 / 科目类别 / 年级 / 学科 / 主讲** 维度的**按天**数据——数据源在哪、**ES 能不能直接拿**、要不要建新表。
> 「可续学员量」当天一直变走 [`可续人数为什么一直在变化.md`](可续人数为什么一直在变化.md)；与数分（大航海）对不上走 [`可续学员量与数分报表对不上.md`](可续学员量与数分报表对不上.md)；「不报名意向率」偏高走 [`不报名意向率异常虚高.md`](不报名意向率异常虚高.md)。

## 一句话结论

**看板数据源不是 ES，也不需要建新表**：续班过程看板读的是 student-data 的 Doris 快照表 `student_data_renewal.sub_clazz_renewal_process_snapshot`；它由 xjob `RenewalDashBoardHandler` 从 ES `ads_large_subclazz_user_index`（学员粒度）聚合 + 外部补全后写入，**已带主讲/学年/学期/学科/年级/科目类别维度和全部看板指标，且按天留存**。要导出直接查这张 Doris 表即可。

## 数据链路（谁写、写什么）

1. xjob **`RenewalDashBoardHandler`**（student-data-facade，prod 每 5 分钟）：
   - 以 ES **`ads_large_subclazz_user_index`**（学员粒度）按 `subclazzNumber × assistantAccountId(二讲) × roundIdx(轮次) × studentTypeWithSubject(学员类型+学科)` 聚合指标：`canRenewal∈{1,2,8}` 计数（可续学员量）、`preRegistrationIntentKey`（报名/考虑/不报名/未填写）各计数、`presaleStatus≠0` 的预报名量；
   - **外部补全维度**（`getSnapshotExternalInfos`）：学年/学期/学科/年级/科目类别 ← course-center `CourseDO`；**主讲 ← `ClazzLessonService.listClazzLessonFullIndex`（班级主讲）**；二讲/小组长/组织 ← staff / medusa / CAS；
   - 写 **Doris `student_data_renewal.sub_clazz_renewal_process_snapshot`**（`snapshot_time` 只到天＝当天 0 点，同一维度当天每次重跑覆盖；跨天累积成日历史）。
2. 看板展示 = 该快照表按 `snapshot_time` 当天、同维度/轮次的 `SUM`。

## ES 能不能直接拿？（关键判断）

- ES `ads_large_subclazz_user_index` 是**学员粒度**，聚合只用 `canRenewal`、`preRegistrationIntentKey`、`presaleStatus`、`roundIdx`、`studentTypeWithSubject`、二讲（`assistantAccountId`）等字段；
- **主讲 / 学年 / 学期 / 学科 / 年级 / 科目类别 不在 ES 里**——这些是 handler 从 course-center、clazzLesson 外部补的（见上）。**所以纯 ES 聚合拿不到主讲维度**；要主讲维度必须复用 handler 的补全链路（course-center `ClazzLessonFullIndex` + `CourseDO`），或直接消费快照表。

## 怎么取（只读）

```sql
-- prod Doris（mysql_query table=student_data_renewal.sub_clazz_renewal_process_snapshot）
SELECT snapshot_time, school_year_name, term_name, course_category, grade_name, subject_name, main_teacher_name,
       SUM(can_renewal_count)                       AS can_renewal_cnt,
       SUM(pre_registered_intent_filled_count)      AS intent_filled_cnt,
       SUM(pre_registered_intent_sign_up_count)     AS intent_signup_cnt,
       SUM(pre_registered_intent_not_sign_up_count) AS intent_not_signup_cnt,
       SUM(pre_registered_intent_consider_count)    AS intent_consider_cnt,
       SUM(pre_registered_presale_count)            AS presale_cnt
FROM student_data_renewal.sub_clazz_renewal_process_snapshot
WHERE snapshot_time BETWEEN '2026-10-01 00:00:00' AND '2026-10-30 00:00:00'
GROUP BY snapshot_time, school_year_name, term_name, course_category, grade_name, subject_name, main_teacher_name;
```

## 口径 / 注意点

- **"每天的值"= 当天最后一次 5 分钟重算**（≈23:55），不是精确 24:00 秒级落点；与看板同源，故与看板一致。
- 快照本身粒度含 **二讲（`assistant_teacher_*`）、轮次（`round_idx_name`）、学员类型（`student_sub_type_name`）**；要按需求方口径（学年学季/科目类别/年级/学科/主讲）汇总，需按这些列 `GROUP BY` 求和，并确认轮次要否分轮。
- 日历史保留：实测 2026-10-17 ~ 10-30 每天都有行（每天 ~4 万行、主讲课 ~610–660 个）。job 只处理续班窗口内的计划，但历史行仍在表里。
- 快照里 `main_teacher_name` 可能多值（逗号拼接，如 `马旭悦-运营3,马旭悦`）、`grade_name` 多值（逗号拼接，且有"高中预科/初级 高一→初三"的特殊改写，见 `specialDealWithSnapshot`）——按主讲去重/归并时注意。

## 验证

- 快照表某天同维度 `SUM(can_renewal_count)` 与看板同筛选当天数字一致；
- 需求方只要"带主讲维度的日数据"→ 跑上面 SQL 能直接出，**不需要新表**；若坚持要精确 24:00 点、或要独立数据集/导出态，才需另立新需求。
