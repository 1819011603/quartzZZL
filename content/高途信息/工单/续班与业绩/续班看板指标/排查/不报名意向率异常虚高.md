# 续班看板指标 · 不报名意向率异常虚高

> **只解决**：续班看板"不报名意向率"这个展示指标偏高（含 100%）的归因排查。
> 学员个体的续班问卷状态字段本身对不对，走 [`../../续班问卷状态/排查/问卷已提交但花名册显示未发送.md`](../../续班问卷状态/排查/问卷已提交但花名册显示未发送.md)，与本文无关——两者字段不同，不要混。

## 判定入口

"不报名意向率"在 SQL 里是残差，不是独立统计的指标：

```
不报名意向率 = 1 - 考虑意向率 - 预报名意向率
```

它 = 100% 只有一个数学含义：已填意向数 > 0，且"考虑数"和"预报名数"都是 0（不是分母为 0——分母为 0 是 `0/0=NULL`，报表显示空白，不会是 100%）。

## 排查

代码在 `student-data-service` 的 `RenewalIntentInfoServiceImpl#resolvePreRegistrationKeyByConfigType`（`configType=2`，"意向科目"口径）：

1. **该口径下"考虑"分支永远不会产生**：方法只会返回 `EMPTY`(未填写)/`SIGN_UP`(报名)/`NOT_SIGN_UP`(不报名)，没有 `CONSIDER` 分支——"考虑意向率"在这套口径下恒为 0，指标退化成 `1 - 预报名意向率`。
2. **`clazzSubjectId` 解析失败时整班兜底判"不报名"**（这是最致命的一条）：`if (clazzSubjectId == null) { return NOT_SIGN_UP; }`——不是跳过、不是未填写，是**直接判成不报名**。
3. `clazzSubjectId` 的解析链路：班级 → 课程 `subjectId` → 字典科目名 → Apollo `question.course.subject.mapping`（namespace `application`）→ 字典 code。任何一环断掉（尤其是科目名没配进 Apollo 映射）就是 null。
4. 排查时先查 Apollo 现状：`apollo_get_key(app_id=student-data, env=PROD, key=question.course.subject.mapping)`，看报表里出问题的科目名是否真的不在这份映射里——**注意这份映射会被人工持续补充，历史分析报告举的具体科目例子可能已经过时**（映射后补上了），不能只看报告结论就直接下"需要补映射"的判断，要先读现状。
5. 如果 Apollo 映射确实缺失，补上对应科目名 → 中文标准科目名的映射即可；但即便补齐了当次已经产出的看板快照数据也不会自动回刷，需要另外触发 `RenewalDashBoardHandler`（job_id 见 xjob-admin，`jobDesc` 含"续班看板"）重算，或等下一次自动调度周期（该 job 默认每 5 分钟跑一次）。
6. 更根本的修法（截至 2026-09-28 尚未实施，需要跟需求方确认口径）：要么把"不报名意向率"改回用 `pre_registered_intent_not_sign_up_count / filled` 直接计算（不再用残差），要么在 `configType=2` 口径里补上"考虑"这个分支。这是设计缺陷，不是简单的配置补漏。

## 验证

- 确认某个具体班级/科目命中兜底分支：查该班课程的 `subjectId` → 字典科目名 → 是否在 Apollo 映射里能查到；查不到就是命中点。
- 应用日志里 `RenewalIntentInfoServiceImpl` 相关的科目名解析会打 info（成功）或不打（失败静默 null），失败没有专门的 error 日志，只能靠"查不到映射"这个事实反推，不要指望日志能直接报错。
- 补映射后要等看板 job 下一轮跑完（或手动触发一次）才能在页面上看到指标变化，不要补完 Apollo 立刻去看页面就下"没生效"的结论。
