# 续班看板 · 预报名状态延时 排查链路（runbook）

> **只解决**：belong 预报名大盘 `P99(90)预报名状态延时` 飙高时，**怎么从大盘一步步定位到具体是哪一段/哪个 MQ**。
> 指标口径与面板清单见 [`../看板与指标清单.md`](../看板与指标清单.md)。

## Step -1 前置：先确认「预报名关系」有没有配（否则不是延时，是压根没数据）

「预报名情况 / `presaleStatus`」依赖 course-center 的**预报名关系**（`course_relation_map.calculate_renewal_type = 2`）。
**关系没配时 `StudentPresaleConsumer` 算不出预报名记录、字段本就不更新**，此时别走本文的"延时/堆积"排查：

- 该班课程号 → 查 `course_center.course_relation_map`，是否存在 `calculate_renewal_type = 2`（1=续班关系/计算可续，2=预报名关系）。
- 关系从续班→预报名**改配置本身不触发重算**：存量学员要等下一次进/退班事件，或手动回溯。
- 2026-10-30 案例：老师反馈"预报名情况延时非常久"，实为**预报名关系未配置**；`renewal.course.cache.seconds` 缓存的续班关系与之**无关**（预报名链路走的是不缓存的 `getPreCourseByNumber`/`getPostCourseByNumber`）。

## 结论先给

- 北极星指标 `P99(90)预报名状态延时` = **端到端**延时：`ES save − 上游消息 born`（不是 ES 调用耗时）。
- 2026-10-29 00:18 的尖峰（51429ms）**全部是 MQ 排队**：消息在
  **topic `gaotu_subclazz_student_event_prod` / 消费组 `GID_student_data_dws_subclazz_student_presale_prod`（`StudentPresaleConsumer`）里排了 ≈56s**，本机处理仅 0.3s。
- 阿里云细粒度实锤：该组 `ready_and_inflight` 峰值 **57008 @00:18**（`ready` 单看仅 ~130 → inflight/顺序排队）。
- **不是** ADS topic（堆积≈0）、**不是** ES（同库 `renewalStateStatus` 同期 ~523ms 正常）。

## 排查链路（按顺序，可复用）

### Step 0 现象
belong `https://belong.baijia.com/pre-signup` → 卡片「P99(90)预报名状态延时」飙高（参考线 5000ms）。

### Step 1 拿到指标口径（Grafana）
- **最快**：belong 卡片自带 `jumpLink`，**点/右键卡片**直接跳到对应 Grafana 面板（如 EES 卡片 → `/d/fFQ7RPCNz/...?orgId=24`），拿到 `/d/<uid>/` 即可。
- 或抓包：belong 是壳，面板来自 `sre-grafana.baijia.com`。浏览器 DevTools → Network 过滤 `sre-grafana`，抓 `GET /api/dashboards/uid/<uid>`（面板定义）与 `POST /api/ds/query`（数据）。
- 「预报名状态延时」在面板 uid `wXhDkxZDk`，expr：
  ```promql
  1000*histogram_quantile(0.8, sum(rate(
    student_data_es_upsert_time_seconds_bucket{
      index=~'ads_large_subclazz_user_index', monitorKey=~'presaleStatus',
      environment="prod", result='true'}[1m]
  )) by (le,index,monitorKey))
  ```
- 命令行走 `chrome-devtools list_network_requests <pageId> --resourceTypes xhr` + `get_network_request <pageId> --reqid <n>`。

### Step 2 读埋点，纠正口径（关键，别想当然）
- `AdsSubclazzUserSyncService.java:412`：`esSaveTime = System.currentTimeMillis()`（在 ES `update()` 之后）；
- `:242`：`currentTimeMillis` 取自**消息体** `CURRENT_TIME_MILLIS`；
- 计时值 = `esSaveTime - currentTimeMillis` → **端到端**，不是"ES upsert 调用耗时"。
- 上游打点：`PresaleSubjectServiceImpl.sendSubclazzStatusUpdate`（`:741-759`）写入 `monitorKey="presaleStatus"`、`CURRENT_TIME_MILLIS=messageBornTime`。

### Step 3 找上游链路
- 该消息 tag = **`renewal_user_clazz_tag`**；消费方 `AdsSubclazzUserSyncConsumer`（ADS topic）；
- 再上游 = `StudentPresaleConsumer`（消费 `gaotu_subclazz_student_event_prod`，tag Enter||Quit），它把 roster 消息的 `bornTimestamp/startDeliverTime` 透传进 ADS body。

### Step 4 排除 MQ/ES（用"就绪+处理中"和对照指标）
- ADS 组 `GID_student_data_ads_subclazz_user_ordered_prod` ready 堆积≈0 → ADS 不是。
- EES 面板（`sre-grafana.../d/fFQ7RPCNz`，orgId=24）对照：`presaleStatus` p80–p97 **60000ms 顶格**，但 `renewalStateStatus` 同期 **~523ms** → 只有 presale 链路异常，**排除全局 ES**。

### Step 5 单条消息逐跳（最快，无需 Grafana/消息详情）
- SLS `queryStr="renewal_user_clazz_tag"`，取该窗日志；生产者 `FuwuOnsMqProducer#sendOrderedMessage success ... body is {...}` **把 body 打进日志**，body 含
  `currentTimeMillis`(上游 born) / `messageStartDeliverTime` / `messageBeginHandleTime` / `messageEventTime`。
- 解析：`born→startDeliver` 与 `handle→send`。实测 00:18 那批：**56.5s / 0.3s** → 全在排队。

### Step 6 阿里云监控坐实（细粒度，别用默认 10min）
```bash
./mcpcli.py aliyun_console ons_group_backlog_curve \
  -k instance_id=MQ_INST_1941505946323830_Bay8En7I \
  -k group_id=GID_student_data_dws_subclazz_student_presale_prod \
  -k region=cn-beijing -k hours=12 -k step_seconds=60 -k metric=ready_and_inflight
```
- 结果：**57008 @00:18**（00:17=24781、00:19=52543、00:20 回落），`ready` 单看仅 ~130。

## 判据与坑

1. **`ready` 会骗人**：顺序消费(FIFO) 的积压主要在 `inflight`（已投递、串行处理中），`ready` 很小甚至为 0；判堆积要看 `ready_and_inflight`。
2. **默认 10 分钟粒度会漏尖峰**：`rocketmq_consumer_ready_messages` 600s 采样，1 分钟尖峰被抹平；查尖峰用 `step_seconds=60`。
3. **别把"端到端指标"当"ES 调用"**：`student_data_es_upsert_time_seconds` 起点来自消息体 `CURRENT_TIME_MILLIS`，含排队。
4. **别查错 ES 实例**：`ads_large_subclazz_user_index` 走 `eesServeClient`（`ees.serve.es.cluster.host`，是另一个集群），不是用户默认给的实例。
5. **TID 内嵌生产时间**（形如 `svc.seq.<epoch10位>...`）可快速算"消费开始 − 生产"= 排队时间。
6. **消息体自带各跳时间戳**是逐跳归因的最快路径（生产者日志 `FuwuOnsMqProducer` 会打印 body）。
7. **并发度 = 分区数**：该 topic 单 broker 8 队列 × 15 broker = **120 分区**（`ons_group_queue_backlog` 数 distinct `queue_id`）；`StudentPresaleConsumer` 是**顺序消费每分区串行**，所以并行上限 = 120，**加线程无用**（`consumeThreadNums` 只对并发消费有效），只能加分区（重建 topic）或加实例覆盖全部分区。
