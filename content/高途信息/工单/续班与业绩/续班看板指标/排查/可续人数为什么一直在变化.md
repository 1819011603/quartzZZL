# 续班看板指标 · 看板「可续学员量」当天一直在变（涨 / 小幅跌）

> **只解决**：续班服务-过程数据（续班过程看板 / 预报名看板的分母）里的"可续学员量"在**同一天内不同时刻**看会变（涨、或小幅跌几个/十几个），业务反复问"为什么一直在变 / 是不是又算错了"。
> 「可续学员量」与数分（大航海）**数字对不上**走 [`可续学员量与数分报表对不上.md`](可续学员量与数分报表对不上.md)；「小组长+1」归属走 [`小组长+1榜里出现小组长.md`](小组长+1榜里出现小组长.md)；「不报名意向率」偏高走 [`不报名意向率异常虚高.md`](不报名意向率异常虚高.md)。这几件事同一张快照表，但问题不同。

## 一句话结论

可续**不是一份存下来的固定名单**，而是判单（业绩归属 performance-attribution）**实时判出来、并且每天整体重算**的状态；续班看板的 xjob `RenewalDashBoardHandler` 每隔几分钟读一次 ES 的**当下值**去重算"当天"那一行快照。所以只要当天有人被改判（新判单命中、退款、调课、重新报名……），看板数字就会跟着变。**这是预期行为，不是算错**，不要指望它当天是一个不动的数。

## 链路：谁把"可续"改了，看板怎么跟着变

1. **判定方 = performance-attribution（判单 / 业绩归属）**。可续 = 某个学员在某订单上的状态，取值 `CanRenewalStatusEnum`；**计入"可续"的只有 `{1,2,8}`**＝ 1 可续-未续 / 2 可续-已续 / 8 可续-后置课程退款（`canRenewal` 字段写的就是这个 code）。
   - **每天凌晨一轮整体重算**：xjob `RenewalOrderSyncHandler`（可续配置同步）、`RenewalOrderSignHandler`（可续标记）、`RenewalOrderCorrectHandler`（可续修正：调课 / 退款修正）。重算按订单号**先删后插**写 `gaotu_stat.performance_regular_can_renewal_sign_x`（`RenewalSignRegularStrategy#saveRenewalSign`，约 283–299 行），所以该表是"当前状态表"，不留历史。
   - **事件实时改判**：支付判单、退款、调课、重新报名等都会即时改状态（判单侧 `CanRenewalServiceImpl` 单订单重算）。
   - 每次状态**有变**（新增 / 删除 / 改状态）就发 MQ `CanRenewalSignMsgEvent`（topic `gaotu_performance_renewal_prod`，tag **`canRenewalChangeEvent`**，只发变化量）。
2. **同步方 = student-data 消费该消息，把新状态写进 ES**（同一 tag 两个消费组，分别处理大班 / 小班）：
   - 大班 / 长期班：`AdsCanRenewalSyncConsumer`（student-data-dws）→ 写 `ads_large_subclazz_user_index` 的 `canRenewal` / `roundIdx`（看板读的就是这张表）；
   - 小班：`OdsSmallCanRenewalSyncService`（student-data-facade）→ 写小班课学员索引的 `smallCanRenewal` / `smallRoundIdx`。
   - 两个消费者都开了 `useExternal`：拿到消息后会**再回查上游拿最新值**再落 ES，避免用事件里可能偏旧的值。
3. **展示方 = xjob `RenewalDashBoardHandler`**（student-data-facade，prod cron `0 0/5 * * * ?`，即**每 5 分钟**）滚动聚合 `ads_large_subclazz_user_index` 上 `canRenewal ∈ {1,2,8}`、排除内部员工（`internalStaffFlag` 不存在或 =0）的文档数，写 Doris `student_data_renewal.sub_clazz_renewal_process_snapshot`。**每条记录的 `snapshot_time` 恒为当天 0 点，同一维度当天只维护一行、每次重跑覆盖它**——所以"当天"的数字每次重算都可能变（页面每 5 分钟刷新就能看出来）。

## 数字会往哪变（业务常见疑问）

- **涨**：新判单命中可续 / 学员重新报名被标可续 / 当天凌晨那轮批量标记把之前漏的补上（如某次长期班标记任务跑完，看板"可续人数"当天整体上台阶）。
- **小幅跌**：退款（5 不可续-已退款）/ 过可续时间（6）/ 退班或调课后可续标记锁到旧辅导班 / 重新报名后修正 / 判单重算。
- 隔天之间的净变几个人属正常抖动；**要两边相等只能对齐"同一时刻的同一口径"**，不接受"今天和昨天必须一样"。

## 旁路：能让可续突变、且跟"判单"无关的

- **速达回溯**（`ees_data.back_quick_task` **type=13** → `quickBackAdsSubClazzUserWorker` → `AdsSubclazzUserBackService#dealClazz`）会重写 `ads_large_subclazz_user_index`，其字段清单 `ads.back.subclazz.user.fieldNames` **含 `canRenewal`**；而 `ads.back.subclazz.user.overwrite.guard.rules` 目前**只护 `renewalQuestionnaireStatus`、没有护 canRenewal**。若某班 / 某续班计划的可续**成批突变**（不是零星几个），先查这张表当天有没有覆盖到它——这类覆盖是用"某一时刻的重算值整体重写"，会把窗口内的实时变化冲掉。
- 另一个旁路：花名册/辅导班学员索引的常规 upsert 也带 `canRenewal`，但走的是字段级增量，不会成批冲。

## 怎么核对 / 定位变化来源（只读）

- **看板数字 = 快照表**：`student_data_renewal.sub_clazz_renewal_process_snapshot` 在 `snapshot_time=当天 0 点`、同维度 / 同轮次的 `SUM(can_renewal_count)`。核对 SQL 见 [`可续学员量与数分报表对不上.md`](可续学员量与数分报表对不上.md) 的「核对 SQL（SelectDB）」。
- **证明"某班今天从 X 变成 Y"**：搜 SLS `student-data` 的 `FuwuOnsMqProducer` 发送记录（topic `student_data_renewal_event_external_prod`，tags `renewal_status`，body `{"userId":…,"subclazzNumber":…,"canRenewal":…}`）；或直接查上游 `gaotu_stat.performance_regular_can_renewal_sign_x`（按 `subclazz_number`，`can_renewal_status ∈ {1,2,8}`，**`COUNT(DISTINCT user_id)`**，`round_idx` 分轮次）。
- **追"上游谁改的"**：查 `performance_regular_can_renewal_sign_x` 的当前值（= 判单此刻结论）+ 判单原因接口 `POST /performance/management/suda/performance/regular/canRenewalSignReason`。详见工单 [`../../业绩归因/排查/可续状态判不可续.md`](../../业绩归因/排查/可续状态判不可续.md)。
- ⚠️ `performance_regular_can_renewal_sign_x` **每轮签单重签覆盖**（按订单号先删后插、`create_time` 被重置），不能用 `create_time` 反推历史；要看历史只能走数仓按 `dt` 分区的表。

## 验证

- **判"是不是正常波动"**：同筛选隔几分钟截图对比，若只差几个 / 十几个、且能对上上面"涨 / 跌"的原因，即正常——看板读的就是实时 ES，`RenewalDashBoardHandler` 每 5 分钟重算。
- **实测样例（2026-10-16，续班计划 `18125077769752000`〔[2026秋] 秋季续班_精品班高三〕）**：同筛选隔几分钟截图 70201→70184；快照当天一轮合计 **70290**（≈截图，页面再排内部员工故略低）、同口径**昨日 70244**（当天净 **+46**，是涨不是跌），按班逐行只有 1 个班 -2 → 属日内抖动，不是下降趋势。
- **判"是不是被回溯冲了"**：查 `ees_data.back_quick_task` 当天有没有覆盖到该班（type=13）。
- **不算证据**：页面刷新前后数字相等（两次看的是同一个时间点）、或"昨天和今天不一样"。
