# 续班看板指标 · 小组长+1榜里出现小组长

> **只解决**：续班服务-过程数据排名里，"小组长+1"维度出现了在虚拟架构里只是"小组长"的人（用户疑问"这里是不是只该显示大组长"、"大组长那行数据包含某个小组吗"）。
> 指标数值本身算错（如"不报名意向率"异常虚高），走 [`不报名意向率异常虚高.md`](不报名意向率异常虚高.md)，与本文无关。

## 判定入口

排名的两列来自**两套不同的组织数据**，混在一起，所以"虚拟架构里是小组长"的人可能出现在 +1 列：

| 列 | 来源 | 取法 |
|---|---|---|
| 小组长 | **虚拟架构组织**（业务虚拟组织） | 二讲所在组的负责人（实线/虚线负责人） |
| 小组长+1 | **CAS 汇报关系**（= 人力 PS 上下级，**不是**虚拟架构大组） | 小组长**账号上的 `manager`** |

只要某人是某位"小组长"的 PS 直属上级，他就会作为 +1 出现——即使他在虚拟架构里也只是小组长。所以"同一人既在小组长列、又在 +1 列"是正常的。

## 排查

代码在 `student-data-facade` 的 `RenewalDashBoardHandler`：

1. **小组长**：`getStaffListLeadersByTypeDTOMap()`（约 961-985 行）→ `staffFeignClient.listLeadersByTypeBatch()`，`leaderTypes` 取 Apollo `renewal.plan.dashboard.leaderTypes:[2,1]`（实线在前）；同一二讲同时有实线/虚线负责人时保留**实线**那条。
2. **小组长+1**：`leaderAccountInfo = casAclService.batchGetAccountInfoByEmailPrefixes(...)` 取到小组长的 **CAS 账号**，`snapshot.setGroupLeaderPlusName(leaderAccountInfo.getManager())`（约 748-755 行）——**用的是账号上的 `manager`，与虚拟架构组织树无关**。
3. CAS 接入：`CasAclServiceImpl`（`/account/accountsByNames.json`，`casapi.baijia.com`），`AccountInfo.manager` / `managerId` 即该员工在人力组织（PS）里的直属上级。
4. 数据落 `sub_clazz_renewal_process_snapshot`（Doris，报表侧 `student_data_renewal.sub_clazz_renewal_process_snapshot`），按 `group_leader_plus_name` 聚合即"小组长+1"维度。

排查 SQL（SelectDB）：

```sql
-- 某人为什么出现在"小组长+1"：TA 的 +1 行里挂了哪些小组长
SELECT DISTINCT group_leader_plus_name, group_leader_plus_number, group_leader_name, group_leader_org
FROM sub_clazz_renewal_process_snapshot
WHERE group_leader_plus_name = '<姓名>';

-- 某人作为小组长所带的组，+1 是谁（判断"大组长那行是否包含该组"）
SELECT DISTINCT group_leader_name, group_leader_plus_name, group_leader_org
FROM sub_clazz_renewal_process_snapshot
WHERE group_leader_name = '<姓名>';

-- 对齐某天的榜（页面数字 = 该 snapshot_time 的 SUM(can_renewal_count)）
SELECT snapshot_time, group_leader_plus_name, SUM(can_renewal_count)
FROM sub_clazz_renewal_process_snapshot
WHERE snapshot_time = '<yyyy-MM-dd> 00:00:00' AND group_leader_plus_name IN ('<A>','<B>')
GROUP BY snapshot_time, group_leader_plus_name;
```

虚拟架构侧（student-data 同步表 `ees_data.virtual_employee_info`；`is_owner` 1=虚线负责人 2=实线负责人，`job_type` 1=主岗 2=兼岗）：

```sql
SELECT account_id, email_prefix, full_name, job_type, is_owner, org_number, org_path_name
FROM virtual_employee_info WHERE email_prefix = '<邮箱前缀>' AND isdel = 0;
```
（该表 `org_number` 无索引，按 `org_number` 过滤易超时，用 `email_prefix` 查。）

## 验证

- 同一人同时出现在"小组长"和"小组长+1"两列不矛盾：作为小组长（虚拟架构）时归到自己的 +1 名下；作为某小组长的 PS 上级时又单独成一行。
- 判断"大组长那行是否包含某小组"：看该小组二讲的 `group_leader_plus_name` 是不是这个大组长；不是就不会并进去。
- `group_leader_plus` 是 PS 上级，**不等于**虚拟架构的大组负责人；两者不一致时会看到"小组长"落在 +1 列，属口径设计，不是数据错乱。
