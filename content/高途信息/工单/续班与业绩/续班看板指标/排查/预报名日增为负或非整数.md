# 续班看板指标 · 预报名日增（率）异常：负值 / 非整数 / 与可续对不上

> **只解决**：EES「过程数据排名」BI 看板（udata `dashboard_645956959946387457`，数据源 Doris `student_data_renewal.sub_clazz_renewal_process_snapshot`）上「预报名日增」「预报名率日增」「意向收集率日增」出现**负值 / 非整数**，或业务用「可续 × 预报名率日增」去等于「预报名日增人数」对不上。
> 「可续学员量」本身当天/隔天一直在变走 [`可续人数为什么一直在变化.md`](可续人数为什么一直在变化.md)；与数分（大航海）对不上走 [`可续学员量与数分报表对不上.md`](可续学员量与数分报表对不上.md)；日数据从哪取走 [`续班过程看板数据从哪取.md`](续班过程看板数据从哪取.md)。

## 一句话结论

三条现象都**不是"预报名/退费数据丢了"**，而是同一套口径的必然结果：**可续量、预报名量、意向量都取自 ES `ads_large_subclazz_user_index` 上同一个"当前可续人群"**（`canRenewal∈{1,2,8}` 且非内部员工），快照每 5 分钟重算一次。人群一变（判单改判 / 调课 / 过可续时间 / 退款 / 拉黑 / 灰名单 / 重新报名…），**可续、预报名、意向一起变**。而看板的「日增」是**率差**（今日率 − 昨日率，单位 %），不是人数差，所以：

- **①可续隔天差几百** = 人群净变；秋续班大促期单日净变数百到上千都属正常（见下方实测）。
- **②预报名日增为负** = 有预报名的人**离开了可续人群**（他 `canRenewal` 不再是 {1,2,8}），**不需要有任何退费**；或该行人群重组（走的人带预报名、进的人不带）。
- **③非整数** = 把"率差 × 可续"当成人数：率差的分母（可续）两天不同，`可续 × 率日增` 既不等于人数差、也非整数。要整数日增人数只能用**人数差**（预报名量 − 昨日预报名量）。

## 判定入口

- 页面：EES 续班服务 →「过程数据排名」按钮；或直接 udata `//udata.baijia.com/taitan/preview.html?dashboardId=dashboard_645956959946387457&appId=EES&source=page`。页面「更新时间 …（每5min更新一次）」= xjob `RenewalDashBoardHandler`（student-data-facade，prod cron `0 0/5 * * * ?`）；过滤器字段与快照表列一一对应（课程部门/学年/学期/年级/学科/轮次/学员类型/二讲/小组长/小组长+1/续班活动名+ID/数据日期/班级/辅导班/主讲）。
- 快照表（可直接查）：`mysql_query table=student_data_renewal.sub_clazz_renewal_process_snapshot env=prod`。当天行 `snapshot_time = 当天 0 点`，同维度当天只维护一行、每次重跑覆盖；`_yesterday` 列由 `insertYesterdaySnapshotInfo` 回查昨日快照行按完整维度回填 = **昨日全天定稿值**。

## 口径（关键，决定所有指标范围）

`RenewalDashBoardHandler.buildEsQueryRequest` 的 ES 查询条件：

- `canRenewal ∈ {1,2,8}`（Apollo `renewal.plan.dashboard.can.renewal.status.list`，未配默认）；
- `subclazzNumber ∈ 本批辅导班`；
- `internalStaffFlag` 不存在或 = 0。

在该范围内聚合各指标：

- `canRenewalCount` = 命中文档数（`value_count`）；
- `preRegisteredPresaleCount` = `presaleStatus` 存在且 ≠ 0（`buildIntentPresaleFilter`，**只看 presaleStatus，不看意向**）；
- `preRegisteredIntent*Count` = `preRegistrationIntentKey` 各值。

**关键：预报名 / 意向量只在"当前可续人群"内统计**——一个学员只要 `canRenewal` 离开 `{1,2,8}`，他就算有预报名也从该行消失（为什么可续会离开：见 [`可续人数为什么一直在变化.md`](可续人数为什么一直在变化.md) 与 [`../../业绩归因/排查/可续状态判不可续.md`](../../业绩归因/排查/可续状态判不可续.md)）。

## 排查（只读）

1. **判断"负/非整数本来就正常"**：看行内 `can_renewal_count` vs `can_renewal_count_yesterday`、`pre_registered_presale_count` vs `pre_registered_presale_count_yesterday`。若 `pre_registered_presale_count < ..._yesterday` 且该行 `can_renewal_count` 也降（或人群重组）→ 人群效应，与退费无关。
2. **量化当日负日增**：
```sql
SELECT snapshot_time,
       COUNT(*) rows_n,
       SUM(CASE WHEN pre_registered_presale_count < pre_registered_presale_count_yesterday THEN 1 ELSE 0 END) neg_ps_rows,
       SUM(pre_registered_presale_count - pre_registered_presale_count_yesterday) ps_delta,
       SUM(can_renewal_count - can_renewal_count_yesterday) can_delta
FROM student_data_renewal.sub_clazz_renewal_process_snapshot
WHERE snapshot_time IN ('<T-1> 00:00:00','<T> 00:00:00')
GROUP BY snapshot_time;
```
   实测（2026-11-01 全量）：负预报名日增的行 2133 行，这些行 `can_delta` 合计 −13282 → 负日增与人群缩水强相关。
3. **验证"率差 × 基数 ≠ 人数差"**：`率日增 = ps/can − ps_y/can_y`；`人数差 = ps − ps_y`；`can × 率日增` 与人数差一般不相等、且非整数（分母两日不同）。这就是业务"可续×预报名率日增=预报名日增人数竟然非整数"的来源。
4. **排除"回溯冲数"**：查 `ees_data.back_quick_task` 当天有没有 `type=13`（`quickBackAdsSubClazzUserWorker`，会整体重写 `ads_large_subclazz_user_index` 含 `canRenewal`）。`type=15` 是小班课、与看板（大班）可续无关。

## 验证

- 行内 `..._yesterday` 与该维度上一日快照值一致（回填没错位）；
- 负日增的行确实伴随可续下降 / 人群重组，且查不到退费记录 → 人群效应成立；
- 若业务要"整数且可解释的日增人数"，用**人数差**而非率差×基数；改看板"日增"公式属 **udata / 数仓** 侧（快照表只是提供 `_yesterday` 底数），不是 student-data 缺陷。
