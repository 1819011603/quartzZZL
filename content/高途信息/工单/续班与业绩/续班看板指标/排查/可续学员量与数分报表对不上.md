# 续班看板指标 · 可续学员量与数分报表对不上

> **只解决**：续班服务-过程数据排名（辅导班维度 / 二讲 / 小组长 / 小组长+1）里的"可续学员量"（也作**预报名看板的分母**），与数分（U分析平台 / 大航海）出的"可续人次/分母"对不上（同一老师/班级两边数字不同）。
> 「小组长+1」维度归属是不是该显示大组长，走 [`小组长+1榜里出现小组长.md`](小组长+1榜里出现小组长.md)；「不报名意向率」偏高走 [`不报名意向率异常虚高.md`](不报名意向率异常虚高.md)。三者的数据源同一张快照表，但问题不同。

## 判定入口

1. **先确认两边是不是同一张表**。续班看板的"可续学员量"取 student-data 的续班快照表；数分是不是同一张表，要数分侧给出取数 SQL（可能是另一条 DWH 链路，不在 student-data）。
2. **对齐"日期 + 维度 + 轮次"再比**。续班看板数字 = 某个 `snapshot_time`（当天 0 点）的快照聚合值；跨天/跨轮次/不同筛选直接比会得到假差异。当天快照每个跑批轮都会变，页面与报告刷新时刻不同也会差。
3. 页面某维度数字 = 快照表按该维度粒度求和，见下方 SQL。

## 怎么定位两边各自的写入源（SLS 全局日志只能追"服务写的表"）

- **SLS 全局日志只能匹配到服务写入**。命中 `service=student-data` + `DorisStreamLoadGenericService` + `.../student_data_renewal/sub_clazz_renewal_process_snapshot/_stream_load`（另加 `RenewalDashBoardHandler#insert`），即可确认 `sub_clazz_renewal_process_snapshot` 是 student-data 写的 Doris 表。
- **`bdg_bi.menu_set_*` 不是服务，是 U分析数据集调度任务**：`bdg-uanalysis-intelligence` 的 `IntelligenceSchedulesService` 把数据集 SQL 发布成 nezha DW 导入任务（`publishNezhaTask` → `nezhaClient`，`DWImportTaskVO.source=bdg_bi`），表名 = `菜单库.数据集menuId_<epoch>`。执行/落库在 nezha executor(EMR)，**不在 SLS**，所以全量 app 日志搜不到写入记录。
- **Hive 表**（如 `gaotu_dw.dm_user_subclazz_regular_clazz_details`、`dw.ods_gaotu_gaotu_clazz_lesson`、`bdg_ba.dws_finance_renew_subclazz_user_addr_df`）是**离线数仓任务产出**，用天工（nezha）血缘看上下游，也不是某个 Java 服务写的。
- `temp_table.<用户名>_*` = 个人临时表，别当数据源。
- 结论：能明确是"服务写的"只有 `sub_clazz_renewal_process_snapshot`（student-data）；数分那张是 uanalysis 数据集调度 + Hive 数仓链路。**要追后两类的写入任务/调度，走天工（nezha），不在 SLS 范围。**

## 数分那张的口径（U分析数据集 SQL，实取）

看板 `dashboard_3861404162508853248`「续班可续&目标同步看板」→ 模型「可续明细」(3109) → 物化表 `bdg_bi.menu_set_3990343659847962624_1792123218`；数据集 SQL（test 账号无 scope，走 Arthas `IntelligenceDataSetService.getMainDetail("menu_set_3990343659847962624").getExecuteSql()` 取，见 `tiangong-datawork` 的 uanalysis 反查 reference）。核心口径：

- **主表** `gaotu_dw.dm_user_subclazz_regular_clazz_details`，取 `canrenewal_uscount=1`（"可续人次"= 该明细行数）。
- **过滤**：`year_term_name in ('2026秋季')`、`course_first_level_department_name='H业务线'`、`course_second_level_department_name='精品班学部'`、`course_subject like '%规划系统%'`、`clazz_round='一轮'`。
- **时间**：`dt=当天(NOW())`、`hour='10'`（离线按天物化，取当天 10 点分区；内层还并 hour∈{'23','10'}）。
- 另 join `dw.ods_gaotu_gaotu_clazz_lesson`、`bdg_ba.dws_finance_renew_subclazz_user_addr_df` 及一批 `temp_table.taokangrong_*`（剔灰名单/手工单、算扩转分母等）。

## 两边口径对照（为什么数字不同）

| 维度 | 续班看板（student-data 快照） | 数分（U分析数据集） |
|---|---|---|
| 数据源 | ES `ads_large_subclazz_user_index`（业绩归属 canRenewal 同步） | Hive `gaotu_dw.dm_user_subclazz_regular_clazz_details`（离线明细） |
| "可续"口径 | `canRenewal ∈ {1,2,8}` | `canrenewal_uscount=1`（数仓自算标记） |
| 时效 | **每小时实时** upsert（当天数值会涨；EES 侧可续实时更新） | **按天离线 T+1**，固定取当天 `hour='10'` 分区（大数据侧可续 T+1 更新） |
| 过滤 | 该二讲名下辅导班/轮次/学员类型，排除内部员工 | 限 2026秋季 + H业务线·精品班学部 + `课程 like '%规划系统%'` + `clazz_round='一轮'`，剔灰名单 |
| 计数 | value_count（人次） | 明细行数（人次） |

→ 不一致的**直接原因（业务已确认）= 更新时效不同：EES 侧可续实时更新，大数据（数分）侧 T+1 更新**；叠加数据源、可续标记来源、过滤范围三处口径也不同。所以同一时刻两边数字天然不等。要坐实某天的差，需按数分同一 `dt`+`hour`（T 日 10 点分区）跑该数据集 SQL，与那一刻的 ES 快照逐项比。

## 相关记录（可续链路出处，不重复正文）

- **可续状态 = performance-attribution（业绩归属）判的**，student-data 只同步落 ES：见知识库 `知识库/cronus/microClazzRoster/continuationService.md`「可续状态/轮次的上游链路（业绩归属，非本服务自算）」；值域 `CanRenewalStatusEnum`（1 可续-未续 / 2 可续-已续 / 8 可续-后置课程退款 = 可续）。
- **上游落库表查法**（本次共同确认用到）：`gaotu_stat.performance_regular_can_renewal_sign_x`（cluster 259），按 `subclazz_number` 过滤、`can_renewal_status ∈ {1,2,8}`、**`COUNT(DISTINCT user_id)`**、`round_idx` 分轮次；按订单查原因接口 `POST /performance/management/suda/performance/regular/canRenewalSignReason`。详见工单 `续班与业绩/业绩归因/排查/可续状态判不可续.md`、[`不算可续分母或可续锁在别的订单.md`](../../业绩归因/排查/不算可续分母或可续锁在别的订单.md)。
- ⚠️ 该上游表**同一学员按 `can_renewal_term` 有多行**，只 `COUNT(*)` 会翻倍（实测寇一清辅导班一轮 90 行 / 45 人），必须 `COUNT(DISTINCT user_id)`——否则会把"行数"当成"人数"误判对不上。
- ⚠️ 该表是**「当前状态」表、每轮签单重签覆盖**：代码 `performance-attribution` `RenewalSignRegularStrategy#saveRenewalSign`（约 283–299 行）是**按订单号先删后插**——`listByOrderNumbers` 取旧行 → `deleteByOrderNumbers(orderNumbers)` 删 → `insertBatch(...)` 插（XML `insert ignore`，`create_time` 不写、走 DB 默认=插入时刻）。所以每轮重算都会把该订单标记的 `create_time` **重置为当次插入时间，不留历史**。实测：一批辅导班的 sign 行 `create_time` 全在当天清晨（10-16 05:28 起），`create_time < 当天` 的行数 = 0 → **不能用 `create_time` 反推"昨天/历史"的 performance 值**（会得 0）。要"昨天/历史"的可续值，只能走**按 `dt` 分区的数仓落库**（数分读的 `gaotu_dw.dm_user_subclazz_regular_clazz_details` 的 `dt=<昨天>` 分区），或另有日报/历史表——`sign_x` 本身不留历史。
- 🔎 **可续变更日志（能定位"某班何时变成可续"）**：`student-data` `FuwuOnsMqProducer:143` 会打 `sendOrderedMessage success ... topic=student_data_renewal_event_external_prod, tags=renewal_status, body={"userId":…,"subclazzNumber":<n>,"canRenewal":1}`；`ai-task` `RenewalEventOnsConsumer:105` 消费同事件。按 `subclazz_number` 搜 SLS（`queryStr='"<subclazzNumber>" and messages: canRenewal'`）即可定位该班可续变化的**时刻与学员**。实测寇一清班 `35330020147855872` 于 2026-10-16 05:28:51 命中 8 个 userId 的 `canRenewal=1`，与该班 `sign_x` 当天 create_time（05:28:47 起）吻合。

## 为什么数分和"昨天"也不完全相等（残差 1-2 人）

对到"昨天"后仍差 1-2 人属**正常边界抖动，不是 bug**，三个来源：

1. **时点对不齐**：快照"昨天"值 = 昨天**最后一次跑批**（接近当天结束）；数分离线批次取的是它自己固定时刻（数据集 SQL 写死 `hour='10'` 的当天分区）**且 T+1**，两个切片不是同一时刻。
2. **可续状态每天在变**：新判单命中可续 / 退款 / 过可续时间(6)转不可续 / 判单重算等，同一批学员隔天净变几人很常见。
3. **（已排除）口径差**：经上游共同确认，student-data 可续 = performance `performance_regular_can_renewal_sign_x` 当前值（寇一清 45=45、朱陈德 141+158=299=299），**两边可续同源、无口径差**，残差纯属时点。

**要精确到"差哪几个学号"（学员级 diff）**：按同一 `(subclazzNumber, 轮次)` 取两边名单按学号对比——

- student-data 侧：ES `ads_large_subclazz_user_index`（`subclazzNumber` + `canRenewal ∈ {1,2,8}` + `internalStaffFlag` 非内部）里的学员；
- 数分侧：其物化表 `bdg_bi.menu_set_*`（或上游 Hive `dm_user_subclazz_regular_clazz_details` 同口径）里 `canrenewal_uscount=1` 的学员；
- 差的学号在两边分别是什么可续状态（枚举见 `CanRenewalStatusEnum`），即可定位是"时点差"还是"口径差"。

> 注意：快照表 `sub_clazz_renewal_process_snapshot` 只存**计数**（`can_renewal_count`），**没有学员名单**；学员级 diff 必须回 ES / 数分上游明细取名单。


## 续班快照的产出与口径（student-data）

- **链路**：XXL-Job `RenewalDashBoardHandler`（`student-data-facade/.../job/dashboard/`）→ 读 ES `ads_large_subclazz_user_index` → 按维度算出各指标 → Doris Stream Load 写入 `student_data_renewal.sub_clazz_renewal_process_snapshot`（库/表由 Apollo `renewal.dashboard.doris.database` / `renewal.dashboard.doris.table` 指定，默认即此）。另一 job `RenewalDashBoardUpdateHandler` 只回刷组织/人员归属列。
- **"可续"口径**：ES `canRenewal ∈ canRenewalStatusList`，即 `{1,2,8}` = 1可续-未续 / 2可续-已续 / 8可续-后置课程退款（`CanRenewalStatusEnum`）。配置项 Apollo `renewal.plan.dashboard.can.renewal.status.list`（prod 未配 → 默认 `[1,2,8]`）。另排除内部员工：`internalStaffFlag` 不存在或 `=0`。
- **`can_renewal_count` = ES `value_count(canRenewal)`**（已由 query 限定 ∈{1,2,8}，故等于命中文档数，是"人次"不是"去重学员数"）。
- **维度切分**：辅导班 `subclazzNumber` → 二讲 `assistantAccountId` → 轮次 `roundIdx` → 学员类型+科目 `studentTypeWithSubject`；每条 = 该维度组合的一行。
- **时间**：`snapshot_time` = 当天 0 点；主 job 每轮只写当天那一行并 upsert，所以**当天数值随跑批变化**（组织归属列由 update job 全量刷新）。
- 归属列口径：`group_leader_*` 取虚拟架构负责人，`group_leader_plus_*` 取 CAS 汇报关系（PS 上级），见 `小组长+1榜里出现小组长.md`。

## 核对 SQL（SelectDB）

```sql
-- 续班看板"可续学员量"对齐：某二讲某天，按轮次看
SELECT snapshot_time, assistant_teacher_name, round_idx_name, SUM(can_renewal_count)
FROM student_data_renewal.sub_clazz_renewal_process_snapshot
WHERE assistant_teacher_name = '<姓名>' AND snapshot_time = '<yyyy-MM-dd> 00:00:00'
GROUP BY snapshot_time, assistant_teacher_name, round_idx_name;

-- 二讲维度合计（含全部轮次）
SELECT snapshot_time, assistant_teacher_name, SUM(can_renewal_count)
FROM student_data_renewal.sub_clazz_renewal_process_snapshot
WHERE assistant_teacher_name = '<姓名>' AND snapshot_time = '<yyyy-MM-dd> 00:00:00'
GROUP BY snapshot_time, assistant_teacher_name;

-- 按 biz 班号定位（班级ID 形如 32YYTS26Q45K11002 是 clazz_biz_number）
SELECT snapshot_time, clazz_biz_number, sub_clazz_biz_number, renewal_activity_name,
       grade_name, subject_name, round_idx_name, student_sub_type_name, can_renewal_count
FROM student_data_renewal.sub_clazz_renewal_process_snapshot
WHERE clazz_biz_number IN ('<班号>', ...) AND snapshot_time = '<yyyy-MM-dd> 00:00:00';
```

## 验证

- 页面某维度当天的数字，应等于上面 SQL 在同一 `snapshot_time`、同一维度、同一轮次口径下的 `SUM(can_renewal_count)`。对不上先怀疑"日期/轮次/筛选"没对齐，再怀疑数据源不同。
- 若两边确实读同一张表却仍差：优先看是不是**快照日期不同**（数分常 T+1 或按上一跑批）或**轮次口径不同**（看板常只看某一轮，快照表含多轮）。
- 若数分读的是别处（如 U分析数据集 / Hive 数仓，不在 student-data），本仓库无法自证，需数分侧提供**数据集 SQL**（经 `bdg-uanalysis-intelligence` / nezha）再逐条对齐口径。
- **判"是不是 T+1"最快**：拿同批二讲，把数分截图的数与快照的**昨日一轮**、**今日一轮**分别比——数分逐行 ≈ 昨日一轮、看板逐行 = 今日一轮，即 T+1（实测已印证：张欣欣03 158=158、杨一枝 234=234、朱陈德 270≈271）。
