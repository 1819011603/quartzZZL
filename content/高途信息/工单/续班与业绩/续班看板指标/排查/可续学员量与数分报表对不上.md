# 续班看板指标 · 可续学员量与数分报表对不上

> **只解决**：续班服务-过程数据排名（辅导班维度 / 二讲 / 小组长 / 小组长+1）里的"可续学员量"，与数分（U分析平台 / 大航海）出的"可续人次"对不上（同一老师/班级两边数字不同）。
> 「小组长+1」维度归属是不是该显示大组长，走 [`小组长+1榜里出现小组长.md`](小组长+1榜里出现小组长.md)；「不报名意向率」偏高走 [`不报名意向率异常虚高.md`](不报名意向率异常虚高.md)。三者的数据源同一张快照表，但问题不同。

## 判定入口

1. **先确认两边是不是同一张表**。续班看板的"可续学员量"取 student-data 的续班快照表；数分是不是同一张表，要数分侧给出取数 SQL（可能是另一条 DWH 链路，不在 student-data）。
2. **对齐"日期 + 维度 + 轮次"再比**。续班看板数字 = 某个 `snapshot_time`（当天 0 点）的快照聚合值；跨天/跨轮次/不同筛选直接比会得到假差异。当天快照每个跑批轮都会变，页面与报告刷新时刻不同也会差。
3. 页面某维度数字 = 快照表按该维度粒度求和，见下方 SQL。

## 怎么定位两边各自的写入源（SLS 全局日志只能追"服务写的表"）

- **SLS 全局日志只能匹配到服务写入**。命中 `service=student-data` + `DorisStreamLoadGenericService` + `.../student_data_renewal/sub_clazz_renewal_process_snapshot/_stream_load`（另加 `RenewalDashBoardHandler#insert`），即可确认 `sub_clazz_renewal_process_snapshot` 是 student-data 写的 Doris 表。
- **`bdg_bi.menu_set_*` 不是服务，是 U分析数据集调度任务**：`bdg-uanalysis-intelligence` 的 `IntelligenceSchedulesService` 把数据集 SQL 发布成 nezha DW 导入任务（`publishNezhaTask` → `nezhaClient`，`DWImportTaskVO.source=bdg_bi`），表名 = `菜单库.数据集menuId_<epoch>`。执行/落库在 nezha executor(EMR)，**不在 SLS**，所以全量 app 日志搜不到写入记录。
- **Hive 表**（如 `gaotu_dw.dm_user_subclazz_regular_clazz_details`、`dw.ods_gaotu_gaotu_clazz_lesson`、`bdg_ba.dws_finance_renew_subclazz_user_addr_df`）是**离线数仓任务产出**，用天工（nezha）血缘看上下游，也不是某个 Java 服务写的。
- `temp_table.<用户名>_*` = 个人临时表，别当数据源。
- 结论：能明确是"服务写的"只有 `sub_clazz_renewal_process_snapshot`（student-data）；数分那张是 uanalysis 数据集调度 + Hive 数仓链路。**要追后两类的写入任务/调度，走天工（nezha），不在 SLS 范围。**


## 续班快照的产出与口径（student-data）

- **链路**：XXL-Job `RenewalDashBoardHandler`（`student-data-facade/.../job/dashboard/`）→ 读 ES `ads_large_subclazz_user_index` → 按维度算出各指标 → Doris Stream Load 写入 `student_data_renewal.sub_clazz_renewal_process_snapshot`（库/表由 Apollo `renewal.dashboard.doris.database` / `renewal.dashboard.doris.table` 指定，默认即此）。另一 job `RenewalDashBoardUpdateHandler` 只回刷组织/人员归属列。
- **"可续"口径**：ES `canRenewal ∈ canRenewalStatusList`，即 `{1,2,8}` = 1可续-未续 / 2可续-已续 / 8可续-后置课程退款（`CanRenewalStatusEnum`）。配置项 Apollo `renewal.plan.dashboard.can.renewal.status.list`（prod 未配 → 默认 `[1,2,8]`）。另排除内部员工：`internalStaffFlag` 不存在或 `=0`。
- **`can_renewal_count` = ES `value_count(canRenewal)`**（已由 query 限定 ∈{1,2,8}，故等于命中文档数，是"人次"不是"去重学员数"）。
- **维度切分**：辅导班 `subclazzNumber` → 二讲 `assistantAccountId` → 轮次 `roundIdx` → 学员类型+科目 `studentTypeWithSubject`；每条 = 该维度组合的一行。
- **时间**：`snapshot_time` = 当天 0 点；主 job 每轮只写当天那一行并 upsert，所以**当天数值随跑批变化**（组织归属列由 update job 全量刷新）。
- 归属列口径：`group_leader_*` 取虚拟架构负责人，`group_leader_plus_*` 取 CAS 汇报关系（PS 上级），见 `小组长+1榜里出现小组长.md`。

## 核对 SQL（SelectDB）

```sql
-- 续班看板"可续学员量"对齐：某二讲某天，按轮次看
SELECT snapshot_time, assistant_teacher_name, round_idx_name, SUM(can_renewal_count)
FROM student_data_renewal.sub_clazz_renewal_process_snapshot
WHERE assistant_teacher_name = '<姓名>' AND snapshot_time = '<yyyy-MM-dd> 00:00:00'
GROUP BY snapshot_time, assistant_teacher_name, round_idx_name;

-- 二讲维度合计（含全部轮次）
SELECT snapshot_time, assistant_teacher_name, SUM(can_renewal_count)
FROM student_data_renewal.sub_clazz_renewal_process_snapshot
WHERE assistant_teacher_name = '<姓名>' AND snapshot_time = '<yyyy-MM-dd> 00:00:00'
GROUP BY snapshot_time, assistant_teacher_name;

-- 按 biz 班号定位（班级ID 形如 32YYTS26Q45K11002 是 clazz_biz_number）
SELECT snapshot_time, clazz_biz_number, sub_clazz_biz_number, renewal_activity_name,
       grade_name, subject_name, round_idx_name, student_sub_type_name, can_renewal_count
FROM student_data_renewal.sub_clazz_renewal_process_snapshot
WHERE clazz_biz_number IN ('<班号>', ...) AND snapshot_time = '<yyyy-MM-dd> 00:00:00';
```

## 验证

- 页面某维度当天的数字，应等于上面 SQL 在同一 `snapshot_time`、同一维度、同一轮次口径下的 `SUM(can_renewal_count)`。对不上先怀疑"日期/轮次/筛选"没对齐，再怀疑数据源不同。
- 若两边确实读同一张表却仍差：优先看是不是**快照日期不同**（数分常 T+1 或按上一跑批）或**轮次口径不同**（看板常只看某一轮，快照表含多轮）。
- 若数分读的是别处（如 U分析数据集 / Hive 数仓，不在 student-data），本仓库无法自证，需数分侧提供**数据集 SQL**（经 `bdg-uanalysis-intelligence` / nezha）再逐条对齐口径。
