# 续班问卷绑定 · 按问卷ID查绑定的续班计划

> **只解决**：已知「问卷ID」，要查它绑在哪个续班计划 / 哪个前置课程；或按常规口径查为空，需要确认计划是否已删除。
> 续班问卷「发送/提交状态」在花名册/EES 显示不对，走 [`../../续班问卷状态/README.md`](../../续班问卷状态/README.md)，与本文无关。

## 判定入口

- 「问卷ID」有两个口径，先分清，混用必查空：
  - **页面/业务口径的问卷ID = `gaotu.questionnaire.biz_id`**（问卷平台作品ID，17 位左右）。
  - `gaotu.questionnaire.number`（内部问卷编号）才是 `renew_master_course_relation.questionnaire_number`、product-b 匹配接口入参用的编号。
- 绑定关系分两层，结论以**绑定层**为准：
  - **绑定层**（问卷 → 计划）：`questionnaire.process_number / node_number → process_config.renewal_number → renew_master`。绑定问卷时写入，改绑会更新。
  - **匹配层**（问卷 → 前置课程，自动算）：`renew_master_course_relation`，由 `calculateRenewCourseRelation` 按年级/学科/部门条件匹配后写入；为空 ≠ 没绑定。
- 计划会被**软删除**：`renew_master.isdel=1`，同时其 `renew_master_course_relation.isdel=1`。**只按 `isdel=0` 过滤会查空，从而误判「没绑定」**。

## 排查

### 1. 问卷ID(biz_id) → 续班计划（绑定层，含已删除）

```sql
SELECT q.biz_id, q.number AS questionnaire_number, q.process_number,
       p.renewal_number, m.name AS plan_name,
       m.isdel AS plan_deleted, p.is_del AS process_deleted
FROM gaotu.questionnaire q
JOIN gaotu.process_config p ON p.number = q.process_number
LEFT JOIN gaotu.renew_master m ON m.number = p.renewal_number
WHERE q.biz_id IN ('<问卷ID1>', '<问卷ID2>');
```

- `plan_deleted=1` = 续班计划已被删除；`process_deleted=1` = 流程被删。
- 不加 `q.is_del=0`：问卷解绑/换版本时可能是 `is_del=1`，加过滤会漏。

### 2. 问卷ID → 前置课程/班级（匹配层）

```sql
SELECT q.biz_id, r.renew_master_number, r.pre_course_number, r.questionnaire_number, r.isdel
FROM gaotu.questionnaire q
JOIN gaotu.renew_master_course_relation r ON r.questionnaire_number = q.number
WHERE q.biz_id IN ('<问卷ID>');
```

- `pre_course_number` 再关联 `course_center.clazz.course_number` 得到班级（跨库，见 `知识库/promotions/continuation-classes/renewalProcess.md`）。
- 这里为空或 `isdel=1` 不能当「未绑定」：计划未发布、规则没命中、计划已删除都会如此。

## 验证

- 第 1 步返回的 `plan_name` 能在 OES「续班计划管理」对上；计划已删则页面查不到，属正常。
- 用 `biz_id` 直接调 product-b 的 `listRenewMasterCourseRelationByQuestionnaireNumber` 返回空，是因为入参口径是 `questionnaire.number` 而非 biz_id，**别据此下「未绑定」结论**。
