> **压测中主要看 belong「续班中 → 服务监控」**：https://belong.baijia.com/sla?tab=0 ，依次关注 **商品、订单、支付、优惠、node** 五个页签。

- 发压机配置发到「续班保障」群
- **服务监控**：在上述五个页签中查看对应服务指标。2026-10-28 用户确认并提供截图：商品页展示 `product.gaotu100.com` 的 CPU 使用率和流量趋势；截图时间范围为近 5 分钟、刷新频率为 1 分钟。原 SOP 记录的 `/application` 是旧记录入口，压测值守以本节的 `/sla?tab=0` 为主。
- **node 时间范围**：切到 `node` 页签，打开时间范围，快捷选择「近 5 分钟」（2026-10-28 用户确认并提供截图，页面展示 `gaotu-mweb`）。
- **MQ 堆积**：同时关注 `MQ_INST_1941505946323830_Bay8En7I`、`MQ_INST_1941505946323830_BcfK60rM` 两个生产实例。真实堆积使用 Prometheus `rocketmq_consumer_ready_messages`（就绪未消费），不要把 `ConsoleConsumerProgress.accumulate` 的位点差当成真实堆积；堆积上涨时查看消费线程、下游 RT、是否有 `Suspend` 重试。
- **顺序消息消费加速器（`enableOrderlyConsumeAccelerator`）**：注解项 `@OnsMessageListener.enableOrderlyConsumeAccelerator` → ONS 属性 `ENABLE_ORDERLY_CONSUME_ACCELERATOR` → `DefaultMQPushConsumer.setOrderlyConsumeAccelerator`，**只对顺序消息有意义**。SDK 注释：*"enable accelerator of orderly consumption which consume messages concurrently with different sharding keys in the same queue"*。
  - `true`：同一 queue 内按 `shardingKeyIndex = hash(shardingKey) % maxConcurrencyForOrderQueue`（SDK 默认 16）分桶**并发**消费，同一 sharding key 仍保序（`ConsumeMessageOrderlyService.submitConsumeRequest`）。
  - `false`（或不配，annotation 默认 `""`）：一个 queue 只提交一个 ConsumeRequest，**队列内串行**。
  - 何时关注：**调低它只会更慢**。顺序消费打 `Suspend` 重试时，`false` 会阻塞**整个 queue**，`true` 只阻塞对应 sharding key 桶——给"整队列串行"的顺序消费者开加速器，能收窄 Suspend 的爆炸半径。
  - 本仓现状：`StudentPresaleConsumer` 默认 `true`；出过 ES 5s 超时的 `AdsSubclazzUserSyncConsumer` **未配**（即 false、整队列串行）。`maxConcurrencyForOrderQueue` 该 starter 未暴露、固定 16，只有开关可配。
  - 关联案例：[预报名状态延时飙到51s](../../续班看板指标/案例/2026-10-29-预报名状态延时飙到51s.md)。
- 前端指标：`gaotu-nginx`（`http_host: m.gaotu100.com`，含 product / learn / courseList）
- 后端指标：`gaotu.order_info` 按 `create_time` / `pay_number` 统计批次单与订单量

### 只读监控脚本

入口：[`Scripts/monitor_renewal.py`](../Scripts/monitor_renewal.py)。在本模块目录执行：

```bash
# 单次采集，固定近5分钟
python3 Scripts/monitor_renewal.py
# 每分钟采集一次，Ctrl-C 停止
python3 Scripts/monitor_renewal.py --watch
# 只看MQ，或只看belong
python3 Scripts/monitor_renewal.py --only mq
python3 Scripts/monitor_renewal.py --only belong
```

- 商品、订单、支付、优惠：复用 belong 的 Grafana 面板查询，采集接口请求量/错误量/错误率/P99、CPU、数据库和 Redis 指标；node 采集 CPU 和流量，固定近 5 分钟。
- MQ：复用 `~/.local/mcp-servers/mcpcli.py` 的 `ons_group_backlog_top`，显式使用生产 region `cn-beijing`，默认两个实例各取 Top 30。这是实例 Top N，不代表所有消费组；可用 `--instance` 指定实例、`--top-n` 调整数量。
- 依赖本地 8888 Cookie 注入代理和既有 MQ CLI；凭据只在运行时使用，不写入脚本或结果。默认只采一次，不发送通知、不修改生产状态。
- 控制台输出摘要，每轮 JSON 保存到 `/tmp/renewal-monitor`（`--output` 可改）；持续采集支持 `--interval`（默认 60 秒）和 `--count`。
- 退出码：`0` 所有面板和 MQ 查询有数据，`2` 查询失败或存在无数据，`3` 登录失效并停止，`130` 手动停止。采集完整不代表业务正常；无数据不等于零流量或零堆积，脚本不自动判业务告警阈值。
- 验证：[`Scripts/test_monitor_renewal.py`](../Scripts/test_monitor_renewal.py)，执行 `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s Scripts -p 'test_monitor_renewal.py'`；2026-10-28 实采验证五个页签和两个 MQ 实例，node 的 `mweb-suyang` 流量查询无数据，按 `no_data` 输出。
