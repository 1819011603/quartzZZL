# 续班保障 · 打限流（Sentinel）排查与查询手册

> **只解决**：续班大促/续班分发期间，`order.gaotu100.com`（或相邻服务）出现 Sentinel 流控告警/`FlowException` 时，**怎么定位是谁在打、打的哪个接口、阈值多少、实际 QPS 多少**。
> 某个班级没进续班学科走 [`班级没进续班学科.md`](班级没进续班学科.md)；压测该配哪些 key 走 [`续班大促压测保障流程.md`](续班大促压测保障流程.md)。

## 告警长这样

```
【高优】【订单-研发】Sentinel流控告警  环境：prod
[TID: xxx] [Sentinel]resource: /feign/order/orderInfo/queryByUserId blocked, args: [],
Caused by: FlowException, Rule: 1841
```

- `FlowException` = **流控**（不是报错、不是降级）。接口被 Sentinel 拦下，feign 调用方拿到 520/429。
- `Rule: <id>` = 命中的流控规则 id（见下方「读规则」）。
- 上报的「异常日志」= 每次被拦都打一条 ERROR，条数 = 被拦请求量，**不是业务异常量**。

## 一句话结论模板

> 续班保障期间 `< 调用方服务 >` 调 `/<资源>` 的 QPS 超过青舟配置的**集群阈值** `< N >`，触发集群流控被拦；流量回落后自愈。

## 怎么查（按顺序）

### 1. 拉限流日志，拿到资源 + Rule id + 调用方 TID

工具 `qingzhou-observe get_log_v2`。**关键：SLS 里 order 的服务名是 `order-gaotu100-com`**（`order.gaotu100.com` 的 `.` 转 `-`），不是域名。

```
get_log_v2(env=prod, backend=sls, logType=error,
           serviceName="order-gaotu100-com",
           grep="Rule: 1841",              # 或 grep="blocked" / grep="Sentinel"
           fromTimestampInSeconds=<告警前>, toTimestampInSeconds=<告警后>)
```

- `serviceName` 与 `queryStr` **不能同时用**；过滤用 `grep`（客户端正则，默认只扫服务端拉回的前 100 条，窗口开小一点）。
- 日志里每条都有 `trace_id`（TID），形如 `stp-distribution-client.74.17932001837191824`，前缀就是**调用方服务名**。

### 2. 用 TID 还原调用链，确认调用方

```
trace_tree(trace_id="stp-distribution-client.74.17932001837191824",
           service_name="order.gaotu100.com", env=prod)
```

被限流的 span 通常是 `statusCode=429 / error=true`，发起方即告警来源。

### 3. 读运行中的 Sentinel 规则（最权威，拿阈值/类型）

直接进 pod 用 arthas 读 `FlowRuleManager` 已加载规则（比翻 etcd/后台快）：

```bash
python3 ~/.agents/skills/pod-terminal/pod_term.py arthas \
  --service-code gaotu_order --env prod \
  --command 'getstatic -x 4 com.alibaba.csp.sentinel.slots.block.flow.FlowRuleManager flowRules' \
  --stop
```

看命中资源那一项：

| 字段 | 含义 |
|---|---|
| `resource` | 被限流的资源（URL path） |
| `grade=1` | QPS 流控（`0`=线程数） |
| `count` | 阈值 |
| `clusterMode` | `true`=集群流控（阈值是**全局**的；单机流控则是每实例） |
| `id` | 规则 id（= 日志里的 `Rule: <id>`） |
| `limitApp` | 生效来源；`default`/`;;;`= 所有来源 |

其它规则类型（降级等）：同法读 `com.alibaba.csp.sentinel.slots.block.degrade.DegradeRuleManager`。

### 4. 量实际 QPS（单 pod access log）

进 pod 数该接口每分钟请求数，判断是「阈值太低」还是「流量真突增」：

```bash
python3 ~/.agents/skills/pod-terminal/pod_term.py exec \
  --service-code gaotu_order --env prod \
  --cmd 'F=/apps/srv/instance/logs/order-access_log.$(date +%F).log; for m in 06 07 08 09 10; do echo -n "23:$m "; grep "23:$m" $F | grep -c "orderInfo/queryByUserId"; done > /tmp/c 2>&1; cat /tmp/c'
```

- 每 pod 一分钟 N 次，乘实例数≈集群 QPS，和 `count` 阈值对比即可定性。
- access log 路径：`/apps/srv/instance/logs/order-access_log.<Y-m-d>.log`；格式 `IP - - [dd/Mon/yyyy:HH:mm:ss +0800] "POST /path HTTP/1.1" 状态 字节`。

## 阈值/规则配在哪

- **青舟「流量防护」页**（可读可改，规则 id 与日志里一致）：`https://qingzhou.baijia.com/#/myApp/flowProtection?appNid=<应用的 appNid>`（appNid 从该应用在青舟的 URL 取）。
  - 后端接口：`/qingzhou/sentineladmin/v1/flow/listRule`（流控）、`/v1/flow/getRule`、`/v1/flow/putRule`、`/degrade/listRule`、`/auth/listRule`、`/sys/listRule`。
- 规则实际持久化在 **etcd**：`/sentinel/rules/<appName>/flowRule/<appGroupName>/`。
  - etcd 地址在 Apollo public namespace `tech-base.arch-sentinel-public` 的 `arch.sentinel.etcd`（读：`apollo_get_key(app_id="order.gaotu100.com", env=PROD, namespace="tech-base.arch-sentinel-public", key="arch.sentinel.etcd")`）。内网地址，本机一般不通，优先用上面的 arthas 读运行态。

## 常见处置

- 流量确需更高：青舟调高该规则阈值，或给调用方单独配 `limitApp` 来源限流（当前多为所有来源共用同一阈值）。
- 疑似放大：查调用方是否有重试/批量循环（本次调用方为 `stp-distribution-client`，续班分发）。
