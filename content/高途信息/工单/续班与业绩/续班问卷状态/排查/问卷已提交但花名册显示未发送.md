# 续班问卷状态 · 问卷已提交但花名册显示未发送

> **只解决**：家长/学员确认已经在小程序里填写并提交了续班问卷，但花名册页面（student-center 的 `roster/renewal/page`，即 EES 课后督学看到的页面）显示的 `renewalQuestionnaireStatus`（问卷状态）或 `preRegistrationIntentKey`（预报名意向）等字段没跟上——**这两个字段已确认会被同一类"MySQL 源表对、ES 没同步对"问题影响，排查方法通用，遇到哪个字段都按本文走**。
> 问卷压根没收到/没弹出来（触达任务本身没送达），走触达/reach-service 排查，与本文无关。

## 判定入口

- 现象只有一种可观察表现：EES/花名册页面这个字段显示"未发送"（对应 `RenewalQuestionnaireStatusEnum.UN_SEND=1`），但业务方能确认家长已经提交过。
- 先问清楚：学员 userId、班级号（前端展示的 `clazzBizNumber`，形如 `16SX26QUP7S11012`）、大概的提交时间。
- 字段存储位置（查一次很贵，直接抄）：
  - ES 索引 `ads_large_subclazz_user_index` 是**别名**，物理索引是 `ads_large_subclazz_user_index_v2`；`GET ads_large_subclazz_user_index/_mapping` 返回的 key 就是 `_v2`，两者是同一份数据，别被名字迷惑。
  - 物理集群 host `es-cn-smw4b9m200004w3hn`：student-data 里对应 `RestHighLevelClient` bean 叫 `eesServeClient`（Apollo key `ees.serve.es.cluster.host`），student-center 里叫 `studentSubclazzClient`（Apollo key `student.subclazz.es.cluster.host`）——**两个项目用不同 bean 名指向同一个物理集群**。
  - 文档 `_id` = `subclazzNumber-userId`（辅导班号-学员号，不是 clazzNumber-userId）。

## 排查

### 1. 先查源头数据对不对——优先查 MySQL，比追 MQ 日志快得多

- `renewalQuestionnaireStatus` 的源头：用 `baijia-invoke` 直连调用（`project=student-data`）
  - `QuestionnaireAclService#batchQuestionnaires([clazzNumber], [userId])` —— 有没有提交记录，`finishTime`、`projectNumber` 是多少。
  - `RenewalMasterAclService#queryRenewalMasterInfo([clazzNumber])` —— 续班计划是否存在且 `status=2`（已发布）。
  - `QuestionnaireAclService#queryQuestionnaireMatchResult(clazzNumber, renewalMasterNumber)` —— 返回的 `bizId` 是否等于问卷记录的 `projectNumber`。
- `preRegistrationIntentKey`（预报名意向）的源头：直接查 MySQL 表 **`renewal_intent_info`**（student-data 库）：`SELECT pre_registration_key FROM renewal_intent_info WHERE user_id=<userId> AND clazz_number=<clazzNumber>`。
- 两者一致（或 MySQL 记录本身是对的）时，说明**计算环节没问题**，问题在"同步到 ES"这一步——直接跳到第 2 步查 ES，不用再纠结 `RenewalQuestionnaireStatusServiceV2`/`RenewalIntentInfoServiceImpl` 的计算逻辑对不对。
- 只有当源头数据（问卷提交记录 / `renewal_intent_info` 表）本身就是错的或缺失时，才说明是数据/绑定关系问题，不是本 runbook 要解决的"存量字段没跟上"。

### 2. 查 ES 里存的值是不是跟源头不一致

用 `es-apply` skill 直接查文档（`instance-id=es-cn-smw4b9m200004w3hn`，`index=ads_large_subclazz_user_index`，`_id=<subclazzNumber>-<userId>`），一次性把 `renewalQuestionnaireStatus`、`renewalQuestionnaireSubmitTime`、`preRegistrationIntentKey` 都读出来对比。**留意"部分字段对、部分字段错"这种特征**（比如 `renewalQuestionnaireSubmitTime` 是对的、但 `renewalQuestionnaireStatus` 是错的）——这说明覆盖写入的请求体里没带那个"对的"字段（ES 局部更新只覆盖请求体出现的字段），可以用来反推是哪一类写入者干的（只写单个字段 vs 整体重算写多个字段）。

### 3. 全部已知写入者清单（跨 student-data + student-center 两个项目，共 7 处）

这个字段完全没有单一权威写入口，任何一处都可能是问题源：

1. `DwsRenewalQuestionnaireConsumer`（student-data-dws）—— 问卷提交事件驱动。`innerUpdateQuestionnaireStatus` 里先 `checkRenewalMaster` 校验续班计划已发布才写，通过 MQ topic `student_data_ads_large_subclazz_user_ordered_prod`（tag=`user_clazz_tag`）发给 `AdsSubclazzUserSyncConsumer`（部署在 `student-data` 这个真实服务里）落 ES。
2. `RenewalQuestionnaireConsumer#updateByDataQuery`（student-data-facade）—— 续班计划发布/编辑/问卷绑定变更事件驱动，对**整班学员批量**用 `RenewalQuestionnaireStatusServiceV2`（实时计算）重算并写回，同样走 `user_clazz_tag`；**写入体里只有 `renewalQuestionnaireStatus`，不带 `renewalQuestionnaireSubmitTime`**——如果观察到"submitTime 对、status 错"，先怀疑这一处（但 2026-09-28 两次实测都没在日志里找到它被触发的痕迹，假设未被证实，仅供下次排查参考）。
3. `AdsLessonUserMultipleOrderConsumer#feedbackHandler`（`reachSceneCode=renewalSendQuestion`）—— 触达任务送达回执驱动，单学员重算写回，同样只写 `renewalQuestionnaireStatus` 不带 submitTime。
4. `SubclazzUserBcpJobTemplate`（`BCP_LARGE_SUBCLAZZ_USER` 场景，对应 XXL-Job `bcp_大班续班花名册`，job_id **11259**，jobGroup 314/`高途-运营工作台-student-data`，cron 每天10点）—— 随机抽样比对+自愈任务，**绕开 MQ 直接批量写 ES**（用 `eesServeClient`）。**2026-09-28 实测确认它当前的 executorParam 是 `BCP_LARGE_SUBCLAZZ_USER|120|100|userName,renewalQuestionnaireStatus,presaleStatus,canRenewal,renewalStateStatus|false`——最后一段 `compareAutoFix=false`，即自动修复是关闭的，它只发通知不写 ES，结构上可以直接排除**，不用再查它的执行日志。
5. `RenewalQuestionnaireTransferSyncService` + `RenewalQuestionnaireTransferConsumer`（调课调班后重算，2026-09-24 加入）—— 排查前先确认这批代码是否已发布到 release/master（`git merge-base --is-ancestor <commit> origin/release`），没上线就不用往这个方向查。
6. `DwsStudentFieldSyncConsumer`（GAIA 学员字段同步，`dealLargeSubclazz`）—— 消费 `student-center-field-data-update-*` 事件，**绕开 MQ 直接 scroll+bulk 写 ES**。
7. `UserSubClazzSyncTemplate`（**student-center 自己的**直写路径，被 `StudentListEditServiceImpl`"编辑学生信息"接口调用）—— 走 `studentSubclazzClient`，**完全绕开 student-data 全部 MQ 消费者**，只查 student-data 的日志/代码会完全看不到这条。

逐一排查方法：拿目标学员的 `shardingKey`（`subclazzNumber-userId`）去搜每个写入者对应的日志关键词，看是否在可疑时间窗内有该写入者的活动记录。**2026-09-28 两次案例都把这 7 处全部排除了（日志里都查不到）**，如果这次也全部排除，不用继续在应用日志里死磕，直接看下面这条。

**已排除、但容易被误认为写入者的第三方**：student-center 自己独立注册了一个声明 `renewalQuestionnaireStatus` 所有权的 `RenewalFiledConvertDataQueryServiceImpl`（`DataQueryServiceV2` 实现）——读代码确认它只在字段为 `null` 时默认填 0，不会覆盖已有值，且只用在只读的 `RenewalService.page()` 响应构建里，没有写回 ES 的路径。看到这个类名不用慌，它不是写入源。

**如果 7 处应用层写入者全部排除**：说明问题大概率不在应用代码层，而在"MySQL→ES 同步"这一层本身（比如是否存在独立于这 7 处之外的批量同步/CDC 任务）——这个方向截至 2026-09-28 还没有排查工具/方法，是本文档最大的未解决缺口。

### 4. 跨服务查日志的技巧

- `student-data` 这个 gapm 服务名其实是**两个真实部署**：`student-data`（facade+service，含 `AdsSubclazzUserSyncConsumer`）和 `student-data-dws`（含 `DwsRenewalQuestionnaireConsumer`）。`qingzhou-observe` 的 `serviceName` 参数要按这两个真实名分别查，笼统传一个会漏掉另一半日志。
- 拿到任意一条日志的 `trace_id`（形如 `student-data-dws.866945.17903331653590989`）后，直接整体套双引号传 `queryStr: messages: "<trace_id>"`（不加 `serviceName` 限制），能一次拉出这条 TID 下**跨所有服务**（student-data/student-data-dws/course-center/clazz-distribution-server/ai-task 等）的完整调用链日志，比走 `trace_tree` 更适合这种"MQ 异步链路"场景（`trace_tree` 是给同步 RPC 调用链设计的）。
- `get_log_v2` 的 `queryStr` 用单个稀有 token（msgId/shardingKey/trace_id 数字部分）配合窄时间窗最稳；两个 `messages:` 词 `AND` 组合在词不够稀有时**不保证真正生效**（实测出现过 AND 查询返回值和单词查询几乎一样大的情况），别轻信"加了 AND 就精确"。
- 命中 0 先怀疑是不是 `serviceName` 传错了真实部署名，别急着下"这条链路没跑过"的结论。

## 回溯修正单个学员

确认底层数据（问卷提交记录 / `renewal_intent_info` 表）是对的、只是 ES 存量字段没跟上时，可以直接调用生产同款写入方法回溯（**这是写操作，需先取得授权**；这个方法就是 `SubclazzUserBcpJobTemplate#repairData` 底层用的同一个 ES `docAsUpsert` 原语，不是临时手推的野路子）：

```
project=student-data
service_method=com.gaotu.student.data.app.service.syncdata.AdsSubclazzUserSyncUpdateService#singleUpsert
# renewalQuestionnaireStatus：
params=[{"shardingKey":"<subclazzNumber>-<userId>","renewalQuestionnaireStatus":3,"renewalQuestionnaireSubmitTime":<finishTime毫秒>}]
# preRegistrationIntentKey（值以 MySQL renewal_intent_info.pre_registration_key 为准，不要凭问卷答案猜）：
params=[{"shardingKey":"<subclazzNumber>-<userId>","preRegistrationIntentKey":<pre_registration_key的值>}]
```

写完必须读回 ES 确认字段值已变成预期值，不能只看调用返回成功。两个字段互不影响，可以分开写、分开验证。

## 批量核对一个班/辅导班

**`renewalQuestionnaireStatus`**：
1. `SubclazzStudentBizFeignService#listAllSubclazzStudentBySubclazzNumberAndStatus(subclazzNumber, [1,2,3])` 拿全部在班学员 userId。
2. `QuestionnaireAclService#batchQuestionnaires([clazzNumber], [全部userId])` 一次拿到该班所有真实提交记录（按 `projectNumber` 过滤到目标问卷）。
3. ES 按 `subclazzNumber` + `terms(userId, 提交记录里的userId)` 查一次，对比 `renewalQuestionnaireStatus` 是否都是 3；不是 3 的才是需要回溯的。
4. 没有提交记录的学员，可选用 `ReachTaskDataService#listClazzUserTasks(clazzNumbers, userIds, [3], [87])` 查触达送达记录（`scene=87` 问卷发送场景，`status=3` 已完成），确认"未发送"是不是真的没送达，避免误判成同类 bug。

**`preRegistrationIntentKey`**（发现问题后建议顺手一起查，2026-09-28 案例证明同一批事件会同时影响两个字段）：
1. 同上拿全部在班学员 userId。
2. 直接查 MySQL：`SELECT user_id, pre_registration_key FROM renewal_intent_info WHERE clazz_number=<clazzNumber> AND user_id IN (<全部userId>)`——**注意 `clazz_number` 是"大班"维度，一个 clazzNumber 下可能有远多于单个辅导班人数的记录（同一大班多个辅导班共用），务必带 `user_id IN` 限定到本次核对的名单，否则会查出几千条无关记录**。
3. ES 按同样的 `subclazzNumber` + `terms(userId)` 查一次 `preRegistrationIntentKey`，跟 MySQL 结果逐条比对，不一致的才是需要回溯的（注意方向可能双向：MySQL=1/ES=0，或 MySQL=3/ES=1 都出现过）。

## 验证

- ES 读回目标字段变成预期值，才算修复生效；调用返回成功不算数。
- 批量核对时，"全部提交记录/`renewal_intent_info` 记录对应的 ES 值都一致" 才算这个班/辅导班没有遗留问题；没有源头记录的学员显示"未填写/未发送"，要么是真的没提交，要么另查触达送达记录再下结论。
- 经验数据（2026-09-28）：单个辅导班（150~250人规模）里，这类不一致通常是个位数（1~4 条），**不是全班性问题**，核对时不用假设"全班都要修"，按实际比对结果来。
