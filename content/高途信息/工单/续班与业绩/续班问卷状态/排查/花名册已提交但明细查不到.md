# 续班问卷状态 · 花名册显示已提交但明细查不到

> **只解决**：花名册/EES 该学员的"续班问卷状态"显示**已提交**（`renewalQuestionnaireStatus=3`），但按学员查"明细/学员档案-问卷"里**没有这条问卷**。
> 反向症状（明细有、花名册显示未提交/未发送）走 [`问卷已提交但花名册显示未发送.md`](问卷已提交但花名册显示未发送.md)，与本文无关。

## 判定入口

- 先拿：学员 `userId`、班级号（大班 `clazzNumber` / 前端 `clazzBizNumber`）、问卷 `questionnaireId`(=product questionnaire_number) / `projectNumber`(=bizId)。
- 两个字段各自的源头不同，**先确认是不是"明细 user_id 没归属"这一类**：
  - **花名册状态** = ES `ads_large_subclazz_user_index.renewalQuestionnaireStatus`，由 student-data-dws 消费 product 的"续班问卷回收"MQ 直接写入（匹配到 `computedUserId` 时写 3）。
  - **明细** = teacher-tool `user_questionnaire_record`，**按 `user_id` 归属**；`user_id=0` 的行不会出现在按学员查的明细里。
- 只要"明细行存在但 `user_id=0`"，本症状即成立，与本 runbook 的处置一致。

## 排查

### 1. 读两侧现状（最快）

- 花名册 ES 存值（PROD 走 SRE，见 `es-apply` skill；`_id = subclazzNumber-userId`）：
  ```bash
  # query: ids 命中 subclazzNumber-userId；看 renewalQuestionnaireStatus / studentName
  ```
- 明细（学员档案-问卷 tab 同款接口，`teacher-tool`，必须带 `traffic-env: prod`）：
  ```bash
  # POST /bgwApi/teacher-tool/questionnaire/report/list  {"userId":<userId>,"pager":{"current":1,"pageSize":20}}
  # 看返回里有没有目标 questionnaireId
  ```

### 2. 对照两张表定位是不是"user_id 没归属"

- teacher-tool 明细（cluster `gaotu-center-prod`=71，库 `gaotu`）：
  ```sql
  SELECT id,user_id,questionnaire_id,questionnaire_phone,clazz_number,project_number,
         unique_biz_id,questionnaire_group_id,registered_mobile_flag,finish_time
  FROM user_questionnaire_record
  WHERE questionnaire_id=<questionnaireId> AND questionnaire_phone='<报名手机号>';
  ```
  **`user_id=0`（而其它提交 resolved）→ 命中本 runbook。** 记下 `questionnaire_group_id`。
- product 明细源（`gaotu.questionnaire_record`，按 `number`=明细 `unique_biz_id` / `record_id`）：
  ```sql
  SELECT id,number,record_id,computed_user_id,origin_user_id,clazz_number,questionnaire_number,submit_time
  FROM questionnaire_record WHERE number=<unique_biz_id>;
  ```
  `computed_user_id` 已解析成学员 → 说明 product 是匹配上的，只是 teacher-tool 明细没跟上。

### 3. 确认根因：是否"首条 MQ 未匹配、retry 才匹配"

按 `number`（=unique_biz_id）搜 prod app 日志（窗口放宽到提交当天）：
```bash
# qingzhou get_log_v2 queryStr: "<number>"（含 - 才加引号），env=prod，logType=app
```
看两类记录：
- `MqProducerImpl ... tag:user_submit ... QuestionnaireRecordDTO(id=..., computedUserId=0, ...)`（product-task，首条未匹配）
- `DwsRenewalQuestionnaireConsumer#consume,processing,msgId is <number> ... computedUserId=0 ... noBindClazzNumbers=[...]` → `sendTeacherToolQuestionMsg start, msgDTO is TeacherToolQuestionMsgDTO(userId=0, ...)`
- 稍后第二条 `tag:compute_handler_submit ... QuestionnaireRecordDTO(... computedUserId=<userId> ...)` → dws `parseObj,normal match process` → `updateQuestionnaireStatus` → `sendTeacherToolQuestionMsg ... userId=<userId>`（同一 `uniqueBizId`）
- teacher-tool：`QuestionnaireConsumer:157 续班问卷回收，userId=0，直接插入记录` + `创建主数据成功/创建子数据成功`（首条）；后续（匹配条）`QuestionnaireConsumer:201 续班问卷回收, 不存在旧记录, 继续处理` 可能重复多次。

两条都命中且 `uniqueBizId`/`questionnaire_group_id` 相同 → 坐实"明细先以 userId=0 落库、匹配条因唯一键冲突未回填"。判据：
- `SHOW INDEX FROM user_questionnaire_record` → 唯一键 **`uq_account_id_unique_biz_id (account_id, unique_biz_id)`**：首条已占 `(account_id, unique_biz_id)`，匹配条同键 → insert 撞唯一键、也不会更新既有行 → 明细停在 `user_id=0`（teacher-tool 常无 error 日志）。
- 时间线用提交时间 → 匹配条 `compute_handler_submit` 的 `updateTime` 相减（本案例 ≈ **18 分钟**）：这 18 分钟就是"未匹配明细"已落库、正确 userId 尚未到的窗口。**瓶颈不是时长，是"未匹配也落明细 + 事后不回填"**——缩短时长也不能可靠消除竞态。
- 消费端"该跳未跳"：Apollo `student-data` `dws.renewal.question.not.consume.tags`（默认 `[cds_no_user_submit]`）只跳过"无用户"tag；若首条 tag 是 `user_submit`（不在名单），dws 就会按正常提交处理。

### 4. 旁证

- `dws` 的 `queryRenewalQuestionnaireStatus(clazzNumber,userId)`（走 teacher-tool 明细 + 触达）会返回 **未发送/未提交**，与花名册 ES 的 **3** 不一致 —— 正是"两条链路不一致"的旁证。
- 手机号 → userId 直查：`IdQueryAclService#queryUserInfoByRelatedId(["<手机号>"],1)` 若为空，说明报名手机号不是可直查的注册手机号（product 靠姓名等规则才匹配）。

### 5. 处置

- **单条修复（PROD 写，需授权）**：把该组明细回填 user_id：
  ```sql
  -- 预览：SELECT id,user_id,clazz_number FROM user_questionnaire_record WHERE questionnaire_group_id=<group>;
  UPDATE user_questionnaire_record SET user_id=<userId> WHERE questionnaire_group_id=<group>;  -- 或仅 clazz_number=<本班> 那条
  ```
  回填后直调 `teacher-tool/questionnaire/report/list` 验证目标 questionnaireId 出现。
- **系统性修复（找 product-server / student-data-dws / teacher-tool 侧）**，三者任一即可闭环：① product 把"未匹配到学员"的提交打 `cds_no_user_submit`（dws 已跳过该 tag），别打 `user_submit`；② dws 在 `computedUserId=0` 时不发 `sendTeacherToolQuestionMsg`（不落未归属明细）；③ teacher-tool 收到带 userId 的重复消息时按 `questionnaire_group_id`/`unique_biz_id` **UPDATE 回填 user_id**（而非 insert 撞唯一键后跳过）。否则凡"首条 MQ 未匹配、稍后 compute 才匹配"的提交都在 ~18 分钟级窗口内命中本问题。

## 验证

- 明细接口 `/bgwApi/teacher-tool/questionnaire/report/list` 返回里出现目标 questionnaireId（statusDesc=已完成）才算修好；只看 `user_questionnaire_record` 的 UPDATE 行数不算。
- 若未做写操作，只报告：花名册 ES=3（已提交正确）、明细行 user_id=0（未归属）、根因=首条 MQ 未匹配。
