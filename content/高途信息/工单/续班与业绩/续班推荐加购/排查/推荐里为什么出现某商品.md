# 续班推荐加购 · 推荐里为什么出现某个商品

> **只解决**：学员续班推荐里出现了某个商品/组合/联报，要查它从哪来、为什么被推。
> 推荐完全不出/只出一部分走 [`续班链接加购商品不展示.md`](续班链接加购商品不展示.md)；在读学员无纯续走 [`在读学员纯续推荐缺失或提示未报名.md`](在读学员纯续推荐缺失或提示未报名.md)。
> 业务口径（纯续/扩科/推荐排除三类）见知识库 [续班推荐业务逻辑（纯续-扩科-推荐排除）](../../../../知识库/续班科目/续班推荐业务逻辑（纯续-扩科-推荐排除）.md)；推荐**收口在 cart**，student-data 不出推荐。

## 判定入口

- 需要三个对象：`userId`、`班级号(clazzNumber)`、`商品号(SPU/productSpuNumber 或 productNumber)`。
- 推荐列表 = **纯续 + 扩科 + 加购**；先粗归类，再落到配置/关系表。
- 期次：小班计划可能因 **【纯续关联】(EM关联)** 把"从计划"的纯续并进来（2026-11 上线），所以商品来自"非本计划"的前置课是正常的关联行为。

## 排查

### 1. 班级 → 续班计划
- 小班班级号即商品 SKU 号：`gaotu.product_sku`（cluster_id=71 `gaotu-center-prod`, db `gaotu`）`where product_sku_number=<班级号>` 取 `product_spu_number`（=前置课程号）。
- 用该 SPU 反查计划：`gaotu.renew_master_course_relation` `where pre_course_number=<SPU>` → `renew_master_number`（`isdel=0`）。
- 大班课程号直接用 `course_center.course`（cluster_id=317 `gaotu-course-prod`, db `course_center`）确认。

### 2. 复现推荐（看商品在不在、类型）
- B 端：`invoke_http(project="product-b", route="/product-b/b", path="/renewMaster/recommendProductList", body={"renewMasterNumber":"<计划>","userId":"<学员>"}, traffic_env="prod")`
  - 返回项含 `productNumber`(SKU) / `productSpuNumber` / `productType`（2 大班 / 23 联报 / 51 组合 / 6004 小班 / 8014 券）。**只看返回，不含 recommendType**。
- 要 recommendType 用 cart 7 参 `getRenewalDetail`（线下）；线上 cart acl 桥未启用，改用日志按 traceId 看 `listRenewalMasterByRenewalNumber` 返回。

### 3. 归类来源
- **扩科**：`gaotu.renewal_expand_subject_recommend` `where renewal_number=<计划> and product_number=<商品号>`（配置是 (grade, subject, product_type, product_number)，按计划读）。
- **加购**：`gaotu.node_config` type=3 的 `productNumberList` / 推荐节点配置。
- **纯续（后置课程）**：course-center 续班关系 `course_center.course_relation_map`
  `where relation_number=<前置课程号>`：`course_number`=后置课程号，`relation_type=1`(续报课程)、`calculate_renewal_type=1` 才算可续，`isdel=0`。
  - 组合(51)商品的真实子课在 `gaotu.product_sku_combine`（`combine_product_spu_number`），把子课号拿到 `course_relation_map` 里对 `relation_number`（前置）。
- **关联并集**：`gaotu.renew_master_relation` `where main_renew_master_number=<计划> or sub_renew_master_number=<计划>`（`is_del=0`）→ 关联计划号；若商品后置对应的**前置课属于关联的从计划**（不在主计划的 `renew_master_course_relation` 里），则来源=关联并集。cart 侧日志：计划返回体 `related_renew_master_numbers=[...]` + `listRenewalMasterPreCoursesByNumbers renewalNumbers is：[...]`。

### 4. 确认前置课是学员在读
- 大班：`gaotu.subclazz_student` `where user_id=<学员> and course_number=<前置课> and isdel=0`，`status=1` 在读。

### 4b. 生产大表横向分析前先看索引（2026-11-13 教训）
- `course_center.course_relation_map`（约 52 万行）只有 `PRIMARY(id)` / `idx_relation_number` / `idx_course_number` 三个索引；**isdel / calculate_renewal_type / relation_type 均无索引**——按前置/后置号点查走索引，任何"按可续标记过滤"的横向分析查询注定全表扫。
- 跑批量分析前先 `SHOW INDEX` + `EXPLAIN` 评估；`IN (子查询)` 改写优化器仍会选全扫（选择性不足），初一(7阶)课程号本身 1000+ 门、字面量 IN 列表也不现实——52 万行单次全扫秒级、只读一致性读不锁业务，**低峰期跑一次可接受**，但要避免反复跑和大 offset。需要高频分析时走 DDL 工单加联合索引（需授权）。
- `course_center.course` 约 27.6 万行，`number` 有唯一索引 `unq_number`；按名称 LIKE 匹配阶数（`%7阶%/%七阶%`）是全扫，单独跑一次可接受。

### 5. 商品状态核对
- `gaotu.product_spu` / `gaotu.product_sku` 的 `sale_status`（40 可售 / 50 不可售/停售）+ `stop_sale_time`。推荐出的是停售商品时，作为"是否该过滤"的疑点上报产品，而非断言 bug。

## 扩科/联报为什么没匹配到（用户说"某类联报没出"）

先确认**这条推荐是按哪个计划算的**——同一学员、同一时点，主计划与从计划结果可能完全不同（实测：小班主计划出青藤联报，大班从计划出大班联报）。B 端 `recommendProductList` 的入参 `renewMasterNumber` 决定口径。

- **扩科只取主计划自身**：`ExpandSubjectRecommendService` 的 `recommendList` 来自主计划 `expandSubjectConfig`；年级收口 `collectStudentPostGrades` 与"当前课程" `resolveCurrentCourse` 都按 `mainOwnPreCourseNumbers`（主计划自身前置课），排除从计划并集部分。
- **【纯续关联】只并纯续、不并扩科**：`relatedRenewMasterNumbers`（计划返回体、日志 `EM pure relation merged courseNumbers`）只进 `SmallRenewalCoreService` 的纯续；从计划的扩科/联报不会并入。→ 学员在从计划（如大班）的联报，不会出现在主计划（如小班）的推荐里。
- **推荐排除**（`excludeMode=1`）：小班计划排除"大班在读"学科、大班计划排除"小班在读"学科。排除集口径 = 与当前（前置）课程**同学年+学期**，学期取**前置课**的 term（2026 秋 = `Q`，别错用 `C`）。可用 student-data acl 桥直读：
  `com.gaotu.student.data.domain.service.RenewalInReadSubjectService#listOtherModeInReadSubjects`，params `[userId, currentRoomType, schoolYearId, schoolTermId]`（小班=2 / 大班=1）。
- 另：B 端会过滤已购（`signUp==1`），扩科候选被学员买过时不返回。

## 验证

- 能复现：B 端接口返回里确实有该商品。
- 能指向：目标商品 → 具体前置课 →（配置行 / course_relation_map 行 / 关联计划）一条链闭合。
- 前置课确实为学员在读，且 `calculate_renewal_type=1`、`isdel=0`。
- 不能只凭"接口没返回某个商品"断定推荐没算出来（B 端会过滤已购 `signUp==1`）。
