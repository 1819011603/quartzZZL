# 续班推荐加购 · 在读学员纯续推荐缺失或提示未报名

> **只解决**：学员有在读订单，纯续链接只推荐部分课程或无课程，页面提示非在读。
> B端加购未展示走 [续班链接加购商品不展示](续班链接加购商品不展示.md)。

## 判定入口

先确定计划、学员userId、真实请求时间、B端预览还是C端入口，并取得线上实际镜像提交。不能用本地开发分支代替线上代码，也不能根据页面“非在读”文案反推没有订单。

## 排查

1. 用mysql-query按订单号核对userId及有效状态，按课程号确认年级科目；用户一次可能购买多个年级，必须按计划分别取前置订单。
2. **小班课(6004)计划先查「赠课订单过滤」**（最常见的「纯续链接无课程」原因）：小班推荐走 `SmallRenewalCoreService#recommendAll` 的 builder 责任链（`cart-app/.../renewal/small/builder/`）。`GiftOrderFilterSubBuilder`（order=25）会把支付渠道 `payChannel=30`（BOSS赠送/赠课）的订单整体剔除，**赠课订单不算可续前置订单**。若学员订单全是赠课 → 前置班级/续班关系构建失败 → 无后置课程可推 → C 端「暂无可报名课程」。判据：查 cart 日志（服务名 `cart-gaotu100-com`，用 traceId 或 userId 定位）出现 `GiftOrderFilterSubBuilder:69 赠课订单过滤, filteredCount=N, remainCount=0`，随后 `PreClassInfoBuildSubBuilder:42 没有订单信息，无法构建前置班级`、`RenewalRelationMapBuildSubBuilder 没有前置课程编号`、`ClazzInfoQuerySubBuilder 没有查询到任何班级信息`。开关 `renewal.small.gift.order.filter.enabled`（默认 true）。属设计行为，非 bug。
2b. **小班(6004)「转换推荐结果失败」导致整单返回空**（2026-11-06 案例，同症不同因）：若逻辑**已算出**候选（`SmallRenewalCoreService:149 续班推荐完成 resultCount>0`）但 B端/C端仍空，查 cart 日志是否 `RenewalService:3767 转换推荐结果失败 java.lang.IllegalStateException: Duplicate key ClazzSetVO(number=...)`。根因=扩科配置把**同一联报 SKU(`productType=23`) 配到多个年级** → 推荐合并后同一联报编号重复 → `RenewalService#convertToRenewalCartVO` 收集 `allActivityNumbers` 未去重、`listClazzSetInfoByNumbersWithCache` 逐条返回重复 VO、`Collectors.toMap(ClazzSetVO::getNumber, ...)` 无 merge 函数 → 抛错被吞、返回不含 `gradeClazzList` 的空 VO。**属缺陷**（修法：`allActivityNumbers.distinct()` 或 toMap 加 merge 保留首个）。判据日志：`RenewalDataService:233 listClazzSetInfoByNumbersWithCache` 返回列表存在重复 `number`。复现：`POST /product-b/b/renewMaster/recommendProductList`（`b_client: EES`）。**已修复**（2026-11-06 分支 `feature-renewal-clazzset-dedup`/`a37f1067`）：`listClazzSetInfoByNumbersWithCache` 出口按 `number` 去重（保留首个）+ `convertToRenewalCartVO` 的 toMap 补 merge。**同源根因线索**：`RenewalDataService` 的同类 loader `getClazzByClazzNumbersWithCache`(L259)、`getCourseByNumbersWithCache`(L380) 都早已对入参 `.distinct()`，**唯独 `listClazzSetInfoByNumbersWithCache` 漏了去重**——它就是这个模式里唯一缺失的一环。`getCombinedDTOsBySkuNumbersWithCache`(L602)、`getSingleProductsByClazzNumbersWithCache`(L628) 同样缺入参去重，暂未触发（调用方当前去重/用 put 覆盖），属同类潜在隐患。
3. 用traceid-debug查真实请求。大班 cart日志的 `renewal-data-from-coreHandle-hit` 为空代表未命中预热缓存；`preCourseOrderInfoDTOS` 可证明前置订单已进入推荐。拿完整trace再查 `RenewalDataService`，不能只查 `RenewalService`，联报数据日志在另一个类。小班(6004)则先看 `SmallRenewalCoreService` 与各 `*SubBuilder` 日志。
4. 新模板 `recommendMapType=2`、`productType=23` 时，`RenewalService#coreHandle` 取 `renewalRecommendMap[前置班级号]` 的指定联报。配置了联报ID只证明有映射，还需过计划商品池、子班与后置候选交集、联报状态/库存、已购子班等条件。白名单指定联报失败时不自动改荐其它联报。
5. 在对应提交核对 `handleWhitelistClazzSet` → `isClazzSetCanRecommend`：联报为空、库存为空或≤0均过滤；`fromBCart=false` 时还排除 `ActivityStatus.NO_SELLING`（status=3，停止招生）。`status=1` 为未上架。注意后台“联报状态”对应status，“售卖状态”对应saleStatus，两字段独立；实际数据可同时出现status=3与saleStatus=1（可售卖）。必须向业务确认要限制哪个字段，不能从当前实现或枚举注释反推业务要求。
6. 同一trace的 `RenewalDataService#listClazzSetInfoByNumbersWithCache` 会记录联报number/name/status/statusName/remainCount，可逐项对照。日志查询无userId时用trace限定；原始日志含请求头时落临时文件并只提取最少字段，不复制Cookie或令牌。
7. `/web/renewal/cart` 调7参重载，`/web/renewal/operation/cart` 调5参重载；后者 `fromC` 决定fromBCart，必须按真实入口核对。桥功能关闭不应改生产配置开启；页面重放被CAS挡住时保留真实历史日志证据，标明未完成实时重放。

## 验证

需要同时证明：前置订单命中、前置班→指定联报映射、实际读取的联报状态/售卖状态/库存、线上对应提交的过滤条件、最终推荐与页面现象一致。仅有联报ID或库存充足不能证明可推荐。小班计划若 `remainCount=0` 且日志显示「赠课订单过滤」把订单全剔除，即证明是赠课学员无有效前置订单（设计行为）；此时不要把「赠课订单应否参与纯续」当成 bug，改该过滤属业务变更。若业务确认按售卖状态，应检查代码是否误用了联报状态，不能直接要求改招生状态；修改需获授权并从原入口核验逐科推荐。问“谁改的”时先对生产提交git blame，再用git log -S及git show追溯字段切换diff，区分原始规则、新模板沿用、Author/Committer和提交/上线时间。
