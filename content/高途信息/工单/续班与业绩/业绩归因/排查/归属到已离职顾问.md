# 业绩归因 · 订单业绩归属到已离职顾问

> **只解决**：订单已判单、业绩归属人是一个已离职员工。
> 查不到归属人 / 归属人为空走 [`查不到归属人.md`](查不到归属人.md)；
> 已落库但排行榜显示 0 走 [`判单正常但排行榜显示0.md`](判单正常但排行榜显示0.md)。

## 判定入口

先确认三件事，再判断是「数据没回收」还是「判单逻辑没过滤」：

1. 归属人是谁、走的哪条判单策略
2. 该员工当前在职状态
3. 归属来源（sellerId / CRM 线索 / 私海）是否仍有效

## 排查

### 1. 看归属人 + 判单场景

```sql
-- 成人业务
SELECT order_number, user_id, employee_id, employee_email, employee_scene, leads_id, private_sea_id, trade_status
FROM gaotu_stat.performance_order_attribution_adult
WHERE order_number = '<订单号>';

-- K12 / 汇总
SELECT order_number, user_id, employee_id, employee_email, pre_employee_id, trade_status
FROM gaotu_stat.performance_order_attribution_total
WHERE order_number = '<订单号>';
```

`employee_scene`：4 = CRM 线索归属，5 = 非二讲 sellerId，3 = 二讲 sellerId。成人订单一般在 `performance_order_attribution_adult`。

判单原因表里有完整的步骤链和归属结果：

```sql
SELECT scene, employee_result, create_time
FROM gaotu_stat.performance_attribution_judge_reason
WHERE order_number = '<订单号>' ORDER BY create_time DESC;
```

`employee_result` 里重点看：

- `employeeId` / `employeeScene` / `leadsId` / `privateSeaId`
- `sellerId是否存在`、`sellerId角色是否为辅导`：角色不是二讲（492/948/1209/1210）时不会用销售链接的出单人
- `crm潜客/线索是否存在客户或成单`、`crm潜客/我的线索状态线索是否只有一个`：命中旧私海时直接取私海归属人

### 2. 查员工在职状态

```sql
SELECT id, account_id, email_prefix, status, update_time
FROM gaotu.employee
WHERE id = <employee_id>;
```

`status`：1 在职，2 离职。注意 `gaotu.employee` 在 `gaotu-center-prod`（cluster 71）。

### 3. 查归属来源是否还挂在离职员工名下

CRM 私海详情（线上网关，私海 ID 直接用字符串避免精度丢失）：

```bash
POST /bgwApi/crmApp/ols/w/privateSeaV2/getPrivateSeaDetailsByPrivateSeaId
{"privateSeaId":"<私海ID>","leadsId":"<线索ID>"}
```

返回里看 `accountId` / `accountName`（当前归属人）、`followState`（6=成单）、`saleFlowStage`。私海还在离职员工名下、且是成单/我的线索状态，判单就会命中它。

### 4. 对代码：CRM 判单是否过滤离职

成人 CRM 归属在 `performance-attribution` 仓库：

- `performance-attribution-domain/.../strategy/employeeid/EmployeeIdFromCrm.java`
  - `:143` 走 CRM 分支
  - `:295 getAttributionEmployeeResultsFromCrm`
  - `:326 getFollowUpLeads(userId, thirdLevelId, courseNumber)`
  - `:360` / `:375` 直接取线索的 `employeeId` 返回，**不校验员工状态**
- OMO 分支 `OmoEmployeeIdFromCrm.java` 同样没有状态校验

`TeacherFeignService#isOnJobByEmployeeId` 存在，但只被业绩补偿/续班口径使用，**判单主链路没有调用**。

## 影响面扫描（批量）

单笔确认后，按「近 N 天成人实付订单 × 当前离职员工」扫一遍：

1. 从 `gaotu_stat.performance_order_attribution_adult` 取时间窗内 `trade_status=1 AND isdel=0 AND employee_id>0` 的 `employee_id` 去重列表（DMS 单次结果有 1000 行上限，用 `JSON_ARRAYAGG` 或分页取全）。
2. 用 `gaotu.employee`（cluster 71）按批次查 `id IN (...)`，保留 `status=2`。
3. 回到成人表按这批 id 聚合：
   - `COUNT(*)` / `SUM(employee_scene=4)`：时间窗内全部归属
   - `SUM(trade_time > 员工记录 update_time)`：状态变更后归属（`employee_id` 到日期的映射可用 `CASE employee_id WHEN ... THEN ... END`）
4. 按 `account_id` 再查一次 `status=1`：同 account 有在职新 id 的，归为「重新入职旧 id」，与真正离职分开统计。

注意：`gaotu.employee.update_time` 是记录最后更新时间，**不是正式离职日期**，只能作为近似；结果用于判断影响面量级，不能直接作为结算/追回依据。

## 验证

- 归属人确实 `status=2`，且 `employee_result` 的场景/线索/私海与业绩表一致；
- CRM 私海仍 `is_del=0`、归属离职员工、阶段为成单/我的线索；
- 代码路径确认没有在职校验（不是「状态查了但被别的逻辑覆盖」）。

结论成立后，处置分两层：上游 CRM 是否应在离职时回收私海/线索；判单是否需要在命中线索归属人时做离职兜底。两者都属于业务规则变更，需产品确认后再动。
