# 业绩归因 · 已设为不可续但页面/导出显示可续

> **只解决**：运营在续班计划「管理可续学员」把学员设为「不可续」（续班灰名单）后，页面/导出又显示「可续」，且再次设置报「该用户已被设置为不可续，无需重复设置」。
> 学员被判成不可续（相反方向，页面该显示可续却显示不可续）走 [`可续状态判不可续.md`](可续状态判不可续.md)。

## 判定入口

- 展示口径：`b/renewal/manage/student/list`（product-server `RenewalStudentService#studentList`）的「可续状态 / 灰名单类型」**只看可续标记表** `gaotu_stat.performance_regular_can_renewal_sign_x.can_renewal_status`：=17(`不可续-续班配置灰名单`) → 不可续，其它 → 可续；与灰名单配置表无关。
- 灰名单配置：`gaotu_stat.can_renewal_config`（cluster 259）：`status=1(生效)` + `type=0(不可续)`。
- 报错来源：performance-attribution `CanRenewalServiceImpl#batchSetCanRenewalConfig`（type=0）发现该订单 config 已 `status=1 & type=0` → 直接返回「该用户已被设置为不可续，无需重复设置」。
- **不一致判据**：`can_renewal_config` 里该订单 `status=1 & type=0`，但 `sign_x.can_renewal_status != 17`（常见=1 可续）→ 本症状。

## 排查

1. 按学员查两处（cluster 259 / `gaotu_stat`）：
   ```sql
   -- 灰名单配置
   SELECT order_number,user_id,subclazz_number,status,type,last_can_renewal_status,msg,create_time,update_time
   FROM gaotu_stat.can_renewal_config WHERE user_id IN (<学员ID>);
   -- 可续标记
   SELECT order_number,can_renewal_status,round_idx,create_time,update_time
   FROM gaotu_stat.performance_regular_can_renewal_sign_x WHERE order_number IN (<上一步 order_number>);
   ```
   配置 `status=1,type=0` 而标记 `!=17` 即命中。
2. **为何标记被冲掉且不再恢复**：
   - 每日可续标记任务 `RenewalOrderSignHandler`（`doSign`，job 3297）只重算标记、**不套灰名单**。
   - 灰名单回套在单独任务 `RenewalOrderGreyUserCorrectHandler`（job 9593，父任务链式触发），时间窗固定 **[今天 00:00, 明天)**，按 `sign_x.create_time` 过滤（`getMinMaxIdByTimePeriod`）。
   - 因此：**在当天灰名单修正任务跑完之后才「新建/刷新」的 sign_x 行，当天不再被扫；后续每天窗口都按 `create_time=当天`，永远扫不到这批旧 create_time 的行** → 灰名单永久失效，页面/导出按 sign_x 显示可续。
   - 触发这种「任务跑完之后才写标记」的情形：当日标记任务跑得很晚/跨小时（大促异步队列积压），或订单事件/回溯在傍晚重算该订单标记。
3. 区分「标记未生成」（该订单 sign_x 0 行）——那走 [`可续状态判不可续.md`](可续状态判不可续.md)。

## 处置

- **按订单重新回溯**（走 `CanRenewalServiceImpl#renewalOrderCanRenewalBack`，链尾 `correctGreyUserCanRenewalStatus(orderNumbers, null, null, ...)` 时间窗为 null，会重新套 17）：用「订单可续回溯」页（`/ark/app-yunfan/orderRecall`）或对这批订单跑一次灰名单修正。回溯后 sign_x=17、页面恢复不可续、即可再设置。
- 根治在 performance-attribution：sign 任务直接套灰名单，或灰名单修正按 `update_time` / 覆盖足够时间窗，而不是只按 `create_time=当天`。

## 验证

- 回读 `sign_x.can_renewal_status=17`（`update_time` 变新），且页面「可续状态」= 不可续。
- 只 config 存在 ≠ 生效：必须 sign_x=17；`canRenewalSignReason` 的 `signResult` 应与之一致。
