# 业绩归因 · 大班续班服务里「在班」学员查不到 / 可续学员数比花名册少

> **只解决**：大班续班服务页（`clazzRosterOL` 的 continuationService tab）某个「在班」学员查不到、顶部「可续学员数」比花名册少（差 1~几个），而**判单与花名册都是对的**。
> 「学员被判不可续」（可续字段本身错，如 `不可续-无续班关系`）走 [`可续状态判不可续.md`](可续状态判不可续.md)；花名册/续班服务「在读科目数」偏多走 `../续班保障/在读科目比实际多.md`。

## 判定入口

大班续班服务页读 ES 索引 **`ads_large_subclazz_user_index`**（ees 集群 `es-cn-smw4b9m200004w3hn`，bean `studentSubclazzClient`），文档 `_id = subclazzNumber-userId`。查询用 `es-apply` skill 的 `es_workorder.py search`（prod 只能走它）。

关键字段（口径见 `知识库/cronus/clazzRosterOL/continuationService.md`）：

| 字段 | 维度 | 值 |
|---|---|---|
| `clazzStudentStatus` | **班级**（在读状态） | 1 在读 / 0 退班 |
| `subclazzStudentStatus` | **辅导班**（是否本人辅导班） | 1 在 / 2 不在 |

合法组合（`StudentSubStatusEnum`，student-data-client）：
`(1,1)` 在读且本人辅导班 / `(1,2)` 在读非本人辅导班 / `(0,2)` 退款；
**枚举里没有 `(0,1)` —— 出现即非法态**。

## 排查

1. 拿报障学员 `(subclazzNumber, userId)` 读该索引，看 `clazzStudentStatus` / `subclazzStudentStatus` / `canRenewal`：
   - **`clazzStudentStatus=0` 且 `subclazzStudentStatus=1`（非法态 (0,1)）** → 命中本问题：该学员被退班事件误清成「退班」，续班服务按 `clazzStudentStatus` 过滤在班 → 漏掉。
2. 对照大班**花名册**索引 `ads_large_clazz_user_<年>`（studentServe 集群 `es-cn-4xl3gu6ls0007l185`）同一 `(clazzNumber,userId)` 的 `clazzStudentStatus`：本问题下花名册通常 =1（与续班服务不一致）。
3. 核对页面「可续学员数」口径：`canRenewal ∈ {1,2,8} 且 clazzStudentStatus=1` 的条数即页面数；与本班花名册在班数差 1（或几个）就是这些学员。
4. 看源头（课程分发）该学员是否仍在该班级下有在班辅导班：acl 桥 `ClazzDistributionSyncAclService#listSubclazzStudentByUserIdsAndClazzNumber([userId], clazzNumber, [1,2,3])`（走 `baijia-invoke` 的 `invoke_service`）。有 status=1 的在班辅导班却 `css=0` → 确认误清。
5. 影响面（全体）：查 `subclazzStudentStatus=1 且 clazzStudentStatus=0` 的文档数，并按 `clazzNumber` 聚合得到待修班级清单。

## 根因（代码）

`SubclazzUserSyncConsumer`（student-data-dws，MQ tag `TAG_Subclazz_Quit` → `quitClazz`）：
- 原 `quitClazz()` 用 **`UserClazzDimension`（班级维度）广播**，经 `UserClazzConvertUserSubclazzService.convert` 展开成该学员在该班级下**所有**辅导班文档，一起写 `clazzStudentStatus=0` → 把同班其它**仍在班**的辅导班文档也误清（其 `subclazzStudentStatus` 仍=1 → 非法态 (0,1)）。
- 情境：学员**同一班级下有 ≥2 条辅导班关系**（同班换辅导班、赠课/正价并存等），且「退老辅导班」的事件在「进新辅导班」之后被消费（两事件属不同 shardingKey、跨 key 无序）→ 新辅导班的在班标志被清。故**很偶发、量少**。
- 权威口径在 `SubclazzTransferStudentDataQueryServiceV2`（**由字段 `transClazzStudentStatus` 触发**；该字段**不是真实存储字段**，只是触发名，文档里查出来是 null）：`clazzStudentStatus = 该班级下是否还有 status=1 的辅导班`。

## 修复

- **数据**：按班跑 **type=13 速达回溯**（`QuickBackAdsSubClazzUserWorker` / `AdsSubclazzUserBackService#dealClazz`）。入口二选一：`ees_data.back_quick_task` 写 `type=13, clazz_numbers=<班号>` 后跑 `QuickBackJobHandler#execute`；或 xjob。回溯字段集含 `transClazzStudentStatus` → 触发上面的 query service 按源头重算 `clazzStudentStatus`（`sss` 一并重写）。批量按 `clazzNumbers` 分批（每批 ≤ 池上限，prod=10）。回溯较慢（实测大班约 40 学员/秒），大班多的批次要排期。
- **代码**：`quitClazz` 改为「退班时用 `DataContext(transClazzStudentStatus,"ods")` 重算 `clazzStudentStatus`，再按班级维度广播该值」——与官方富化一致、同班同人一致、与事件顺序无关；开关 `subclazz.user.sync.quitClazz.recompute.switch`（默认 true，置 false 回滚原盲写）。

## 验证

- 回溯真生效的判据是**读回目标文档字段**（`clazzStudentStatus` 变 1、`(sss=1,css=0)` 归零、页面可续数对齐），不是接口 200 / 任务创建成功 / pipeline SUCCESS。
- 只改一个班时，对比改前改后同一条文档同字段。
