# 业绩归因 · 业绩类型为什么是召回/扩科而不是续班（判单顺序）

> **只解决**：某订单最终业绩类型(`renewal_type`)为什么不是预期类型——「为什么是召回/新签不是扩科」「为什么是扩科不是续班」等，以及要复现任意一单的完整判单过程。
> 业绩表查不到这单 / 归属人为空走 [`查不到归属人.md`](查不到归属人.md)；
> 判单正常但排行榜显示 0 走 [`判单正常但排行榜显示0.md`](判单正常但排行榜显示0.md)。

## 一句话结论

判单**按优先级顺序**依次尝试：`续班(1) → 扩科(2) → 召回(3) → 新签(4)`，**首个命中的类型即最终类型**（命中即停，不再往后判）。
所以「为什么不是扩科」= **扩科的三道筛没全过**，而更低优先级的召回/新签恰好过了。

## 通用判单顺序与各类型筛选逻辑

规则来自 `gaotu_stat.performance_attribution_rules_config`（prod cluster 259），按 `biz_line / operation_mode / product_type` 匹配，`priority` 升序执行：

| priority | type | 类型 | 筛选步骤（全过才命中） | 命中后归属人 |
|---|---|---|---|---|
| 1 | 1 | 续班 | 保护期筛选 → 续班关系筛选(前置续班课程) | 前置订单二讲老师 |
| 2 | 2 | 扩科 | 保护期筛选 → 续班关系筛选 → **同辅导筛选** | 前置订单二讲老师 |
| 3 | 3 | 召回 | 拉召筛选(`newOrRecallRestrain=true`) | **sellerId** |
| 4 | 4 | 新签 | 拉召筛选 | sellerId |

各步语义：

- **保护期筛选**：只保留处于保护期内的前置订单（班级保护期配置 / 订单保护期）。
- **续班关系筛选**（续班、扩科共用）：
  - 前置班型 ∈ {长期班 `REGULAR`(1), 入口班 `ENTRANCE`(2)}：按 `前置订单 courseNumber ∈ beforeCourseList` 命中（`RenewalRelationByCourseConfigStrategy:48`）。
  - 前置班型 = 短期班 `CERES`(3)：后置课是**系列课**时按 同学科 `subjectId` + 同学部 `departmentId`（**不校验年级**）；非系列课时按 同学科 + 同主讲 —— **或** 命中 `beforeCourseList`。
  - `beforeCourseList` = **后置课**（本订单的课程）在 `course-setting`.`course_extension` 里 `extension_type=3`（`CourseExtensionTypeEnum.FOLLOW_COURSE`「续报课程」）配置的课程号集合（**在线支付判单**据此判定）。
  - 另有 `course-center`.`course_relation_map`（`relation_type=1` 续班关系）—— **回溯判单**据此判定。**两者是两处配置、可能不同步**：只补一处会出现「回溯已改判续班、新支付单仍判扩科」（2026-10-30 预报名案例即此）。
- **同辅导筛选**（仅扩科）：只保留「**前置订单的二讲老师 == 本单销售(seller)**」的前置订单。
- **拉召筛选**（召回、新签共用）：保留「支付时间在本单支付前 365 天内的正价课 + 180 天内的体验课」。

**扩科的两个关键特性（最易误判）**：

1. 扩科要求**续班关系筛选为空**才继续。若续班关系已满足，该单会归「续班」（priority 1 先命中），扩科直接判未命中（`ExtendPerformanceAttributionStrategy.java:70-73`）。
2. 扩科命中 = 续班关系不满足 **且** 同辅导满足。**同辅导要求前置订单的辅导老师就是卖这单的人**——只认「卖单的人自己名下」的前置订单，不是学员名下所有前置订单。

## 预报名单为什么不是续班（后置课=预报名专题课）

预报名订单的**后置课**是那门「2027寒春预报名【20抵120】（高三|X）」专题课（`course_type=30`），不是寒春正课。前置是学员的秋季正课（长期班 `pre_clazz_type=1`）。要判续班，就得让**预报名课**与学员秋季课之间存在续班关系（见下两处）。常见卡点：

1. 该预报名课**缺**与学员所在秋季课的续班关系（如漏配/误删「目标一本班」）→ 续班关系筛选为空 → 落扩科。
2. 关系只补进 `course_relation_map`(course-center) 而 `course_extension`(course-setting, type=3) **未同步** → **回溯**会判续班、但**新支付单仍判扩科**（两处来源不同，见上）。

核对（prod）：

```sql
-- 在线支付判单读取：后置课的前置续班课程（course-setting, cluster 71 gaotu）
SELECT number, extension_value, isdel FROM gaotu.course_extension
WHERE number = <预报名课号> AND extension_type = 3 AND isdel = 0;
-- 若学员前置秋季课号不在结果里 → 新支付单续班必未命中

-- 回溯判单读取：course-center 的续班关系（cluster 317 course_center）
SELECT relation_number, calculate_renewal_type, isdel FROM course_center.course_relation_map
WHERE course_number = <预报名课号> AND isdel = 0;
```

判据：把 `pre_order_detail` 里该学员的前置秋季**课号**分别与上面两处集合比对；不在则对应链路判不出续班。

**正常同步链路**（两处本应一致）：course-center 是关系主库，编辑「续报课程」→ 写 `course_relation_map`(relation_type 1) 并发 MQ `course_relation_change`（`relationType=FOLLOW_COURSE` 时另发 `course_follow_change`，见 `OuterDomainEventSendListener#handler(CourseRelationEvent)`）→ course-center 同步框架 `CourseRelationFieldEventTrigger` 消费 → `CourseCenterCourseEntity#buildSettingCourseExtension`（:221-228，relation_type 1→ext 3、0→ext 2）写 course-setting `course_extension`。两处不一致 = 该 MQ→sync 没跑（不发消息的批量改 / 消费失败 / sync 异常），排查时查 `course_relation_change` 消息轨迹与该同步消费日志。

## 排查（复现任意一单的判单过程）

```sql
-- 1) 最终业绩类型 + 归属人（cluster 259）
SELECT order_number, renewal_type, pre_order_number, pre_clazz_type, employee_email, real_price, trade_status
FROM gaotu_stat.performance_order_attribution WHERE order_number = <订单号>;

-- 2) 完整判单过程（每个策略、每一步的满足集合）——决定性证据
SELECT scene, rule_result, employee_result, pre_order_detail
FROM gaotu_stat.performance_attribution_judge_reason WHERE order_number = <订单号>;
-- scene: 1待支付 / 2支付 / 3回溯 / 4申诉 / 5调课；字段是 rule_result（不是 strategy_judge_reason）

-- 3) 本单适用规则与优先级
SELECT type, priority, type_config, pre_order_number_config, employee_config
FROM gaotu_stat.performance_attribution_rules_config
WHERE biz_line=<biz_line> AND operation_mode=<operation_mode> AND product_type=<product_type>
ORDER BY priority;
```

读 `rule_result`（JSON 数组，按策略顺序）：

- 每个策略有 `strategyJudgeResult`（命中/未命中）；
- `stepJudgeResults[].isStepSatisfied` + `satisfiedOrderNumbers` 就是每一步的筛选结果——**第一个出现「不满足」的步骤就是该类型未命中的卡点**；
- `pre_order_detail` 里每条前置订单带 `preAssistantEmailPrefix`（二讲老师），可直接和本单 seller 对比验证「同辅导」。

## 验证

- 结论必须由 `performance_attribution_judge_reason` 的 `rule_result` 逐步证据支撑，不能只凭最终 `renewal_type` 反推。
- 说「不是扩科」必须指出扩科**具体卡在哪一步**（保护期 / 续班关系 / 同辅导），以及该步的 `satisfiedOrderNumbers` 为空。
- 归属人核对：召回/新签取 `sellerId`；续班/扩科取前置订单二讲老师。

- 续班关系细则：`attributionType/renewalRelation/RenewalRelationByCourseConfigStrategy`（长期班/入口班走 `beforeCourseList` :48，短期班系列课 :68-81）；`beforeCourseList` 来源 `syncGetCourseExtensionVOList(courseNumberList, 3)`（`CourseExtensionTypeEnum.FOLLOW_COURSE`「续报课程」）。
