# 业绩归因 · 多笔支付订单归属以首笔支付时间为准

> **只解决**：一个订单分多笔支付（付款计划有多期），质疑"应按尾款/最后一次支付判给后面的顾问，为什么判给了首笔支付时的顾问"。
> 业绩表查不到这单 / 归属人为空或不对走 [`查不到归属人.md`](查不到归属人.md)；
> 判单正常但排行榜显示 0 走 [`判单正常但排行榜显示0.md`](判单正常但排行榜显示0.md)。

## 结论（判单口径）

**多笔支付订单的判单时间锚点取首笔支付时间 `firstPaidTime`（付款计划里 `showOrder = 0` 的首付），不是尾款。**

因此当首付落在 A 顾问/前置班保护期窗口内、尾款落在 B 窗口内时，判单必然命中 A。**这是设计行为，不是 bug**，不需要回溯或改归属。

## 判定入口

先确认这单确实是多笔支付，再谈口径：

1. 付款计划有 2 笔及以上（首付 / 第二期 …），订单渠道显示"多笔支付"。
2. 判单侧口径：订单消息 `payInfo.payPlanType = PayPlanTypeEnum.INSTALLMENT_PAYMENT(1,"多笔支付")`。
3. 若 `payPlanType != 1`，`firstPaidTime` 就等于本次 `paidTime`，本篇口径不适用。

## 排查（证据链）

1. 支付事件构造凭证时，首笔时间由 `OrderMsgUtils.setFirstPaidTime(paidTime, payInfo)` 决定
   （`performance-attribution-web` `util/OrderMsgUtils.java:48`）：
   - 非多笔支付 → 返回 `paidTime`；
   - 多笔支付 → 从 `payInfo.payPlanBO.payPlanItemBOS` 里取 `showOrder == 0` 那笔的 `payRecordBO.paidTime` 作为 `firstPaidTime`（取不到则回退 `paidTime` 并打 `not found first pay record in multi-pay occasions`）。
   - K12 大班课在 `mq/rocketmq/handler/attribution/bigclazz/OrderPaySuccessEventHandler.java:82` 调用后塞进 `AttributionCredential`。
2. `AttributionCredential.firstPaidTime` 注释即口径本身
   （`domain/dto/attribution/AttributionCredential.java:97-100`）：
   *"首笔支付时间，对于多笔支付订单，该字段和支付时间 paidTime 不相同；对于非多笔支付订单，该字段和支付时间 paidTime 相同"*。`paidTime` 是尾款/本次支付时间。
3. 保护期判断用的就是 `firstPaidTime`，不含尾款：
   - `strategy/attributionType/protection/ProtectionPeriodFromClazzRenewalConfigStrategy.java:32,49-51`：
     `protectBeginTime ≤ firstPaidTime < protectEndTime` 才命中前置班续班保护期；
   - `.../ProtectionPeriodFromPaidTimeStrategy.java:52`：前置订单需在 `firstPaidTime` 前 365 天内。
   - 新单/召回、`EarliestPayTimeStrategy` 等同样以 `firstPaidTime` 为当前订单时间锚点。
4. 尾款 `paidTime` 只出现在少数旁路（如 CA 协作单 `strategy/employeeid/EmployeeIdFromCrm.java:208` 传给 `getAssistantOrder`），**不参与保护期/续班判单**。

> 注意分清两类"支付时间最早/最近"策略（`uniqueOrder/EarliestPayTimeStrategy`、`uniqueOrder/MostRecentPayStrategy`）：它们是**多个前置订单之间**的择优，与"本单按首笔还是尾款"无关，别混。

## 验证

- 用订单号捞 `performance-attribution` 的判单日志，核对保护期策略打印的 `paidTime`/筛选结果是否等于**首付时间**：
  `ProtectionPeriodFromPaidTimeStrategy running, orderNumber is {}, paidTime is {}`。
- 核对 `performance_attribution_credentials`（prod DMS `cluster_id=259`）该单，比较首付时间与最终归属，应与首付时间的归属一致。
- "系统判给了 A"与首付时间所在归属一致 ⇒ 结论成立；若最终归属与 `firstPaidTime` 所在窗口也不一致，才转 [`查不到归属人.md`](查不到归属人.md) 走判单主干排查。
- 光凭"多渠道/多期支付 + 归属变了"不能下结论，必须核到 `firstPaidTime`。
