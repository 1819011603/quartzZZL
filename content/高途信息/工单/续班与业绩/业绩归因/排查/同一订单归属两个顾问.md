# 业绩归因 · 同一订单归属两个顾问

> **只解决**：续班订单双归属、取消重下后从单归属变成平分。

## 判定入口

先区分待支付判单与真实支付业绩。页面显示两个人，不代表已产生两份支付业绩；同时在保护期也不等于必然平分。

## 排查

1. 在 gaotu-stats-prod（cluster 259）按 `order_number` 查询 `gaotu_stat.performance_attribution_credentials`，比较两次订单的 `seller_id`、`stage`、`create_time`。不要直接用凭证表无索引的用户字段大范围扫描。
2. 按订单号查 `performance_attribution_judge_reason`，对比 `rule_result` 的保护期和续班关系、`unique_order_result` 的“按同辅导筛选”，以及 `pre_order_detail`。
3. 待支付结果查 `performance_order_attribution_no_pay` 的前置订单、邮箱及 `price_ratio/user_ratio/order_ratio`；实际支付结果另查 `performance_order_attribution`。不能把 no_pay 中的状态字段直接当成已支付凭据。
4. 若销售标识不同，查创单消息 `extParam.sellerId`，结合页面订单来源判断是否 boss 生单与 app/H5 下单的差异；不要用“顾问发过链接”替代实际携带 sellerId 的证据。
5. 代码入口：`SameAssistantTeacherStrategy#getUniqueOrder`、`AbstractPerformanceAttributionStrategy#judgePreOrder`。sellerId=0 时同辅导返回空，策略链恢复上一步候选继续筛选；命中同辅导且非空时立即返回。具体规则是否适用以当次判单记录为准，不能泛化为所有保护期订单。
6. 回应"判单逻辑是否变过"：对涉事策略文件跑 `git log origin/master -- <文件>` 看最后实质改动时间（本例同辅导策略 2024-03-29 后未动），再对比判单原因落库；代码层面未变 ≠ Apollo 开关/配置没改，开关历史另走[判单开关溯源](判单开关溯源与回溯补数据.md)。
7. 回答"第一次创单是几号/订单号"：订单创建与取消时间用 OES `POST /orderComponent/orderFieldSearch`（`user` 传手机号）取 `createTimeAsTimestamp/updateTimeAsTimestamp`；状态含义以 order 仓库 `NeoOrderStatus` 为准（4=手动取消、5=自动取消，页面均显示"已取消"），创单人看订单事件消息 `ext_param.seller_id` 或 operate-log `operatorUserId`，别拿 cas/员工表另一套 ID 体系硬套。

## 验证

至少对齐两次凭证、判单原因和结果占比；支付前的结果仅称“待支付判单结果”。招生课分给不同顾问属于 CRM 分配链路，另核真实 `purchaseIntentionId`、`modelType`、规则和分配事件，不能仅按页面品类同名推断同一分配口径。
