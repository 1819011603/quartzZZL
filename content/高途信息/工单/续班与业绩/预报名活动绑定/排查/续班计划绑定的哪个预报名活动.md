# 续班计划绑定 · 按续班计划查绑定的预报名活动

> **只解决**：已知「续班计划 number」，查它的预报名流程节点到底绑定了哪个预报名活动；以及活动被删后代课/花名册仍能看到预报名活动时，怎么解释与怎么改。
> 预报名活动本身的增删改（列表/详情/发布/作废）问题走 [`知识库/promotions/pre-register-activity/_page.md`](../../../../知识库/promotions/pre-register-activity/_page.md)。
> 「按问卷ID查绑定的续班计划」是另一对象，走 [`../../续班问卷绑定/排查/问卷绑在哪个续班计划.md`](../../续班问卷绑定/排查/问卷绑在哪个续班计划.md)。

## 判定入口

- 「续班计划 detail 页 + 续班流程」的预报名配置节点绑定关系，权威表是 **`gaotu.renewal_link_activity`**（product-server，`gaotu` 库），不是 `node_config`（`node_config.ext_config` 为空，活动号不落这里）。
- 链路：`续班计划 number` → `process_config`（`renewal_number=计划号`、`type=3`=预报名）→ `node_config`（`process_number`、`type=4`=预报名配置 / `type=5`=预报名链接发放）→ `renewal_link_activity`（`process_number` + `node_number` → `activity_number`）。
- 两个口径别混：`续班计划 number`（`renew_master.number`，17 位）≠ `预报名活动 number`（`pre_order_activity.number`，18 位，如 `587024504451006464`）。前端 JS 会截断 18 位精度，传参/赋值一律按字符串。

## 排查

### 1. 计划 → 绑定的预报名活动

```sql
-- gaotu 库（product-server）：流程 + 节点 + 绑定活动
SELECT p.number AS process_number, p.type AS process_type,
       n.number AS node_number, n.type AS node_type,
       a.activity_number, a.is_del AS link_del, a.create_time AS link_time
FROM gaotu.process_config p
JOIN gaotu.node_config n ON n.process_number = p.number
LEFT JOIN gaotu.renewal_link_activity a
       ON a.process_number = p.number AND a.node_number = n.number
WHERE p.renewal_number = '<续班计划number>'
  AND p.is_del = 0 AND n.is_del = 0;
```

- `process_type=3`（预报名）/`node_type=4`（预报名配置）那行才是绑活动的地方。
- `renewal_link_activity` 一行 = 该节点当前绑定的活动。`link_time` = 当初绑定/新建活动的时刻，可据此与候选活动的 `create_time` 对齐判断绑的是哪一个（同一节点一般来说只有一条有效行）。
- 注意 `renewal_link_activity.is_del` 只是该绑定行自己的标记；**活动在预报名活动页面被删（`pre_order_activity.is_del=1`）不会把这一行置删**，要交叉查活动主表（下一步）。

### 2. 活动主表（活动是否已被删/什么状态）

```sql
-- promotion 库（cluster `prod-marketing-promotion`，db `promotion`）
SELECT number, name, type, activity_status, begin_time, end_time, is_del, create_time, update_time
FROM promotion.pre_order_activity
WHERE number IN ('<活动1>', '<活动2>');
```

- `is_del=1` = 该活动已在「预报名活动」页删除；`activity_status`：0=待发布 / 1=发布中 / 2=待开始 / 3=进行中 / 4=已结束 / 5=已暂停 / 6=已作废。
- 库名/集群不要猜，`mysql_query` 传 `promotion.pre_order_activity` 会要你选集群，选 `prod-marketing-promotion`。

### 3. 「活动删了，代课还看得到」的根因

- **删活动不级联清计划绑定**：预报名活动页的删除 → promotion `PreOrderActivityService#delete`（`promotion-app/.../service/preorder/PreOrderActivityService.java:810`）只置 `pre_order_activity.is_del=1`，**不动** product-server 侧的 `renewal_link_activity`；计划仍指向这个已删活动。
- **已删活动仍能被解析出来**：`PreOrderActivityRepository#getByNumber` **不过滤 `is_del`**；状态延迟消费者 `PreOrderActivityStatusDelayConsumer` 也是按时间把状态推到「进行中」，不看 `is_del`。所以即便活动被删，计划详情/代课/花名册按活动号取详情仍能拿到「进行中」的活动 → 表现为"还在、还能看到"。
- 附带坑：删活动本应仅限「待发布」状态（`delete` 校验 `WAIT_PUBLISHED`），若在待发布时删除、随后 began 时间到了，延迟 MQ 仍会把已删活动状态刷成「进行中」，`is_del` 与 `activity_status` 就出现"已删却在跑"的组合。

## 验证

- 第 1 步查出的 `activity_number` 与「当初在计划里新建的那个活动」的 `create_time` 对齐（`renewal_link_activity.create_time` 通常等于该活动 `pre_order_activity.create_time`），即可确认绑的是哪一个。
- 用计划号调 product-b 的 `renewal/process/list`，返回的 `preOrderActivityNumber` 应与第 1 步一致。
- 改绑：在续班计划 → 续班流程 → 预报名配置里重新绑定目标活动（走 `bind`/`edit`，写 `renewal_link_activity`）；改完回读第 1 步确认 `activity_number` 已变。要清掉指向已删活动的残留绑定，改绑到有效活动即可覆盖（无独立解绑入口）。
