## 结论

不是王永诗查法的问题，也不是配置缺失或 bug：这两门课的续班关系判定走的根本不是 `course_relation_map` 这条路径，而是判单服务（performance-attribution）"前置续班课程"策略（`renewalRelationRestrain=前置续班课程`，对应 `RenewalRelationByCourseConfigStrategy`）里的**系列课"同学部+同科目"分支**：

```java
// RenewalRelationByCourseConfigStrategy.java 61-96行
if (courseCategoryId == SERIES_COURSE(系列课, code=40)) {
    命中 = (同科目 subjectId 一致 AND 同学部 departmentId 一致) || 命中 course_relation_map 配置
} else {
    命中 = (同科目 AND 同主讲 lecturerNumbers 交集) || 命中 course_relation_map 配置
}
```

当前订单课程 `23KXTJ26QK8K1` 的 `courseTypes=40`，等于 `CourseCategoryEnums.SERIES_COURSE.getCode()`（`courseCategoryId` 字段就是直接取 `courseTypes`，见 `CourseConverter.java:221`），走的是**系列课分支**，这个分支根本不看主讲，只看同科目+同学部：两门课 `subjectId` 都是 126、`schoolDepartment`（映射为 `departmentId`，见 `CourseConverter.java:225`）都是 20，两项都满足即直接命中，跟 `course_relation_map`（已确认两个方向 0 条）无关。

排查过程中曾误判为走"同科目+同主讲"分支（非系列课分支），并用"整体命中=真、beforeCourse=假"反推"同主讲必然为真"——这个反推被王永诗提供的 OES 截图推翻：两个班的主讲（方展 vs 李雪冬/王冰/王泽龙/曹云霞）完全不重合。**教训：能实测的字段一律调接口查实际值，不能靠外层结果反推内层条件**，重新读代码 61-68 行发现遗漏了"是否系列课"这个前置分支判断，才定位到真正命中的是同学部+同科目这条。

## 当前状态与处置

已解决，无需运营侧处置。核心认知：`course_relation_map` 只覆盖"前置续班课程"策略里的一条命中路径，**该课程分类是系列课时还有一条不依赖该表、也不看主讲的"同学部+同科目"兜底路径**，OES「续班设置」页面只展示 `course_relation_map` 的数据，天然看不到这条兜底路径命中的记录——这是设计内行为，后续同类反馈可直接按此结论解释，不必再走 myreview 页面。
